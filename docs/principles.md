# 黑潮 DNS 的核心理念與設計原則

這份文件寫的是「黑潮為什麼這樣設計」。新增功能、修問題、調整預設值、寫測試報告之前，先對照這裡，避免越改越偏。各功能的細節在 [README](../README.md) 與 [規格](spec/README.md)；這裡只寫不會隨版本變的方向，以及兩個最容易走偏的特別情境。

## 一、黑潮是什麼

黑潮讓每一台黑潮都能自己拿到**真實、乾淨、快**的 DNS：

- **真實**：繞過劫持與竄改。答案要能用網站的 TLS 憑證證明是對的。
- **乾淨**：擋廣告、遙測、惡意與詐騙網站。
- **快**：CDN 的回應換成實際驗證過的台灣節點，把連線帶回台灣。

使用者選黑潮，就是想繞過阻擋、拿回自己的網路。

## 二、六條原則

### 1. 目的優先：台灣節點是黑潮的本質

- 功能不為了省資源而砍掉。CDN 台灣節點置換是黑潮存在的理由，任何機器都不「關掉」。
- 小機器是**減量**，不是關掉：找出最花資源的部分減少次數（例如 `cdn.lite`：只驗證問過 2 次以上的網域、每分鐘上限），保留功能本身。
- 追求快的前提是正確：要回給裝置的台灣節點一定先驗證過；朋友分享、上游傳承、種子資料、匯入的資料都只當候選或起點。

### 2. 不當攻擊者，也不讓自己被封殺

- 每日評測、劫持探測、雙層黑潮的共用結果，都是為了**不要對同一批伺服器重複大量查詢**。否則：
  - 測來測去，測到的都是同一台劫持伺服器（路上的攔截者會把所有一般 DNS 都接走）。
  - 大量流量對上游像攻擊。
  - 被上游封殺之後，整個網路就異常了。
- 所以要**分散、限速、共用、不重複做**：背景工作有排隊上限與並行數，失敗的上游暫停並逐次拉長暫停時間，同一個名稱同時只問一次，兩台黑潮之間共用結果。
- 判斷流量的標準是「有沒有浪費、有沒有重複」，不是「越少越好」。為了拿到真實的台灣節點而多用一點流量是值得的；同一件事一直重做、一直重複下載、對同一台伺服器大量查詢，才是問題。

### 3. 每一台黑潮都有自由

- 每一台黑潮都是獨立運作的個體，有自己的過濾清單、自己的加密上游、自己的判斷。
- 上游的過濾是上游的政策。下游有自己的 DoT／DoH 可以防劫持，**要不要擋，由下游自己的清單決定**（見第三節）。
- 「下游可以繞過上游的阻擋」不是漏洞，是設計：真的要管住區網裝置，是上游關掉 `allow_downstream`、在網路層管制，不是靠 DNS。

### 4. 上下游是「直系血親」：繼承但查核

- 兩台黑潮之間是自動成立的好友關係（社群共享的變種）。上游會把資料傳承給下游，像評測結果、節點池，下游不必重做一樣的事（過濾清單 3.4.3 起不傳：每台自己跟清單網址下載，拿到的就是正本）。
- 但下游是**有想法的個體**，不深度依賴上游：
  - 保有自己收集資料的能力：自己的工作定期照跑，自己的資料比較新時不被上游蓋掉。
  - 拿到的資料自己查核：匯入時檢查格式、範圍、簽章，並抽查上游給的答案。
- 原因：節點金鑰是每台自己產生的，「驗證過」只證明對方會講黑潮的協定，不證明它是誰。上游可能是偽裝的，也可能有問題。

### 5. 走安全的路線

- 雙層黑潮、特殊網路環境都不常見，**不做激進優化**，寧可多花一點資源，也不要冒險。
- 任何新機制都要：
  - **有上限**：時間、次數、記憶體、連線數。
  - **會自己恢復**：壓力解除、上游回來、網路恢復後，不需要人去處理。
  - **不形成風暴或迴圈**：一筆查詢不能放大成大量查詢；不能反覆停用／恢復、反覆下載、反覆暫停／接回。
- 判斷錯誤時的最壞情況，要是「退回單獨運作」這種本來就會走的路，不能是斷線或錯誤的答案。

### 6. 不做讓效能變差的修改

- 主要的目標硬體是 MT7621 這類兩核心、沒有 AES 指令、32 位元的路由器。
- 每筆查詢都會走到的路徑上，不新增鎖、配置與系統呼叫。背景工作要能在小機器上排得完。
- 32 位元 MIPS 沒有 64 位元原子操作，計數器用 32 位元。

## 三、特別情境一：上下游都是黑潮（串接）

兩台黑潮前後接著（例如 D3 接在跑黑潮的主路由器後面）時，原則 2（不重複做）和原則 3、4（自由、不深度依賴）要同時成立。做法：

| 情況 | 黑潮怎麼做 | 為什麼 |
|---|---|---|
| 下游發現一般 DNS 被上游黑潮接走 | 用節點金鑰簽章驗證身分之後，把上游當第一順位上游，不再同時問自己的加密上游 | 省下下游的 TLS 負擔，上游也不會被重複查詢 |
| 上游回 SERVFAIL（它自己的上游與備援都解析不到） | 就是最後答案，不再問自己的上游 | 剛註冊的網域一多，重做只會重複使用網路、在下游做 CDN 驗證 |
| 上游擋掉（0.0.0.0），下游自己的過濾沒擋 | 用下游自己的加密上游解析一次；自己的上游也沒有答案時才照上游的擋 | 原則 3：下游自己決定要不要擋 |
| 上游完全沒回應 | 那一筆改問自己的上游；連續 3 次暫停串接 30 秒 | 不讓上游掛掉拖累下游 |
| 上游給的 CDN 答案 | 照用（上游已經驗證、換好台灣節點），但每 16 筆抽 1、每 30 秒最多 1 個檢查 TLS 憑證；不符時用自己的上游比對，1 小時內 3 次可疑就暫停串接 | 原則 4：繼承但查核 |
| 上游給的評測結果、節點池 | 照用，略過自己的工作；但自己超過 7 天沒跑就照排程自己跑一次，自己的比較新時不被蓋掉 | 原則 4：保有自己的能力 |
| 過濾清單 | 每台自己跟清單網址下載（3.4.3 起；3.4.0～3.4.2 跟上游拿副本）。下游沒辦法證明上游給的就是正本，而且清單決定這台擋什麼；下載一份清單只是一個 HTTPS 請求、大多回 304，不像評測會對大量伺服器查詢 | 原則 3、4：要不要擋、擋哪些由自己決定，拿正本 |
| 防迴圈 | 節點 ID 鏈，A → B → A 不會串起來，最多 4 層 | 原則 5 |
| 剛開機還不知道會不會串接 | CDN 的定時檢查、背景工作的補跑先等串接確定（都有上限：3／10 分鐘） | 不在串接建立前就把該省的工作做掉 |
| 上游關掉 `allow_downstream` | 下游自己算（重複使用網路），每 10 分鐘探測一次，上游重新開放就自動接回 | 尊重上游的選擇，也會自己恢復 |

刻意不做的事：

- 不做「下游永遠不自己算」這種深度依賴。
- 不擋下游繞過上游的阻擋（原則 3）。
- 不為了雙層黑潮做會影響單台使用者的激進優化（原則 5）。

規格：[10-chain.md](spec/10-chain.md)（第 1.6 節回答怎麼用、第 3.8 節直系血親）。

## 四、特別情境二：上游或業者劫持

台灣常見的情況：業者或上游路由器把所有 53 埠的一般 DNS 接走、把「不存在」改成廣告頁、竄改特定網域、擋掉 DoT（853 埠）或 QUIC。黑潮用**路徑檢查**分辨「上游壞了」和「路上有人動手腳」，再照實際的路調整，不冤枉正常的上游。

| 情況 | 怎麼發現 | 黑潮怎麼做 |
|---|---|---|
| 一般 DNS 被接走（53 埠全部轉走） | 對文件用的保留位址（`192.0.2.1` 等）查詢，有回答就是被接走 | 每日評測不測一般 DNS；執行時一般 DNS 的回答不參加多數決、不合併 IP，只當最後備援。一般 DNS 的答案完全一樣時只算一票（幾百台一般 DNS 其實都是同一個攔截者） |
| 攔截者是黑潮 | CHAOS TXT `version.kuroshio` | 進入串接（第三節） |
| 攔截者是業者或不明設備 | `version.bind` 等 | 狀態頁寫成白話；用自己的加密上游 |
| 「不存在」被改寫 | `.invalid` 底下的隨機名稱有回答 | bootstrap（解析加密上游的主機名稱）改用 IP 直連的 DoH |
| 答案被竄改 | 知名網域（`dns.google` 等）的答案不對 | 同上；攔截者是黑潮時解除串接（`tampered`） |
| 加密協定整條被擋 | DoT、DoH、QUIC 各試三台知名伺服器 | 那種上游先不用、評測也不測；路恢復了自動加回 |
| TLS 中途攔截 | 好幾台伺服器都出現憑證錯誤 | 顯示提醒 |
| 上游的答案被汙染 | 每日評測用網站憑證檢查答案 | 憑證不符要在不同的 2 天發生才列入黑名單；同業者 3 家以上加密 DNS 都連不上同一個網站、或多家 CDN 的網域連不上時，照常計分、不記可疑；30 天沒再發生就忘掉 |
| 上游一直失敗或時好時壞 | 連續失敗次數 | 暫停 1 → 2 → 4 分鐘逐次拉長；穩定 10 分鐘後才重新從 1 分鐘算 |

重點：

- **不冤枉**：依路徑檢查略過的候選（一般 DNS 被接走、沒有 IPv6、協定被擋）不記可疑、不進黑名單。
- **不攻擊**：評測分批、限並行數，不對被接走的一般 DNS 灌大量查詢（原則 2）。
- **憑證是最後的裁判**：DNS 答案可以被竄改，網站的 TLS 憑證很難偽造。CDN 驗證、評測的汙染判斷、串接的答案抽查，都用同一個標準。

規格：[README 的路徑檢查](../README.md#路徑檢查336)、[整合文件](integration.md#路徑檢查336-起)。

## 五、改東西之前的檢查清單

新增或修改功能、調整預設值、接受別人的建議之前，逐條問：

1. 有沒有讓黑潮拉回台灣節點、拿到真實答案的能力變弱？要減量的話，是「少做不值得做的」，還是「整個不做」？（原則 1）
2. 會不會對同一批伺服器重複大量查詢、一直重做同一件事、一直重複下載？有沒有排隊上限與並行數？（原則 2）
3. 有沒有替下游做了它自己的決定，例如強迫照上游的擋？（原則 3）
4. 有沒有讓下游更依賴上游，卻沒有查核、沒有保留自己的能力？（原則 4）
5. 有沒有上限？壓力解除、上游回來、網路恢復後會不會自己恢復？最壞情況是什麼？會不會反覆來回？（原則 5）
6. 在 MT7621 上，每筆查詢的路徑有沒有變慢？背景工作排得完嗎？（原則 6）
7. 文件、測試、範例只用 `example.com`／`example.net` 與文件用 IP（`192.0.2.0/24`、`198.51.100.0/24`、`2001:db8::/32`），不寫真的網域與公網位址。

測試報告也照這個標準判斷：好的結果是「功能都在、有上限、不放大、不迴圈、壓力解除後會自己恢復」。「流量是 0」不是目標。
