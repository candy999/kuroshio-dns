# 11 3.5.0 工作包規劃

這份是 3.5.0 的工作分解：使用者與測試者（老毛子 D3、Windows）在 3.4.x 累積下來的 30 個項目，分成 A（每日評測與預設名單）、B（CDN 台灣節點）、C（系統、串接、記憶體、儲存）三組；另外加上 E（觀測與線路感知，第 5 節）：資料新鮮度、發現清單、這條線到得了哪些台灣機房、機房層級的健康。每個工作包寫明範圍、現況（實際讀過的檔案與函式）、設計、注意事項、測試與文件。

設計方向一律對照 [核心理念與設計原則](../principles.md)；串接相關的沿用 [10-chain.md](10-chain.md)，記憶體沿用 [09-memory.md](09-memory.md)，儲存沿用 [05-resources.md](05-resources.md)。

分支：`dev/3.5.0`（內容等於已發布的 3.4.4，另外已經有 C7、C8 的修改）。

## 0. 共同規定（每個工作包都適用）

### 0.1 硬性限制

- **硬體**：主要目標是 MT7621：2 核心、沒有 AES、32 位元、**沒有 64 位元原子操作**（不能用 `AtomicU64`／`AtomicI64`；計數器用 `AtomicU32`，要 64 位元就放在既有的 `Mutex` 裡）。RAM 小（D3 512 MB，也有 128 MB 的機器），狀態分割區可能只有 7.5 MB Flash。
- **效能**：不做讓效能變差的修改。每筆查詢都會走到的路徑（`resolver.rs` 的 `serve()`／`ask()`、`optimizer.rs` 的 `apply()`、`upstreams.rs` 的 `select()`／`record()`、`filtering.rs` 的比對）不新增鎖競爭、配置與系統呼叫。新功能要記東西時，先想能不能放在背景工作、評測子程序或管理 API 被呼叫的那一刻。
- **MSRV 1.80**：不能用 `Option::is_none_or` 這類較新的 API；延遲初始化照現有程式的寫法用 `OnceLock`。
- **原則**：每台黑潮獨立自由；上下游與好友只是輔助，拿到的資料自己查核；不當攻擊者（不對同一批伺服器重複大量查詢、不重複做同一件事，標準是「不浪費、不重複」）；任何機制都要有上限、會自己恢復、不形成風暴或迴圈；不做激進優化；小機器是「減量」不是「關掉」。
- **學習資料都要有上限**（筆數或位元組），寫進狀態目錄的要算進小 Flash 與每日寫入額度（`system.flashWriteBudgetKB`，預設 4,096 KB），並在 `space.rs` 的 `tier_of()` 歸類（能重建的歸 `Rebuildable`）。
- **範例**只用 `example.com`／`example.net` 與文件用 IP（`192.0.2.0/24`、`198.51.100.0/24`、`2001:db8::/32`；區網 `192.168.1.1`／`192.168.1.2`）。不採用 hosts 類清單的 IP 當答案或節點。測試一律用本機的假伺服器（`127.0.0.1:0`），不連網際網路；跟時間有關的測試用注入的時鐘（`JobCtx::with_clock`、`tokio::time::pause`），不用真的 `sleep`。
- **驗證**（每個 PR）：

  ```
  cargo fmt --all --check
  cargo clippy --all-targets -- -D warnings
  cargo clippy -p kuroshio --all-targets --features acme -- -D warnings
  cargo test --workspace
  ```

  行為改變要有測試、更新對應文件與 `docs/release-notes/v3.5.0.md`（這個檔還沒有，第一個合併的工作包建立）。
- 文件、介面文字、日誌、commit 訊息用繁體中文（台灣用語）。

### 0.3 評測學習資料共用一個檔

A2、A4、A6、A7 都要記「跨天的評測紀錄」。為了小 Flash，不各開一個檔，共用 `state/benchmark-learn.json`（寫入器會壓成 `.zst`）：

```json
{ "v": 1, "day": 20781,
  "control": { "<id>": "ddddpd-u…" },
  "hist":    { "<id>": { "t": 1073741823, "s": 1073741820, "q": 0, "ms": 12, "last": 20781 } },
  "h3skip":  { "<id>": { "f": 3, "n": 1, "until": 20790, "last": 20783 } },
  "neverOk": { "<id>": { "since": 20780, "n": 2 } } }
```

- 由評測子程序在每次評測結束時寫一次（每天一次）；`neverOk` 由主程式在事件發生時登記到記憶體，下一次評測開始前由主程式寫出（見 A7）。
- 上限：`hist` 2,000 筆、`control` 64 筆（同 `MAX_PROTECTED`）、`h3skip` 512 筆、`neverOk` 32 筆；超過時先丟名單裡已經沒有的 id，再丟 `last` 最舊的。原始大小上限約 160 KB，壓縮後估 50 KB 以內。
- **實作（A4）**：`hist` 每筆寫成陣列 `[t, s, q, ms, dv, e, last]`（物件寫法 2,000 筆會超過讀檔上限）：`q` 改成位元遮罩（哪幾天有汙染／可疑，才會跟著 30 天滾動；單一計數器沒辦法過期）、多 `dv`（延遲的平均偏差）與 `e`（升降狀態）。2,000 筆原始約 130 KB、壓縮後幾十 KB 以內（測試 `hist_roundtrip_and_capped_at_2000_drops_unlisted_first` 檢查在 64 KB 以內）；讀檔上限 `MAX_RAW` 從 256 KB 放寬到 384 KB。
- `space.rs` 的 `tier_of()`：歸 `Rebuildable`（丟了只是重新學，不影響正確性）。不進備份的分享檔、不傳給下游與好友（原則 4：自己的判斷自己累積）。
- 讀不到、格式不對、`v` 不認識：當成空的，照人工分級跑，不失敗。舊版不讀這個檔。
- `day` 用「本地日期的日數」（`u32`），位元遮罩 `t`／`s` 是 `u32`（近 30 天，最低位是 `last` 那天）；跨天時依日數差左移。系統時間倒退（還沒對時）時不寫、不位移。

## 2. A 組：每日評測與預設名單

評測的程式在 `crates/kuroshio-jobs/src/benchmark/`（`mod.rs` 的 `Benchmark::run_inner()` 是整個流程：路徑檢查 → 候選 → Phase 0 資格賽 → Phase 1 收集與逐網域判斷 → Phase 2 查業者 → `compute()`／`select::select()` → 寫 `upstreams.json`）。主程式用子程序跑（`crates/kuroshio/src/benchjob.rs` 的 `BenchJob`、`child_main()`），所以評測裡多用一點記憶體不影響常駐的主程式，但子程序同時的原始答案有 `PER_CANDIDATE_BYTES` 的估算與 `effective_conc()` 的限制，新資料結構要算進去。

### A1　名單標記

**目標**：讀出預設名單每一筆的標記，讓候選帶著標記走完整個評測。**不做**：標記不影響任何判斷（那是 A2～A5 的事）；不改名單檔格式。

**現況**

- `util.rs` 的 `parse_list()` 把 `#` 開頭的整行丟掉、其餘原樣回傳；`BenchPaths::read_lists()` 合併使用者的（`list_dir`）與程式附帶的（`default_list_dir`），用第一個欄位去重。
- `candidate_ids()` 回 `(Vec<String>, usize)`：`dohlist.txt`、`doqlist.txt`、`dotlist.txt`、`stamps.txt` 用 `pick_token()`／`split_whitespace()` 取第一個像網址的欄位，後面的文字（`# tier=A op=… ms=… ecs=1 src=… checked=…`）直接忽略。
- **`iplist.txt` 的格式不一樣**：檔頭寫明「同一行不可加註解，每個位址上一行的註解是它的資料」，上一行長得像 `# A <經營者>（AS…）…`，另外有 `# ---- A 級 ----`／`# ---- B 級 ----` 的分段行。`parse_list()` 把這些都丟了，所以一般 DNS 現在完全沒有分級資訊。
- `protected.txt` 由 `protected_ids()` 另外讀，只取 `filter=`。
- `stamps.txt` 沒有標記。

**設計**

- 新檔 `crates/kuroshio-jobs/src/benchmark/tags.rs`：

  ```rust
  pub enum Tier { A, B, User, Unknown }
  pub struct Tag {
      pub tier: Tier,
      pub op: String,          // 經營者（AS 名稱），最長 64 位元組，超過截斷
      pub ms: Option<f32>,     // 整理名單時量到的延遲，只當沒有歷史時的排序依據

      pub carrier: bool,
      pub filter: Option<String>,  // 對照組預期會擋的類型
  ```

  - 行內標記：`#` 之後以空白分開的 `key=value`；不認識的 key 忽略（之後加標記不用改舊版）。
  - 上一行標記（`iplist.txt`）：緊接在位址前一行的註解，第一個欄位是 `A`／`B` 就當 tier，其餘文字當 `op`（截到第一個全形或半形括號前）。分段行 `# ---- A 級 ----` 設定「目前的預設 tier」，沒有自己標記的行用它。
  - 使用者自己的名單（`list_dir` 跟 `default_list_dir` 不同時，來自 `list_dir` 的）：沒有標記的一律 `Tier::User`（使用者親手加的，A3 的分級不會把它排除）。
  - 都沒有：`Tier::Unknown`，A3 當成 B。
- `BenchPaths::read_lists_tagged(name) -> Vec<(String, Tag)>`：合併與去重規則同 `read_lists()`；同一個上游兩邊都有時，用使用者那一筆的網址、預設名單的標記（使用者沒寫標記時）。`read_lists()` 留著（`web.txt`、黑名單還在用）。
- `candidate_ids()` 改回 `Vec<Cand>`（`struct Cand { id: String, tag: Tag }`）：`h3://` 的候選沿用它的 `https://` 那一筆的標記；社群好友給的候選（`upstream-candidates.json`）一律 `Tier::B`（好友給的只是候選，不能靠別人的話升到 A）。
- `Srv` 加 `tag: Tag`（`Srv::new()` 多一個參數）；`protected_ids()` 改用同一個解析（`Tag.protected = true`、`Tag.filter`）。
- 輸出（只新增欄位）：`upstreams.json` 的 `selected[]` 加 `tier`（`"A"`／`"B"`／`"user"`）、`op`；`counts` 加 `byTier`；`final_csv()` 多 `tier` 欄放在最後（舊的欄位順序不動，`tests/parity` 的對照要跟著更新預期）。

**注意事項與預防問題**

- 標記是「人工整理時的資料」，只能當起點與排序依據，**不能讓有標記的候選跳過任何檢查**（資格賽、汙染、封殺、憑證）。這是原則 1「正確優先」。

- 容易走偏：不要順手把 `ms=` 當成今天的延遲用在選擇上（那是整理名單那天、那條線路量的）。

### A2　對照組

**目標**：對照組（`protected.txt`）補三件事：跨天的回歸比較、資格賽就過不了的要判得出原因、狀態頁看得到。**不做**：對照組照舊永遠不選、不記可疑、不進黑名單、不參加多數決；不因為對照組的結果自動改名單。

**現況**

- `Srv.protected: Option<String>`、`selectable()`／`learns()` 回 false；`protected_result()` 把結果分成 `detected`（淘汰原因是封殺／汙染／可疑開頭）、`passed`、`untested`（其他，包含「資格賽失敗」）。結果寫進 `upstreams.json` 的 `protected` 與報表的 `protected.csv`。
- 資格賽（Phase 0）：`PREFLIGHT_DOMAIN` 要解析到 `PREFLIGHT_EXPECTED` 兩個位址之一，否則 `kill("資格賽失敗 (…)")`。
- **測試者回報 SafeSurfer 連資格賽都過不了**：資格賽用的網域是一家公共 DNS 的主機名稱。家庭／兒童類的過濾 DNS 常把「其他公共 DNS 的主機名稱」也擋掉（防止繞過），所以很可能是資格賽網域本身被它擋了，結果被歸成 `untested`，對照組裡等於沒作用。**這是推測，要先看 `judge.log` 或 `protected.csv` 的 `reason` 確認**（是 `NXDOMAIN`／導向封鎖位址，還是連線逾時）。
- 介面：`data/dashboard/dashboard.js`、LuCI 的 `status.js`、`data/admin/app.js` 都沒有顯示對照組。

**設計**

1. **資格賽的對照組判斷**（`run_inner()` 的 Phase 0）：對照組的資格賽結果是 `Outcome::Blocked`（明確的阻擋：NXDOMAIN、封鎖位址）時，不算「沒測到」，`fail_reason` 寫成 `封殺 <資格賽網域>（資格賽）`，`protected_result()` 因此回 `detected`，報表另外加一欄 `stage`（`preflight`／`domain`／`probe`）。連線失敗、逾時照舊是 `untested`。一般候選的資格賽規則不變。
2. **跨天回歸**（`benchmark-learn.json` 的 `control`，見 0.3）：每台對照組記最近 30 天的結果字串（`d`＝判出、`p`＝沒判出、`u`＝沒測到、`-`＝那天沒跑）。評測結束時比較：
   - **回歸**：過去 7 天裡有 3 天以上是 `d`、今天是 `p` → `judge.log` 與主程式日誌各一行 WARN（「對照組 X 以前判得出過濾，今天沒判出：評測可能判不出這一類了」），`upstreams.json` 的 `protected[].regress = true`。
   - **整體回歸**：今天 `d` 的比例比過去 7 天的中位數少一半以上（而且今天有測到 8 台以上）→ 一行 WARN。這是在抓「評測網域檔或判斷規則改壞了」。
   - 只報告，不改變今天選出來的上游。
3. **預期值**（等 A5）：`upstreams.json` 的 `protected[]` 加 `expectMet`：`filter=` 裡的類型至少有一種今天有對應的探測（成人、追蹤、惡意）而且判出 → true；對應的探測今天失效（A5 的自我檢查沒過）→ null；有探測卻沒判出 → false。A5 完成前，只有 `malware` 的固定是 null（跟 3.4.2 `protected.txt` 檔頭寫的「只擋惡意的判不出來是預期的」一致）。
4. **顯示**：`/api/benchmark` 已經原樣回 `upstreams.json`，不用新 API。`dashboard.js` 的評測區塊加一張摺疊的表（上游、預期、今天、近 7 天、是否回歸）；LuCI `status.js` 與 Windows 設定頁各一行摘要（「對照組 44 台：判出 30、沒判出 2、沒測到 12；回歸 0」）。近 7 天的字串由評測寫進 `protected[].recent`（7 個字元），介面不用讀學習檔。

**注意事項與預防問題**

- 對照組不能反過來影響正常候選：不參加多數決、不進 `universe`（現有程式已經排除，改 Phase 0 時不要動到）。
- 「沒測到」很多（例如 DoQ 被擋的線路）是正常的，回歸判斷要排除 `u` 與 `-`，不然路徑檢查略過一類協定就會誤報。
- 對照組最多 64 台、每天各多查一輪網域，流量有上限；不要為了回歸報告加測第二輪（原則 2）。
- 隱私：`protected.csv`、`judge.log` 只有上游與測試網域，沒有使用者的查詢。
- 測試穩定性：回歸比較用注入的日期（`JobCtx` 的時鐘），不要用系統時間。

**測試**

- `control_blocked_in_preflight_is_detected`（假 prober 對資格賽網域回 NXDOMAIN）。
- `control_timeout_in_preflight_is_untested`。
- `control_regression_reported_not_enforced`：前 7 天 `d`、今天 `p` → `regress=true`，`selected` 跟沒有對照組時一樣。
- `control_history_capped_and_shifted`：31 天後字串長度還是 30；跳過幾天沒跑補 `-`。
- `ui-core.tests.json`：對照組摘要文字。
- 實測：老毛子直連，確認 SafeSurfer 那一台的 `reason` 與修正後的結果。

**文件**：README 的每日評測段、`docs/integration.md`（`upstreams.json` 的 `protected[]` 新欄位）、`data/benchmark/protected.txt` 檔頭（3.5.0 起的行為）。

**實作備註（3.5.0）**

- SafeSurfer：`reason` 的括號裡本來就分得出被擋（`NXDOMAIN`、`導向 …`）、答案不對（一串位址，導到封鎖頁）、連不上（`逾時`），但 `protected_result()` 一律歸 `untested`。同一次其他 DoH 都過資格賽，判斷是資格賽網域被擋 → 改資格賽判斷、不移出對照組。
- 跟設計第 1 點的差別：「有回答但不是預期的位址」（導到封鎖頁）也算，不只 `Outcome::Blocked`；而且資格賽被擋的對照組**照樣測網域**（不在資格賽就結束），網域判斷也判出時 `stage = domain`、`reason` 用網域判斷的，資格賽的說明另外放 `preflight`。
- `control` 的位移用自己的 `controlDay`（不是檔案的 `day`：主程式登記 `neverOk` 時也會更新 `day`）。`recent` 第一個字元是今天；資格賽網域被擋算 `d`。
- `expectMet`：`ads`、`adult`（與 `tracking`、`telemetry`）有評測網域對應；`malware` 等 A5，先是 `null`；資格賽網域被擋不算符合。
- 測試：`learn.rs` 的 `control_history_capped_and_shifted`、`control_regression_rules`；`tests/benchmark_control.rs`；`ui-core.tests.json` 的 `controlSummary`。

### A3　分級評測

**目標**：新設定 `benchmark.tiers`，小機器每天只測 A 級，A 級涵蓋不夠時從 B 級補；高階機器 A＋B 都測。**不做**：不是「小機器不評測」；不改選擇演算法 `select::select()` 本身。

**現況**：候選全部進 `all`（固定上游 → 對照組 → 一般候選），預設名單合計約 1,800 個候選（含自動產生的 `h3://`），A 級約 470 個。`effective_conc()` 依記憶體限制同時測幾個，但總量不變；MT7621 上每個加密候選都是一次沒有 AES 的 TLS 握手。

**設計**

- 設定 `benchmark.tiers`（字串）：
  - `"auto"`（預設）：實體記憶體小於 256 MB → `a`；其他 → `ab`。換算放在 `benchjob.rs` 的 `make_benchmark()`（子程序的 `child_main()` 也走這裡），跟 `cdn.lite` 在 `app.rs` 的作法一致。
  - `"a"`：A 級＋使用者自己加的（`Tier::User`）＋多樣性補位＋探索名額。
  - `"ab"`：全部（今天的行為）。
  - **待決**：512 MB 的 D3（MT7621）`auto` 落在 `ab`。要不要讓「沒有 AES 而且 2 核心以下」也用 `a`，等 D3 實測兩種設定的評測時間與流量再決定（第 6 節），3.5.0 先照記憶體。
- **多樣性保護**（`a` 模式；在路徑檢查略過、黑名單略過之後才算，因為一般 DNS 被接走時 A 級的 UDP 候選整批不測）：
  - 統計今天要測的 A 級候選：不同經營者（`Tag.op`）數、每種 `upstream.autoTypes` 類型的候選數。
  - 門檻（常數）：不同經營者至少 12 家、每種類型至少 8 個（那一類型在名單裡本來就不到 8 個的不算）。
  - 不夠時從 B 級補，最多 `B_FILL_MAX = 32` 個、同一個經營者最多 2 個：有歷史的依 A4 的歷史分數（倖存率高、穩定、沒有可疑紀錄），沒有歷史的依 `Tag.ms` 由小到大。
- **探索名額**：`a` 模式每天另外測一小批 B 級，讓 B 級有機會累積歷史（A4 才升得上來）。每天最多 `B_EXPLORE_MAX = 40` 個，用「日數＋候選 id 的雜湊」決定輪到誰（同一天重跑會測同一批，不會因為手動多跑幾次就把 B 級全測完）。約 1,300 個 B 級一個月左右輪完一次。
- `judge.log` 寫明：「今天測 A 級 N 個、補位 M 個（原因：經營者只有 9 家）、探索 K 個；B 級其餘 X 個今天不測」。`upstreams.json` 的 `counts.byTier` 與新的 `tiers`（`{ "mode": "a", "fill": M, "explore": K, "skippedB": X }`）。
- 不測的 B 級不算淘汰、不記任何紀錄（跟路徑檢查略過一樣）。

**注意事項與預防問題**

- **原則 1**：這是減量。A 級是「經營者明確的公共 DNS 與電信商」，本來就是選得上的主力；補位與探索保證不會只剩少數幾家。
- **多樣性是抗劫持的一部分**：A 級如果多半是同幾家大型任播業者，某一家在這條線路上被擋或被竄改時，候選就不夠了。補位門檻要用「今天實際要測的」算，不是名單上的總數。
- 小機器的評測時間：`a` 模式約 470＋72 個，是全部的三成；`timeoutMin` 150 分鐘不用調。
- 串接：下游照用上游的評測結果（原則 4），自己超過 7 天沒跑才跑一次，那一次也照自己的 `tiers`。
- 不要把「A 級」寫成信任等級：A 級一樣要過所有檢查，一樣會進黑名單。
- 設定位置：`defaults.json`、UCI 的 `benchmark` 區段會自動對應（`tiers` 沒有底線）、LuCI `advanced.js` 的評測區段加一個 `ListValue`、`fields.json` 加一個 `select`。

**測試**

- `tiers_auto_follows_memory`（`make_benchmark` 的換算，注入記憶體大小）。
- `tier_a_tests_only_a_user_fill_and_explore`。
- `fill_when_operators_short_after_path_skip`：一般 DNS 整批略過後，經營者不足 → 從 B 補，同經營者最多 2 個、總數不超過 32。
- `explore_slice_is_stable_within_a_day_and_rotates`（同一天兩次一樣、隔天不同、不超過 40）。
- `tier_ab_matches_previous_behaviour`（跟 3.4.4 的候選完全一樣）。
- 實測：D3 兩種模式的評測時間、流量、選出的上游有沒有變差。

**文件**：README 每日評測段、`05-resources.md`（小機器減量表）、LuCI 說明文字、`fields.json`。

**實作備註（3.5.0）**

- 程式在 `benchmark/tiers.rs`（純函式 `plan()`、`explore_slice()`、`auto_mode()`）；`run_inner()` 組完候選（路徑檢查、黑名單、`h3skip` 略過之後）才套用。換算放在 `benchjob.rs` 的 `tiers_auto()`／`make_benchmark()`，結果放在 `Benchmark::tier_auto`（測試與沒有換算時預設 `ab`）。讀不到記憶體大小時用 `ab`。
- 跟設計不同的地方：
  - **多一類「沿用」**：上一次 `selected[]`／`spares[]` 裡的 B 級今天照測（最多 `INCUMBENT_MAX = 16`）。選上游只看今天的結果，不沿用的話探索到的 B 級今天選上、明天不測就掉出去，執行中的上游每天換（原則 5：不反覆來回）。
  - **探索是分組輪流，不是每天雜湊抽 40 個**：B 級依 id 的 FNV-1a 排成固定順序、每 40 個一組，今天是「日數 mod 組數」那一組。每天獨立抽的話一個月只會測到約六成；分組保證名單不變時每一組輪一次就全部測過。
  - **多樣性只算會被選用的類型**（`upstream.autoTypes`），補位也只補這些類型；門檻用「今天實際能測的」算，`min(8, 今天那一種類型能測的個數)`、`min(12, 今天能測的經營者數)`。
  - 經營者沒有 `op=` 時用主機的可註冊網域（IP 用 /16）。
  - 執行時從未成功的（`neverOk`，A7）不論分級都照測（它要被這次評測算一次），但不算進多樣性。
  - `tiers` 多 `auto`、`a`、`incumbent` 三個欄位。
- 上限（`a` 模式每天比 A 級多測的 B 級）：沿用 16＋補位 32＋探索 40＝最多 88 個（加上 A4 的試用 24、升級 64，合計最多 176 個）。
- 測試：`tiers.rs` 的 `auto_follows_memory_and_parse`、`ab_tests_everything`、`explore_slice_is_stable_within_a_day_and_rotates`、`tier_a_tests_only_a_user_fill_and_explore`、`fill_when_operators_short_after_path_skip`、`fill_is_capped_and_per_operator`；`tests/benchmark_tiers.rs` 的 `tier_a_tests_only_a_user_fill_and_explore`（今天不測的 B 級一筆查詢都沒收到）、`tier_ab_matches_previous_behaviour`；`benchjob.rs` 的 `tiers_auto_follows_memory`。

### A4　分級依評測歷史自動升降

**目標**：人工分級是起點，之後依這台自己近 30 天的評測歷史調整「實際分級」。**不做**：不改名單檔；不把歷史分享出去；不取代每天的檢查。

**現況**：沒有跨天的每台歷史（只有可疑天數 `Strikes` → `blacklist-suspects.json`，30 天沒再發生就忘掉）。

**設計**（細部由 Fable 定，這裡是框架與上限）

- `benchmark-learn.json` 的 `hist`（0.3）：每個測過的候選一筆：`t`（近 30 天哪幾天測過）、`s`（哪幾天倖存到最後）、`q`（30 天內可疑／汙染次數，飽和到 255）、`ms`（倖存那幾天平均延遲的 EWMA，整數毫秒）、`last`。
- 更新時機：評測結束、`write_json(upstreams_file)` 成功之後。評測失敗（`bail!`：沒有任何 DNS 通過資格賽、沒有倖存）**不更新**：那是本機網路的問題，不能記到候選頭上。路徑檢查略過、今天沒輪到的不動。
- **實際分級**（純函式 `effective_tier(tag, hist, today) -> Tier`）：
  - 測過不到 7 天：照人工分級。
  - **降級** A → B：測過 7 天以上而且倖存率低於 50%，或 `q` ≥ 2。
  - **升級** B → A：測過 10 天以上、倖存率 90% 以上、`q` = 0、延遲穩定（細部由 Fable 定義，例如近 10 次的變異係數）。升上來的最多 `PROMOTE_MAX = 64` 個（依歷史分數取前面的）。
  - 中間地帶（50%～90%）維持原本的，避免每天來回。
  - 對照組、固定上游、`Tier::User` 不參與升降。
- 降級的 A 仍然在 B 級的探索名額裡輪得到（A3），恢復了會再升回來：這就是「會自己恢復」。
- 歷史分數（A3 補位用）：`score = 倖存率 × 穩定度 −（可疑懲罰）`，細部由 Fable 定；只用來排序。
- `upstreams.json` 的 `tiers` 加 `promoted`、`demoted` 兩個數字；`judge.log` 列出今天升降的各前 20 筆。

**注意事項與預防問題**

- **不要冤枉**（principles 第四節）：路徑檢查略過、整批協定被擋、評測整個失敗，都不能算成「沒倖存」。倖存率的分母只算「那天真的測到它、而且評測成功」的日子。
- 線路換了（從串接改直連、換 ISP）歷史會不準：WAN 變動（`/api/notify/wan-changed`）不清歷史，但因為要 7 天以上才生效、30 天滾動，會自己修正；`judge.log` 寫明依據。
- 上限：2,000 筆。約 1,800 個候選加使用者自己的，放得下；超過時先丟名單裡沒有的。
- Flash：一天寫一次、壓縮後幾十 KB，算進每日額度；`tier_of()` 歸 `Rebuildable`，空間不夠會被刪，刪了照人工分級。
- 不形成迴圈：升降只影響「測不測」，不影響「選不選」；選擇仍然只看今天的評測結果。
- 32 位元：`t`／`s` 是 `u32` 位元遮罩，位移前先檢查日數差 ≥ 32 直接歸零（避免位移溢位 panic）。
- 測試穩定性：全部是純函式＋注入日期。

**測試**

- `hist_shift_across_days_and_gaps`（含日數差 ≥ 32、時間倒退不寫）。
- `demote_needs_seven_days_and_low_survival`、`promote_needs_ten_days_clean_and_stable`、`middle_band_keeps_tier`。
- `failed_run_does_not_touch_history`、`path_skipped_not_counted`。
- `hist_capped_at_2000_drops_unlisted_first`。
- `promoted_capped_at_64`。
- `learn_file_unreadable_falls_back_to_manual_tiers`。

**文件**：README 每日評測段、本檔 0.3 節的格式搬進 `02-architecture.md` 的 state 格式表。

**實作備註（3.5.0）**

- 資料在 `learn.rs` 的 `Hist`（`aged()`、`record()`、`rate()`、`stable()`、`score()`），規則在 `tiers.rs`（`effective_tier()`、`update_history()`、`history_bad()`、`demotion_fuse()`），都是純函式。`run_inner()` 在組候選時算實際分級、評測成功後（選上游之前、寫檔之後才存）更新。
- 細部定義：
  - **穩定度**：倖存那幾天的平均延遲做 EWMA（α = 1/4），另外記平均偏差的 EWMA（`dv`，同 TCP 的 RTTVAR）。穩定 = `dv ≤ max(ms × 0.5, 10 ms)`。不存最近 10 次的原始值（2,000 筆 × 10 個數字放不下）。
  - **歷史分數** = 倖存率 ×（1 − min(dv/ms, 1) × 0.5）− 0.25 × 可疑天數；只用來排序（補位、升級名額）。
  - **遲滯**：升 90%／降回 75%，降 50%／恢復 80%；狀態存在 `e`。
- 跟設計不同的地方：
  - **多一個「試用」狀態**。規劃裡 B 級要靠探索累積 10 天歷史才升級，但只測 A 級的機器一個 B 級約 33 天才輪到一次，30 天的視窗裡最多 1 天，永遠升不上來。所以探索（或補位、沿用）測到、今天倖存、30 天內沒失敗過、沒有可疑紀錄的 B 級先「試用」：每天測，最多 `TRIAL_MAX = 24` 個、每天最多新增 `TRIAL_NEW_PER_DAY = 8` 個（今天延遲低的先）；失敗 2 天或有可疑紀錄就結束，滿 10 天符合條件才升級，不符合或名額滿了就回到一般 B 級。失敗過的要等紀錄滾出 30 天才會再試用。
  - **降級的 A 級不排進探索、不補位**，靠歷史滾出 30 天（測到不滿 7 天）自己重新測。探索的分組改用人工分級算，升降才不會讓「今天那一組」在同一天裡變動。壞掉的 A 級 30 天最多測 7 次左右。
  - **保險絲**（規劃沒有）：依歷史要降級的超過今天 A 級的三分之一時，當天不採用降級、寫 WARN（換線路、某一種協定時好時壞）。
  - **整批協定失敗不記**（規劃沒有）：某一種類型 3 個以上、今天一個都沒過資格賽 → 那一種類型今天不記歷史（路徑檢查沒抓到的封鎖）。
  - 惡意網站探測判出「擋惡意網站」的候選（A5）當天算沒倖存。
  - `tiers` 除了 `promoted`、`demoted`，另外有 `trial`、`demoteFuse`、`promotedToday`、`demotedToday`。
  - 「今天先測誰」沒有做成測試順序：評測逾時是整次作廢，順序不影響結果；歷史只決定測不測與補位的順序。
- 上限（`a` 模式每天比 A 級多測的 B 級）：沿用 16＋補位 32＋探索 40＋試用 24＋升級 64＝最多 176 個；預設名單下合計最多約 650 個候選（全部約 1,800 個）。
- 測試：`learn.rs` 的 `hist_shift_across_days_and_gaps`、`hist_roundtrip_and_capped_at_2000_drops_unlisted_first`；`tiers.rs` 的 `demote_needs_seven_days_and_low_survival`、`demoted_recovers_by_evidence_or_by_expiry`、`promote_needs_ten_days_clean_and_stable`、`middle_band_keeps_tier`、`promoted_capped_at_64_and_trial_capped`、`path_skipped_not_counted_and_unlisted_dropped`、`demotion_fuse_trips_above_a_third`；`tests/benchmark_tiers.rs` 的 `failed_run_does_not_touch_history`、`history_demotes_a_and_pulls_up_b`、`demotion_fuse_and_unreadable_learn_file_fall_back_to_manual_tiers`。

### A5　惡意網站探測

**目標**：評測判得出「只擋惡意網站的 DNS」，這類一律不選（使用者決定：列為對照組那一類）。探測開始前先自我檢查，探測失效就不拿來判斷。**不做**：不連到探測網域的任何位址；不把探測結果記成可疑或黑名單（擋惡意網站不是竄改）。

**現況**：`web.txt` 有成人與追蹤網域，Phase 1 逐網域判斷時 `Outcome::Blocked` → `kill("封殺 …")`。沒有惡意網域；`protected.txt` 裡 `filter=malware` 的（Quad9 等）因此 `passed`。另外，汙染判斷會對可疑的回答做 `verify_answers()`（真的連到那個 IP 檢查憑證）。

**設計**

- **新檔 `data/benchmark/probe.txt`**（不放進 `web.txt`：舊版把 `web.txt` 每一行整行當網域，加標記會壞；新檔舊版不讀）。格式：`<網域>  # probe=malware src=<出處> checked=<日期>`，最多 `MAX_PROBES = 8` 個、每次評測實際用前 4 個可用的。使用者的 `list_dir` 可以有自己的 `probe.txt`（合併規則同其他名單）。
- **用哪一類網域（要人工確認，這份文件不寫實際網域）**：
  1. 首選：**已經被資安組織或執法單位接管（sinkhole）多年的知名惡意網域**。它們解析到接管方的位址、本身無害，而且各家「擋惡意網站」的 DNS 幾乎都列了。
  2. 次選：過濾服務商或測試組織為了「檢查防護有沒有生效」公布的測試主機名稱。缺點是通常只有那一家擋，只能驗那一家。
  3. **不用**：威脅情資清單裡還在活動的惡意網域（會變、有風險）。
  - 交付條件：名單由人挑、在沒有攔截的線路上確認「不過濾的 A 級都解析得到、對照組的惡意類都擋」，寫上出處與確認日期。這一步是 A5 的前置工作，不是程式。
- **流程**（Phase 1 的一般網域判斷完之後，新的一小段 `probe_malware()`）：
  1. 對象：對照組裡 `filter` 含 `malware` 而且通過資格賽的，加上目前倖存的一般候選。
  2. **自我檢查**（每個探測網域分開算）：對照組裡至少 2 家不同經營者回 `Blocked`，**而且**倖存的一般候選裡 70% 以上解析得到（不是阻擋）→ 這個探測有效。否則失效：寫 `judge.log`，不拿來判斷任何候選。
  3. 有效的探測裡，倖存的一般候選回 `Blocked` → 今天淘汰，原因 `封殺 <探測>（惡意網站探測）`。**不呼叫 `strikes.add()`、不進永久黑名單**（`learns()` 的路徑不走）；`upstreams.json` 的 `blocked[]` 照記，另外在 `judge.log` 建議「這台看起來有擋惡意網站，建議移到 protected.txt」。
  4. 需要兩個以上有效探測都擋才淘汰（單一網域可能剛好被某家誤列）；只有一個有效探測時，一個就算。
  5. 只認明確的阻擋（`classify()` 的 `Blocked`：NXDOMAIN、`0.0.0.0`／`::` 等封鎖位址）。回「另一個位址」（業者自己的警告頁）的 3.5.0 只記在 `judge.log`，不判。
- 探測網域**不進** `universe`（覆蓋率）、不做 ASN 汙染判斷、**不做 `verify_answers()`**、不算延遲。
- `upstreams.json` 加 `probe`：`{ "malware": { "domains": 4, "valid": 3, "blockedBy": 12 } }`；對照組的 `stage = "probe"`、A2 的 `expectMet` 用它。
- 設定：`benchmark.malwareProbe`（布林，預設 true）。關掉時跟 3.4.4 一樣。

**注意事項與預防問題**

- **誤殺風險最高的一包**：探測失效（網域下線、被所有人擋、被 ISP 擋）時如果照樣判，會把好的上游整批淘汰。所以自我檢查兩個條件都要過，而且「倖存的一般候選被這一段淘汰超過一半」時整段作廢（保險絲），寫 WARN、今天不採用探測結果。
- **不當攻擊者／隱私**：每台候選每天多 4 筆查詢，量很小。但查這類網域可能被上游或線路上的資安設備記成「這個 IP 有中毒的裝置」。要在 README 寫明，並提供開關。評測一律只做 DNS 查詢，不連線。
- 一般 DNS 被接走的線路：UDP 候選本來就不測，探測也不會送到攔截者；串接中的下游不自己評測。
- 文件、測試、日誌範例不寫實際的探測網域（測試用 `malware-test.example.com`）；`probe.txt` 本身是評測資料檔，跟 `web.txt` 一樣放真實網域。
- 上限：8 個網域；對象最多是倖存數＋64。
- 測試穩定性：假 prober 依（上游、網域）回固定答案，不連網。

**測試**

- `probe_valid_eliminates_malware_filtering_candidate_without_strike`（`blacklist-suspects.json` 與黑名單都沒有新增）。
- `probe_invalid_when_controls_do_not_block`、`probe_invalid_when_most_candidates_fail`。
- `probe_fuse_trips_when_half_would_be_eliminated`。
- `probe_never_calls_verify_site`（假 prober 的 `verify_site` 被呼叫就失敗）、`probe_not_in_universe`。
- `probe_disabled_matches_previous_behaviour`、`old_web_txt_untouched`。
- `control_expect_met_for_malware`（配合 A2）。
- 實測：老毛子直連，Quad9 類的對照組從 `passed` 變 `detected`；正常的 A 級沒有被誤殺。

**文件**：README（每日評測、隱私說明）、`protected.txt` 檔頭（3.5.0 起判得出惡意類）、`probe.txt` 檔頭寫格式與挑選標準、`fields.json`／LuCI 的開關。

### A6　記住不支援 HTTP/3 的 DoH

**目標**：`https://` 通過、`h3://` 連續幾天 QUIC 逾時的，跳過一段時間再試。**不做**：不改名單；QUIC 整條被擋（路徑檢查）時不記。

**現況**：`candidate_ids()` 對每一筆 `https://` 自動產生 `h3://`（約 350 個）。不支援 HTTP/3 的每天都在資格賽等到逾時（`benchmark.timeoutMs` 1.5 秒，含重試）。

**設計**

- `benchmark-learn.json` 的 `h3skip`：`{ f: 連續失敗天數, n: 已經跳過幾輪, until: 跳到哪一天 }`。
- 記一次失敗的條件（都要成立）：同一次評測裡它的 `https://` 通過資格賽；`h3://` 資格賽是連線錯誤（`Outcome::Error`，不是阻擋、不是答案不對）；路徑檢查沒有判斷 QUIC 被擋（`path_skip()` 沒有略過它）。
- 連續 3 天 → 跳過 `7 × 2^n` 天（7、14、28，上限 30）再加 0～3 天亂數（用 id 雜湊＋日數，不用另外的亂數來源，測試才穩）；`n` 最多 2。跳過期間不產生這個 `h3://` 候選（`judge.log` 記總數）。到期再測：成功就整筆刪掉，失敗（1 次就算）進下一輪。
- 上限 512 筆；`https://` 那一筆已經不在名單時刪掉。

**注意事項與預防問題**

- 會自己恢復：上限 30 天一定再試；伺服器之後支援 HTTP/3 就回來。
- 不冤枉：`https://` 自己也失敗時不記（那是伺服器或線路的問題）；QUIC 被擋的線路整批不記，路恢復後不用等 30 天。
- 省下的是每天約幾百次 QUIC 逾時，對評測時間有感（尤其 MT7621）。

**實作備註（3.5.0）**：`h3skip` 每筆多存 `last`（最後記錄的日數）：同一天評測好幾次只算一天、超過上限時先丟最舊的。另外加一條保險：當天沒有任何一個 `h3://` 連得上（路徑檢查沒抓到的 QUIC 整條被擋）時也不記。測試在 `learn.rs` 的單元測試與 `tests/benchmark_h3.rs`。

**測試**：`h3_skip_after_three_days_only_when_https_ok`、`h3_skip_not_recorded_when_quic_path_blocked`、`h3_skip_backoff_7_14_28_capped_30_with_jitter`、`h3_success_clears`、`h3skip_capped_512`。

**文件**：README 每日評測段一句話；`dohlist.txt` 檔頭補「連續不支援 HTTP/3 的會隔一段時間才再測」。

### A7　一直沒成功的自動上游

**目標**：自動上游裡「上線以來從未成功」的，不要一直 1→2→4→8 分鐘地暫停、接回；降級，並在下一次評測前換掉。**不做**：不動固定上游（使用者指定的）；不因為一台失敗就重跑整個評測。

**現況**

- `upstreams.rs` 的 `Up::record_inner()`：`Role::Auto` 連續失敗 5 次就暫停 `min(30, 2^(trips-1))` 分鐘，`ok == 0` 時日誌加「（上線以來從未成功）」。暫停結束就回到 `select()` 的名單，再失敗 5 次（每次都讓 5 筆查詢多等到逾時），如此循環，最長 30 分鐘一輪。
- `Manager::reload_auto()` 從 `upstreams.json` 的 `selected` 取前 `upstream.autoMax`（預設 5）個；沒有候補。
- 為什麼評測選上的會從未成功：很可能是 **種子資料**（A8：`data/seed/upstreams.json` 是別條線路上的評測結果），或評測時用的位址／協定跟執行時不同。A8 治本，A7 處理剩下的情況。

**設計**

- `Stats` 加 `benched: bool`（在既有的 `Mutex<Stats>` 裡，不是原子）。`record_inner()`：`Role::Auto`、`ok == 0`、第 3 次暫停（合計已經失敗 15 筆、過了至少 7 分鐘）→ `benched = true`、`open_until = now + 6 小時`，WARN 一次（「上線以來從未成功，先不用，下一次評測再決定」）。之後每 6 小時只放 1 筆試探（成功就解除 `benched`、照常使用）。
- **候補**：評測在 `upstreams.json` 多寫 `spares`（沒選上、但合格的前 3 個，依速度；格式同 `selected[]`）。`reload_auto()` 把它們建成 `Up`（`Role::Auto`）放在 `Auto.spares`。`select()` 裡，可用的自動上游（沒暫停、沒 `benched`、沒被路徑擋）少於 `min(autoMax, benchmark.minAuto)` 時，依序補上候補。舊的 `upstreams.json`（沒有 `spares`）就是沒有候補，行為同 3.4.4。
- **回饋給評測**：主程式把 `benched` 的 id 登記到 `neverOk`（0.3，上限 32）；下一次評測讀到時，這台今天照測，但選擇時排除（`judge.log`：「執行時上線以來從未成功，今天不選」），連續 3 次評測都被排除後忘掉重來（它可能修好了）。
- **提早評測**：自動上游可用的少於 `minAuto` 而且沒有候補可補時，用 `Scheduler::request_with_gap("dns-benchmark", "自動上游不足", 720.0)` 排一次（12 小時內跑過就不排）。串接中由上游提供評測結果時不排。
- `/api/upstreams` 的每台加 `benched`；`Manager::auto_info()` 加 `spares`。

**注意事項與預防問題**

- **查詢路徑**：`select()` 每筆查詢都會走到。候補只在「可用的不夠」時才讀，判斷用已經算好的 `Vec` 長度，不加鎖；`benched` 跟 `open_until` 在同一把既有的鎖裡一起讀（`paused()` 改成回傳兩個狀態，一次上鎖）。
- 不形成風暴：提早評測有 12 小時的間隔；試探 6 小時 1 筆。
- 不冤枉：只有「從未成功」才 `benched`。成功過的照舊走 1→2→4 分鐘（那是時好時壞，3.4.2 已經處理）。整台機器斷網時所有上游都會失敗——用「同一段時間內其他自動上游有成功」當條件（`Manager` 記最近一次任何自動上游成功的時間，用 `AtomicU32` 存相對秒數），沒有任何上游成功時不 `benched`。
- 串接：下游的自動上游平常不問（只在繞過與備援時用），累積不到 15 筆失敗就不會 `benched`，沒問題。
- 相容：上游給下游的 `upstreams.json` 多了 `spares`，舊版下游忽略；`usable_auto()` 不變。

**測試**（`upstreams.rs` 單元測試）

- `never_ok_auto_is_benched_after_three_trips`、`benched_probe_every_six_hours_and_recovers`。
- `not_benched_when_no_upstream_succeeds`（全部都失敗＝斷網）。
- `spares_fill_when_usable_below_min`、`old_state_without_spares_unchanged`。
- `flapping_auto_upstream_backs_off`（既有）繼續過。
- 評測端：`never_ok_excluded_from_selection_for_three_runs`。
- 實測：Windows 與 D3 上原本那一台不再反覆出現在 WARN 日誌。

**文件**：README 的上游段、`docs/integration.md`（`/api/upstreams` 的 `benched`、`upstreams.json` 的 `spares`）。

**目標**：全新的 state 第一次啟動時，初始上游用預設名單的 A 級，不用很差的種子評測結果。**不做**：不動 CDN 的種子（節點池、IPv6 節點、網域紀錄）。

**現況**

### A9　手動觸發的工作優先

**目標**：手動觸發（管理介面、指令列）的工作不要排在補跑的長工作後面。**不做**：不同時跑兩個工作（排程器一次一個是為了小機器，不改）。

**現況**

- `scheduler.rs`：`St.queue: VecDeque<(String, String)>` 先進先出，`request_with_gap()` 一律 `push_back`；`try_start_next()` 一次只跑一個。

**設計**

1. `Scheduler::request_priority(name, reason)`：`push_front`（已經在佇列裡的移到最前面）。`admin.rs` 的 `/api/jobs/run` 與指令列的手動執行改用它。排程、補跑照舊 `push_back`。
2. **補跑的順序**：`catch_up_plan()` 的結果裡，`dns-benchmark` 需要補跑而且自動上游目前來自預設名單或種子（`upstreams.json` 沒有 `generatedAt`）時，把它排到 `cdn-scan` 前面（初始上游的品質影響每一筆查詢，網段掃描晚 10 分鐘沒差）。實作：`catch_up_plan()` 多一個排序鍵，不改 `startDelaySec` 的預設值。

- 不形成迴圈：讓出有次數上限；續跑會跳過做過的，不重複掃同一批網段（原則 2）。

## 3. B 組：CDN 台灣節點

CDN 的程式在 `crates/kuroshio-cdn/`：`optimizer.rs`（每筆回應的 `Cdn::apply()` → `apply_locked()`：辨識 CDN、`db.touch()`、決定改寫、排背景工作）、`verifier.rs`（驗證）、`cross.rs`（跨 CDN 探索 `cross_explore()`）、`pools.rs`（節點池與評分 `qscore_of()`）、`health.rs`（定時健檢、`map_paced()`）、`jobs/`（`ranges`、`scan`、`pool` 三個工作）、`db.rs`（網域資料庫 `Db`、分片）。

`apply()` 是每筆 CDN 回應都會走到的路徑（先用唯讀的分類器快照判斷是不是 CDN，是才拿狀態鎖）。**B 組所有的新判斷都不能在「不是 CDN」的那條路上加東西，是 CDN 的那條路上也不能加配置以外的鎖。**

### B1　節點測速改相對評分

**目標**：節點的「慢不慢」跟同一家其他節點比，不再用絕對的 1 MB/s；「幾乎一樣」的誤差範圍依實際傳輸時間決定。**不做**：不增加測速的節點數與流量（3.4.2 才把一次節點池工作從約 960 MB 降到約 340 MB）；不改延遲、丟包的量法。

**現況**

- `jobs/pool.rs` 的階段 C：對前 `speed_top`（小機器 `LITE_SPEED_TOP = 4`）個節點呼叫 `Net::download_speed(ip, url, max_ms, max_bytes) -> f64`（MB/s，最多收 `SPEED_MAX_BYTES` = 8 MiB）。先完整測 `SPEED_PROBE = 4` 個，`same_speed()` 判斷「都在 1 MB/s 以上、最快與最慢差 5% 以內」就當成量到瓶頸，其餘只收 `SPEED_QUICK_BYTES` = 1 MiB 確認 `>= 1.0`。
- 排序：丟包 → 速度（大的在前，直接比數字）→ 延遲。`pools.rs` 的 `qscore_of()`：測過速度且低於 1 MB/s 加 80 分懲罰。`build_nearest()`（Fastly）也用同一套。
- 問題：
  - 快的線路上 8 MiB 不到 0.2 秒就收完，量到的速度雜訊很大（Windows 實測 Cloudflare 各節點差 27%），5% 門檻不成立，瓶頸減量不啟動，每個節點都收滿 8 MiB。
  - 慢的線路（例如 2 Mbps）上每個節點都低於 1 MB/s，全部被加 80 分，等於沒有區別；確認「不慢」的 `>= 1.0` 也永遠不成立。
  - 速度直接比大小：61.2 與 60.8 MB/s 只是雜訊，卻排在延遲之前決定名次。

**設計**（細部與常數由 Fable 定；下面是結構與方向）

- `Net` 多一個方法 `download_sample(ip, url, max_ms, max_bytes) -> SpeedSample { mbps: f64, bytes: u64, secs: f64 }`（`kuroshio-net/src/probe.rs` 的 `download_speed()` 內部本來就有位元組數與時間，改成回結構；舊的 `download_speed()` 留著包一層，2.x 對照測試不用動）。`SpeedSample` 同時是 B2、B4 的量測基礎。
- **誤差範圍** `tolerance(secs) -> f64`（純函式）：傳輸時間越短範圍越大。建議形狀 `clamp(0.06 + 0.10 / sqrt(secs), 0.08, 0.35)`：0.13 秒 → 約 0.34、1.5 秒 → 約 0.14、5 秒 → 約 0.10。實際係數用 Windows 與 D3 的測速紀錄回歸出來（第 6 節要收的資料）。
- **瓶頸判斷** `same_speed()` 改成：前 4 個量到速度的節點，最快與最慢的差在「這 4 個裡最大的誤差範圍」以內 → 量到瓶頸，其餘只做快測。Cloudflare 差 27%（傳輸 0.13 秒）會落在範圍內，減量會啟動。
- **相對的慢**：每一家算一個參考速度 `ref`（量到速度的節點的中位數；不到 3 個時不判斷慢）。節點「慢」＝速度低於 `ref × 0.5`，或低於絕對下限 0.1 MB/s（真的壞掉的）。`qscore_of()` 的簽章不動（2.x 對照），把「慢」改成由呼叫端算好傳進去的旗標：新增 `qscore_rel(ms, jitter, loss, slow: bool)`，`qscore()`／`weighted_qscore()` 改用節點上存的旗標。
- **排序**：速度先分級再比——跟這一家最快的差在誤差範圍內的算同一級，同一級之間由延遲決定。快測確認的節點算「跟瓶頸同一級」。
- 快測的門檻改成相對：收 1 MiB 的速度不低於 `ref × 0.5`（快測傳輸時間短，用它自己的誤差範圍放寬）。
- 儲存：`PoolNode.speed`（MB/s）照舊；慢的旗標與參考速度放在 `ProvEntry` 的 `rest`（`speedRef`）與 `PoolNode.extra`（`slow`），舊版讀到不認識的欄位會原樣保留（`extra` 就是為了這個）。讀舊的 `pools.json`（沒有 `speedRef`）：沿用舊規則（低於 1 MB/s 算慢）直到下一次節點池工作。

**注意事項與預防問題**

- **這一包會改變所有人的節點排序**，風險中高。要先做「離線重播」：把實測的 `pools.json` 與節點池日誌（Windows、D3 各幾份）餵給新舊兩套排序，比較選出來的節點差多少，再合併。
- 相對評分的陷阱：整家都慢（線路塞車那一刻）時，相對的「慢」一個都不會標，這是對的（不是節點的問題）；但參考速度不能跨工作沿用太久——每次節點池工作重算。
- 從上游或好友匯入的節點池：速度是別人線路量的，`slow` 旗標跟著那一份的 `speedRef` 算（同一份資料內相對比較仍然成立）；沒有 `speedRef` 的照舊規則。自己量過之後以自己的為準（原則 4）。
- 流量不能增加：新的量法每個節點最多還是一次 `download_sample()`；瓶頸減量啟動的機會變多，流量只會少。
- 小機器：`cdn.lite` 只測 4 個節點，剛好等於 `SPEED_PROBE`，瓶頸判斷之後沒有「其餘節點」，行為不變。
- 效能：全部在背景工作裡，不碰查詢路徑；`slow` 是節點上的一個布林，`serve_ips()`／`map_ips()` 讀到的還是排好的結果。

**實作結果（3.5.0，跟上面規劃不同的地方）**

### B2　工作負載分數（3.5.0 只做規格與量測基礎）

**目標**（長期）：用「各類使用情境的預估完成時間」評節點，取代單一的延遲＋懲罰分數。**3.5.0 的範圍**：(1) 這一節的規格草案與參考工作負載的出處；(2) 量測基礎：`SpeedSample`（B1）加上握手時間與 TTFB，在既有的探測裡順便記下來、不多連線；(3) 把量到的值放進 `/api/cdn/pools` 供實測收集。**不做**：3.5.0 不用工作負載分數決定任何節點的排序。

**為什麼延後**：分數一上線就會改變所有節點的名次；權重（「慢了多有感」）目前沒有任何實測依據；而且 B1 才剛把速度的量法改掉，兩個同時上線分不出是誰造成的變化。先收一版資料。

**規格草案**

- 量測值（每個節點，全部有上限）：RTT（TCP 握手時間，既有的 `tcp_ping`／`quality`）、抖動、丟包（既有）、TLS 握手時間、TTFB（`https_probe` 目前只回整體的 `ProbeResult.ms`，要拆成連線／握手／第一個位元組三段）、吞吐（`SpeedSample`，最多 8 MiB）。
- 六類工作負載與估算（完成時間都是「估計值」，用來比較節點，不是保證）：

  | 類別 | 模型（草案） | 主要受什麼影響 |
  |---|---|---|
  | 瀏覽 | 數十個請求、合計約 2 MB、少數幾條連線：握手 ×(連線數) ＋ TTFB ×(來回輪數) ＋ 大小 ÷ 吞吐（慢啟動階段受 RTT 限制） | RTT、握手、TTFB |
  | 購物 | 瀏覽＋多個小的 API 來回 | RTT、TTFB、抖動 |
  | 社群 | 連續的小請求＋圖片／短片分段 | RTT、抖動、吞吐（中） |
  | 串流 | 啟動時間（握手＋TTFB＋第一個分段）＋吞吐能不能撐住位元率（撐不住就降畫質） | 吞吐（有門檻，超過就沒差）、丟包 |
  | 大檔 | 大小 ÷ 吞吐 | 吞吐、丟包 |
  | 通訊 | 訊息來回、通話的延遲與抖動 | RTT、抖動、丟包（最敏感） |

- 權重：`權重 = 本機查詢統計裡這一類的占比 × 這一類「慢了多有感」的係數`，每一類設上下限（例如 5%～40%），避免單一類別主導或被歸零。本機查詢統計只用既有的 `stats.rs` 彙總（依 CDN 業者與站台分類的計數），不新增每筆查詢的紀錄。
- 「慢了多有感」：用門檻函式而不是線性——例如通話類延遲超過某個值才開始扣、串流類吞吐超過位元率就不再加分。

**參考工作負載的出處（要人工核對原文與數字後才寫進正式規格）**

- 網頁大小、請求數、連線數：HTTP Archive 的 Web Almanac（年度報告的 Page Weight、HTTP 章節）。
- 使用者感受的門檻：Web Vitals（LCP、INP 的「良好」門檻）。
- 通話的延遲門檻：ITU-T G.114（單向延遲的建議值）；多媒體應用的服務品質分類：ITU-T G.1010。
- 串流的品質模型：ITU-T P.1203 系列；各大串流服務公開的建議頻寬（當位元率門檻）。
- 吞吐的量測方法與 RTT／丟包對 TCP 吞吐的限制：RFC 6349（TCP 吞吐測試框架）、Mathis 等人的 TCP 吞吐公式。
- 以上只列方向；**這份文件沒有引用任何具體數字**，實作前由人逐一核對。

**注意事項**：量測基礎不能多連線、不能多收資料（握手與 TTFB 從既有的驗證與健檢探測裡拆出來）；新欄位放 `PoolNode.extra`，節點池每家最多幾十個節點，大小可以忽略；不碰查詢路徑。

### B3　尊重多來源 CDN、第一層 CNAME 變了就失效

**目標**：(1) 網站自己用 DNS 在多家 CDN 之間分流（GSLB）時，不把它硬綁在其中一家；(2) 網域的第一層 CNAME 換了，之前的驗證與替換結果失效、重新驗證；(3) App 自己決定用哪個 CDN 的服務（影音、系統更新這類）不介入。**不做**：不替網站選 CDN（那是網站的決定）；不為了多來源網域同時維護每一家的完整驗證紀錄（記憶體）。

**現況**

- `apply()` 用 `terminal_name()` 取 CNAME 鏈的**最後一個**名稱，`db.touch(name, provider, via, ips4, ips6, Some(cname))` 存在 `Domain.cname`。`touch()` 發現 `provider` 或 `cname` 變了只是更新欄位、標成重要變動，**不清掉** `v4`／`v6`（`Verdict`）、`cross4`、`ecs`、`best`。
- 所以：網站從 A 家換到 B 家之後，A 家時期的「跨 CDN 可用」（`best == Strategy::Cross`）還會繼續用到 `until`（3 天）；多來源的網域每次回答的業者不同，`provider` 欄位來回改寫、每次都標成重要變動（觸發分片寫入）。
- 最後一個名稱常常帶每次不同的標籤（節點、地區），拿來當「有沒有換」的依據會太敏感。

**設計**（防抖動的細部由 Fable 定）

- **第一層 CNAME 的鍵**：取回答裡查詢名稱的第一個 CNAME 目標，正規化成「可註冊網域＋往前一層」（`providers.rs` 已經有 `last2()` 的作法，沿用同一套規則），存在 `Domain.extra` 的 `c1`（字串，最長 64 位元組）。沒有 CNAME（直接 A 記錄）的是空字串。
- **失效**：`touch()` 發現 `c1` 變了，而且新的 `c1` 對應的業者（`provider_by_cname()`）跟原本不同 → 清掉 `v4`／`v6` 的 `until`（保留 `fails` 歷史）、`cross4`、`ecs`、`best`，回到試用期重新驗證。同一家業者內換 CNAME（同業者的不同產品線）只清 `cross4` 與 `ecs`。
- **多來源判斷**：`Domain.extra` 記 `provs`（最近看到的業者，最多 3 個，各帶最後看到的時間）。24 小時內看到 2 家以上 → `multi = true`。多來源網域的規則：
  - 驗證結果綁業者：`Verdict` 在 `extra` 記 `prov`。回答來自驗證過的那一家 → 照常改寫成那一家的台灣節點；來自另一家 → **回原始答案**（不改寫、不清掉既有結果）。
  - 另一家的驗證：每個網域每 6 小時最多排一次（避免兩家輪流時每次都重驗）。驗過之後兩家各自的結果怎麼存，由 Fable 評估（選項：只留最近驗過的一家；或 `extra` 裡留一份精簡的第二家結果）。
  - 不做跨 CDN 探索（網站已經自己在多家之間選了）。
  - `multi` 在 7 天沒有再看到第二家之後取消。
- **App 層**：`providers.rs` 的 `Provider` 加一個欄位 `app_layer: bool`（由 App 自己選節點的服務所用的業者／網域後綴）。標了的只做「辨識與統計」，不改寫、不 ECS、不跨 CDN。名單由人依實測整理（第 6 節），3.5.0 先放有把握的幾個；使用者可以用既有的 `/api/cdn/policy` 個別覆寫。
- `/api/cdn/domain` 多回 `c1`、`multi`、`provs`（給 B7 用）。

**注意事項與預防問題**

- **風暴**：失效＝重新驗證＝連到 CDN 節點。最怕的是多來源網域每次查詢都觸發失效。所以先判斷多來源、再決定要不要失效；每個網域的失效與第二家驗證都有時間間隔；`cdn.lite` 的每分鐘上限照舊蓋在最外面。
- **Flash**：現在多來源網域的 `provider` 來回改寫，每次都把分片標成 `Mark::Important`。改成綁業者之後，`provider` 欄位只在「主要業者」真的換了才改，寫入反而變少。這一點要有測試守著。
- **記憶體**：新欄位都在 `extra`，只有多來源與有 CNAME 的網域才有；`c1` 最長 64 位元組、`provs` 最多 3 個。`Domain::approx_bytes()` 要算進去（記憶體控制靠它估）。
- **查詢路徑**：`c1` 的正規化在 `apply()` 裡、拿狀態鎖之前做，只對已經判斷是 CDN 的回應做；用切片比對，不配置（跟既有的 `cname` 一樣只在變動時才 `to_string()`）。
- **相容**：舊的分片沒有 `c1`：第一次看到時補上、**不算變動**（不然升級後第一輪會把所有網域的結果清掉、全部重驗——這是最需要避免的事）。舊版讀到新欄位會原樣保留。
- 原則：回原始答案是安全的退路（原則 5）；不硬綁一家是尊重網站的決定，也避免把使用者導到網站已經不用的那一家。

**實作結果（3.5.0，跟上面規劃不同的地方）**

- **不清驗證結果，改成「兩格」**：規劃是「業者變了就清掉 `v4`／`v6`」加上多來源判斷。實作成每個網域最多兩格（目前這一家＋另一家），新的一家拿到空的一格（等於失效），舊的一家留在另一格。這樣「換家」與「輪流」走同一條路，不需要先猜是哪一種；兩家輪流只是對調，不可能形成失效風暴。清掉的只有不分業者的 `cross4`、`ecs`、`best`。
- **Q5 的結論**：保留第二家的驗證結果（理由見 06 第 3.9 節）。
- **多來源的定義**：不是「24 小時內看到 2 家」，而是「回到另一格、而且剛剛那一家 24 小時內才回答過」（看到輪流才算）。只看到換家的不標多來源，24 小時後另一格丟掉、可以做跨 CDN。
- **`c1` 的防抖動**：連續 3 次＋相隔 10 分鐘＋最近看過的鍵（最多 3 個、24 小時）不算新的；失效與開新的一格每個網域 6 小時一次。`c1` 是每一格各自的。空的 `c1`（回答沒有 CNAME）當成「沒有資訊」，不算變動。
- **欄位位置**：`c1` 與 `src` 是 `Domain` 上有型別的欄位（JSON 的鍵是 `c1`、`src`），不是放在 `extra` 的雜湊表裡——`extra` 一有東西就是一整個 `Map`，每個有 CNAME 的網域都要多幾百 bytes。`multi`、`provs` 是 API 回應時算出來的，不存。舊版讀到 `c1`／`src` 會當成不認識的欄位原樣保留。
- **「另一家的驗證每 6 小時最多排一次」**：實作成「開新的一格每 6 小時一次」；有格子的那一家照一般的到期時間複驗。
- **App 層**：3.5.0 標 `google`、`apple` 兩家；`cdn.appLayer` 可以整個關掉。
- **設定**：`cdn.multiCdn`、`cdn.appLayer`（都預設開）。
- **測試**：`crates/kuroshio-cdn/src/tests/multi.rs`。

### B4　跨 CDN 替換加實測評分

**目標**：跨 CDN 探索在原本的條件都通過之後，用實測分數挑比較快的那一家，並確認真的比原站快。**不做**：原本的條件一個都不放寬；每日複驗照舊；不增加探索的家數。

**現況**（`cross.rs` 的 `cross_explore()`）

- 原本的五個條件：① 目標節點用這個網域做 HTTPS 探測成功（憑證相符）；② 回應確實是那一家（`Provider::is_provider()`，Akamai 除外）；③ 不是錯誤頁（`cross_broken()`）；④ 跟原站是同一個網站（`same_site()`：狀態碼、內容類型、標題、轉址）；⑤ 比原站快 `cdn.nearestMinGainMs`（預設 8 ms）以上。
- ⑤ 用的是 `Net::quality()` 的 TCP 延遲（3 次連線）。TCP 延遲低不代表整個請求快（握手、TTFB 可能更慢）。通過的各家依 TCP 延遲排序取第一名。
- 結果存 `Cross`（`until` 3 天、`recheck_at` 依 `cdn.cross.recheckHours`）。

**設計**

- ①～④ 的 HTTPS 探測本來就做了，把它的分段時間（B2 的量測基礎：連線、握手、TTFB）留下來，不多連線。原站的基準探測（`base`）同樣有分段時間。
- **實測分數**：`score = 連線 + TLS 握手 + TTFB`（毫秒；每一家取通過的節點裡最好的）。只有一次樣本雜訊大，所以對「第一名」與「原站」各再做 1 次探測取較小值（最多多 2 條連線）。
- **判斷**：⑤ 改成兩個都要過——TCP 延遲快 `nearestMinGainMs` 以上（原條件不變），**而且**實測分數不比原站差（`score_new <= score_orig × 0.95`，常數由 Fable 依實測定）。排序改用實測分數，分數接近（10% 內）時用 TCP 延遲。
- `Cross` 與 `Tried` 的 `extra` 記 `score`、`origScore`；失敗原因多一種「連線比較近，但整個請求沒有比較快」。
- 每日複驗（`reverify_pick()`、`ok-recheck`）照舊，複驗時用同樣的分數判斷，但加遲滯：已經在用的跨 CDN 結果，要分數比原站差 10% 以上才撤掉（避免每天在邊界來回）。

**注意事項與預防問題**

- 條件只增不減：實測分數只會讓替換變少、變準，不會讓原本不能換的變成能換。
- 流量與連線：每次探索最多多 2 條連線；`cdn.cross.concurrency`（預設 2）照舊限制同時幾個探索。
- 不要用下載吞吐評跨 CDN（要抓大檔，對網站是負擔，原則 2）。
- 好友的跨 CDN 提示（`merge_cross_hint()`）不受影響：仍然只是候選順序。
- 測試穩定性：假的 `Net` 回固定的分段時間。

**測試**：`cross_prefers_lower_request_score_over_lower_tcp`、`cross_rejected_when_request_not_faster`（原因字串）、`cross_recheck_hysteresis`、`cross_extra_probes_capped_at_two`、既有的 `same_site_checks`、`broken_pages` 繼續過。

**文件**：`06-optimizations.md` 的跨 CDN 段、`docs/integration.md`（`/api/cdn/cross` 的新欄位）。

**實作結果（3.5.0，跟上面規劃不同的地方）**

- **先過 ⑤ 再比分數**：規劃是「排序改用實測分數」。實作成先留下 TCP 延遲也過關的幾家，再依分數挑。這樣才能保證「新規則採用的，舊規則一定也會採用某一家」（條件只增不減）；直接依分數排的話，分數第一名的那一家可能 TCP 不過關，反而讓原本換得成的變成換不成。
- **只有原本的條件都通過時才多探測**（最多 2 次：第一名與原站各一次）。TCP 不過關、或量不到分段時間時，探測次數跟 3.4.x 完全一樣。
- **量不到分數時照舊規則**：分段時間是 0（失敗的探測、假的網路）時不套用分數條件，不會因為量不到就全部不換。
- **遲滯只給正在用的那一家**：複驗時挑到的是別家，照新採用的標準（0.95）。
- 分數存在 `Cross.score`／`origScore` 與 `Tried.score`（有型別的欄位，不在 `extra`）；`/api/cdn/cross` 多 `scoreRejected`。
- 開關 `cdn.cross.requestScore`（預設開）。常數 `SCORE_RATIO` 0.95、`SCORE_KEEP_RATIO` 1.10、`SCORE_NEAR` 10%、`SCORE_EXTRA_PROBES` 2 在 `cross.rs`，等 W11 的資料再定（Q6）。
- 測試：`crates/kuroshio-cdn/src/tests/crossscore.rs`。

### B5　上游的台灣率評分

**目標**：評測時順便算每個上游「CDN 網域的答案本來就是台灣節點」的比例，記下它帶不帶 ECS；只影響排序。**不做**：不淘汰任何上游；不在執行時的查詢路徑上用它。

**現況**：評測的 `Srv.history` 記每個網域回的 IP；`Benchmark.tw`（`geo::TwIp`，`with_tw()`）在 Phase 2 用來判斷上游自己在不在台灣（`classify_region()`）。答案 IP 在不在台灣沒有人算。選擇的「覆蓋」階段（`select::select()`）依「新增覆蓋最多」貪婪挑，`near_first` 時先挑鄰近的。

**設計**

- Phase 2 之後、`compute()` 之前：對每個倖存者，數它的答案裡「在台灣網段的 IP」的網域數 ÷「至少有一個倖存者回過台灣 IP 的網域」數（分母排除在台灣根本沒有節點的網站）。存在 `Scored.ext` 的 `tw_rate`（`f32`，0～1；分母小於 10 時是 None）。
- `ecs`：先用 `Tag.ecs`（A1）；評測自己不另外探測。
- 排序：`select()` 的覆蓋階段，貪婪的每一步如果有兩個候選「新增覆蓋」差在 10% 以內，取 `tw_rate` 高的；差距更大時照舊。`near_first`、台數上限、覆蓋率目標都不變。備援（依速度補）不看。
- 輸出：`selected[]` 加 `twRate`、`ecs`；`final_csv()` 加一欄；`dashboard.js` 的上游表多一欄「台灣率」。

**注意事項與預防問題**

- 台灣率高不代表上游好（在台灣的上游自然高；會被竄改的上游也可能高）——所以只在覆蓋差不多時當決勝條件，而且排在所有淘汰檢查之後。
- `tw` 網段資料（`data/geo/tw-ip.json`、每月的 tw-ip 工作）讀不到時整個功能不啟用，行為同 3.4.4。
- 計算放在子程序的 Phase 2，網段比對是每個倖存者 × 每個答案 IP，數萬次以內；跟 `compute()` 一樣放 `spawn_blocking` 裡。
- 不把 hosts 類清單的 IP 當判斷依據：台灣網段來自 `TwIp`（RIR／路由資料）。
- 相容：新欄位，舊版忽略；`tests/parity` 的選擇對照要確認「差在 10% 以內」的決勝不會改到既有的對照案例（必要時對照測試固定 `tw_rate = None`）。

**測試**：`tw_rate_denominator_excludes_sites_without_tw_nodes`、`tw_rate_none_when_few_domains`、`tie_break_prefers_higher_tw_rate_only_within_ten_percent`、`no_tw_data_matches_previous_selection`。

**文件**：README 每日評測段、`10-chain.md` 第 6 節（上游多樣性）補一句。

**實作備註（3.5.0）**：`tw_rate` 放在 `Scored` 自己的欄位（不放 `Ext`：`extended_metrics()` 會整個重設 `ext`）；在 `compute()`（`spawn_blocking`）裡用 `select::tw_rates()` 算。決勝：差在 10% 以內（新增 ≥ 最多的 × 0.9）的候選裡台灣率最高的比原本選到的高，才在那幾台裡照原本的規則（新增多、再快）挑；台灣率全部是 None 或一樣時跟原本逐項相同（`no_tw_data_matches_previous_selection` 用 300 組亂數輸入對照 3.3.7 的 `select()`）。報表的 `greedy_csv` 不看台灣率。`judge.log` 寫分母。

### B6　通訊類保護（3.5.0：框架＋APNs／FCM；其他交接實測）

**目標**：推播與通訊服務的網域不被誤擋、預取與 serve-stale 優先、記憶體吃緊也不掉、不因為小差異換閘道節點。**3.5.0 的範圍**：框架、APNs 與 FCM 兩組（有官方文件寫明的主機名稱）、狀態顯示、給實測的交接清單。**不做**：LINE／WhatsApp／其他推播網域的規則等台灣實測（第 6 節）之後在 3.5.x 加；不做使用者看不到、關不掉的白名單。

**現況**

- 過濾：`filtering.rs` 的清單規則與自訂規則，沒有「內建不誤擋」的概念。
- 快取：`resolver.rs` 的預取（`prefetch()`、`resolver.prefetchRecentSec` 600 秒內問過的才預取）、`serve_stale`（`resolver.serveStaleSec`）。
- 記憶體：`memgov.rs` 的 `CacheStep`／`FloorStep`，最低限度時快取只留 `FLOOR_CACHE = 64` 筆（留哪些沒有特別規則）。
- CDN：`health.rs` 的 `keep_pop()` 有遲滯（`POP_HYST_RATIO` 15%、`POP_HYST_ABS` 5 分），對所有網域一樣。

**設計**

- 新檔 `crates/kuroshio/src/comm.rs`：編譯進去的後綴表 `COMM_SUFFIXES: &[(&str, CommKind)]`（最多 64 筆；3.5.0 只有 APNs、FCM 兩組），`pub fn is_comm(name: &str) -> bool`（後綴比對，不配置）。使用者可以用 `resolver.keepNames`（字串陣列，最多 64 個後綴）自己加。
- 四個保護：
  1. **不誤擋**：清單規則擋到通訊類網域時不擋（`/api/filter/check` 顯示 `rule: "builtin-comm"`），**自訂規則照樣優先**（使用者明確要擋就擋，原則 3）。開關 `filter.protectComm`（預設 true）。每天第一次發生時記一行 INFO（哪份清單、哪個網域），方便回報給清單維護者。
  2. **預取與 serve-stale**：通訊類不受「最近 600 秒問過」的限制，快到期就預取（上限：同時最多 16 個通訊類名稱在預取名單裡）；上游都失敗時的 `staleIfErrorSec` 照既有設定，不另外加長。
  3. **記憶體**：`FloorStep` 縮到 64 筆時，通訊類的項目優先留下；`CacheStep` 的淘汰略過它們（數量有上限，影響可以忽略）。
  4. **CDN**：通訊類網域不做跨 CDN 探索；改寫照常，但節點池主要節點的遲滯對它們加倍（不因為幾毫秒的差異換節點，長連線重連的代價高）。
- 狀態：`/api/status` 的 `resolver.comm`：`{ "names": N, "protectedFromLists": N, "prefetching": N }`。

**注意事項與預防問題**

- **查詢路徑**：`is_comm()` 會在每筆查詢被呼叫嗎？不行。做法：只在三個已經是慢路徑的地方呼叫——過濾器「判定要擋」之後（多數查詢不會走到）、快取項目建立時（把結果存成項目上的一個布林）、記憶體控制淘汰時。比對本身是幾十個後綴的切片比較，不配置。
- 不誤擋是「替使用者做決定」嗎？推播收不到的後果（漏接通知）比多一個連線嚴重，而且有開關、自訂規則優先、狀態頁看得到，符合原則 3 的精神。文件要寫明。
- 上限：後綴表 64、使用者 64、同時預取 16。
- 串接：下游的過濾在問上游之前就先查；上游擋掉通訊類時，下游照既有規則用自己的加密上游解析（3.4.2），不用新機制。
- 交接：LINE、WhatsApp、其他推播服務的網域與閘道行為由台灣實測收集（哪些網域、TTL、IP 換得多頻繁、被哪些清單誤擋過），整理後 3.5.x 加進表裡。**文件與測試不寫實際網域**，測試用 `push.example.com`。

**測試**：`comm_not_blocked_by_list_but_blocked_by_custom_rule`、`protect_comm_off_restores_list_blocking`、`comm_prefetched_without_recent_hit_and_capped`、`floor_keeps_comm_entries_first`、`comm_never_cross_explored`、`keep_names_capped_at_64`。

**文件**：README（過濾、快取）、`09-memory.md`（最低限度留哪些）、LuCI／`fields.json` 的 `filter.protectComm` 與 `resolver.keepNames`、UCI 對應（`filter` 與 `resolver` 區段要確認是不是自動對應）。

### B7　「為什麼沒換到台灣」說明

**目標**：管理 API 與狀態頁可以查一個網域：哪家 CDN、換或不換的原因、驗證結果。**只讀**。

**現況**：`GET /api/cdn/domain?name=`（`admin.rs` → `Cdn::domain()`）回資料庫裡的原始紀錄；`/api/trace` 回實際解析的過程。原因散在 `Verdict.reason`、`Cross.reason`、`Ecs.reason`、政策、`cdn.lite` 的等待、串接狀態裡，要自己拼。

**設計**

- `Cdn::explain(name: &str) -> Value`（`cdn.rs`，純讀取）與 `GET /api/cdn/explain?name=example.com`：

  ```json
  { "name": "example.com", "known": true,
    "provider": "cloudflare", "providerLabel": "Cloudflare", "via": "cname",
    "cname": "example.com.cdn.example.net", "multi": false,
    "decision": "rewritten",
    "text": "這個網域用 Cloudflare，已經換成驗證過的台灣節點（TPE，12 ms）。",
    "steps": [
      { "what": "v4", "result": "ok", "pop": "TPE", "ms": 12, "at": "…", "until": "…" },
      { "what": "v6", "result": "fail", "reason": "…" },
      { "what": "cross", "result": "none" } ] }
  ```

- `decision` 的固定代碼（介面依代碼顯示文字，`text` 是核心給的白話）：`rewritten`、`already-tw`、`trial`（試用期、等驗證）、`lite-waiting`（小機器：問過 2 次才驗）、`verify-failed`、`no-tw-node`（這家沒有台灣節點而且跨 CDN 也沒有）、`cross`、`ecs`、`policy-never`、`multi-cdn`（B3）、`app-layer`（B3）、`comm`（B6）、`chained`（串接中由上游處理）、`cdn-disabled`、`memory-floor`（記憶體最低限度時暫停）、`not-cdn`、`unknown`（沒問過）。
- 冷資料（被記憶體控制移到磁碟的）：呼叫既有的 `ensure_loaded()` 讀回來再回答（這是管理 API，不是查詢路徑）。
- 不發任何網路請求；要重新驗證用既有的 `POST /api/cdn/verify`。
- 介面：`dashboard.js` 的 CDN 網域表每列加「為什麼」；LuCI `cdn.js` 與 Windows 設定頁加一個輸入框。`rpcd.sh` 的 `api` 白名單加 `/api/cdn/explain`（C13）。

**注意事項**：只讀、不改狀態（不能因為查了就 `touch()`、增加 `hits`）；回應裡沒有使用者的來源位址；`name` 用既有的 `normalize()`；`text` 的文字集中在一個函式，方便之後跟介面一起調。

**測試**：每個 `decision` 一個案例（`explain_*`）、`explain_does_not_touch_or_schedule`、`explain_loads_cold_entry`、`admin_security.rs` 確認它是 GET、不在 POST 清單。

**文件**：`docs/integration.md`（新 API 與代碼表）、README 的 CDN 段、LuCI 說明。

### B8　cdn-scan 的連線尖峰

**目標**：每週的網段掃描每秒新連線有上限、開始時間攤開。**不做**：不減少掃描的網段（那是節點池的基礎）。

**現況**

- `jobs/scan.rs` 的 `scan_batch()`：`workers` 個工作者（`scan.concurrency`，`PER_CORE` 每核心 50、32～400）各自迴圈 `http_probe()`（80 埠），沒有節流。節點很近時每個探測幾毫秒就回來，Windows 實測每秒 1,832～1,904 條新 TCP 連線。
- 3.4.2 已經替健檢與節點池加了 `health.rs` 的 `map_paced()`（`HEALTH_NODES_PER_SEC`、`LATENCY_IPS_PER_SEC`），掃描沒有。
- 預設排程 `jobs.cdn-scan`：每週日 03:20，沒有每台錯開；排程器已經有 `jitterMin`（`scheduler.rs` 的 `jitter_ms()`，種子存在 `jobs.json`，tw-ip 在用）。

**設計**

- `scan.rs` 加共用的節拍器 `Pacer`（做法同 `map_paced()` 裡的 `next`：一把背景工作用的 `Mutex<Instant>`，每次探測開始前登記「下一個可以開始的時間」，間隔 `1 / per_sec`；落後了不補）。每個 `http_probe()` 之前等它。
- 上限 `scan.maxPerSec`：預設 `"auto"` → 每核心 50、下限 50、上限 200（放進 `PER_CORE`）；`cdn.lite` 時再砍半。使用者可以填數字（1～1000）。
- 時間估算寫進工作開始的日誌：「約 N 個探測，每秒最多 M 個，預計至少 X 分鐘」。`timeoutMin` 240 分鐘夠用（要在實作時用實際的 /24 數量驗算，寫進測試的註解）。
- `defaults.json` 的 `jobs.cdn-scan` 加 `"jitterMin": 30`：每台往後錯開 0～30 分鐘，大家不在同一秒開始打同一家 CDN（原則 2）。
- 逾時的探測佔著工作者時不會讓後面的一起爆發（節拍器是「拿到才登記」，跟 3.4.2 修過的 `map_paced()` 同一個教訓）。

**注意事項與預防問題**

- 掃描變慢是預期的，要確認不會壓到同一晚的其他工作（cdn-pool 05:30、dns-benchmark 04:10 排在後面等；A9 的讓出機制也有幫助）。
- `jitterMin` 第一次會在 `jobs.json` 產生這個工作的種子：舊的 `jobs.json` 沒有種子時 `tick()` 會自動補，不用遷移。
- UCI：`scan` 區段自動對應（`max_per_sec` → `maxPerSec`）。
- 測試不要用真的時間：`tokio::time::pause()`＋假的 `Net`，數每一秒開始了幾個探測。

**測試**：`scan_paced_never_exceeds_per_sec`（暫停時鐘，每秒起始數 ≤ 上限）、`scan_no_burst_after_stall`（前面的探測卡 10 秒後，下一秒仍然 ≤ 上限）、`scan_max_per_sec_auto_table`（核心數換算）、`cdn_scan_default_has_jitter`。實測：Windows 用同樣的方法量每秒新連線。

## 4. C 組：系統、串接、記憶體、儲存

### C1　Windows 主控台關閉／登出／關機時正常停止

**目標**：以主控台（cmd）方式執行時，按視窗的關閉鈕、登出、關機都走正常停止（寫快照、寫日誌）。**不做**：服務模式（`winsvc.rs` 已經處理 `ServiceControl::Stop | Shutdown`）不改流程。

**現況**：`main.rs` 的 `shutdown_signal()` 在非 Unix 只等 `tokio::signal::ctrl_c()`。關閉視窗（`CTRL_CLOSE_EVENT`）、登出（`CTRL_LOGOFF_EVENT`）、關機（`CTRL_SHUTDOWN_EVENT`）、Ctrl+Break 都沒有處理，行程直接被系統結束，`AppRun::shutdown()`（`app.rs`：`stage_hot_names()`、`stage_sources()`、`Persister::flush_for_shutdown()`）沒有跑，也沒有日誌。

**設計**

- `shutdown_signal()` 的 Windows 分支：`tokio::signal::windows` 的 `ctrl_c()`、`ctrl_break()`、`ctrl_close()`、`ctrl_logoff()`、`ctrl_shutdown()` 一起 `select!`，回傳是哪一種（新的 `enum StopReason`）。任何一種都走同一個正常停止，日誌寫「收到主控台關閉／登出／關機，正常停止」。
- **時間限制**：Windows 對主控台程式的這三種事件，在處理函式回傳後或大約 5 秒後就強制結束行程。`persist.rs` 的 `SHUTDOWN_BUDGET` 是 10 秒，太長。`flush_for_shutdown()` 加一個參數（預算），這三種事件時用 3 秒；Ctrl+C 與服務停止照舊 10 秒。
- **要先確認的事（實作第一步）**：目前鎖定的 tokio（`Cargo.lock` 是 1.54.x）在收到這三種事件時，處理函式會不會擋住等程式自己結束。如果它立刻回傳，系統會馬上結束行程，3 秒的預算也用不到——那就要改用 `windows-sys` 自己註冊 `SetConsoleCtrlHandler`，在處理函式裡通知主迴圈並等「停止完成」的訊號（最多 4 秒）再回傳。兩種做法擇一，以實測為準。
- 檔案日誌（`log.fileLog`）在結束前要沖出去。

**注意事項與預防問題**

- 3 秒內寫不完的快照：既有的規則是小檔先寫、寫不完的下次啟動用上一次存的；配合 C5（關機時不寫只有計數變動的分片）後要寫的量會少很多。
- 只有 Windows 的程式路徑：`#[cfg(windows)]`，Linux／MIPS 的建置與行為不能受影響；CI 的 Windows 建置要過 clippy。
- 這是結束時的路徑，跟查詢效能無關。
- 沒辦法在 CI 自動測「關閉視窗」，一定要 Windows 實測（第 6 節）。

**測試**：`flush_for_shutdown_respects_custom_budget`（`persist.rs`，注入假的寫入延遲）；`stop_reason_labels`（日誌文字）。實測：關閉視窗、登出、關機、Ctrl+Break、Ctrl+C 五種，各看日誌最後幾行與下次啟動有沒有讀到快照。

**文件**：`docs/windows.md`、`07-windows.md`。

### C2　串接：經攔截綁定後，拿到閘道就安全地換成直連

**目標**：下游先用「經攔截」（對保留位址的查詢被上游接走）綁定之後，如果後來知道了預設閘道、而且閘道就是同一台上游，改成直連閘道。**不做**：不改探測、驗證、心跳的協定；不新增開關。

**現況**（`chain/client.rs`）

- `Event::Verified { again, gateway }`：綁定的當下，閘道探測成功而且公鑰相同 → `Via::Gateway`；否則用命中的保留位址 → `Via::Intercept`，日誌有「（經攔截）」。
- 之後的 `Event::Report(v)`（路徑檢查的新結果）在 `State::Chained` 時回 `Vec::new()`：就算這次 `v.gateway` 有值了也不做事。常見情況是開機時路由表還沒好、第一次路徑檢查沒拿到閘道，之後就一直是經攔截。
- 經攔截的缺點（規格 10 的 1.6）：依賴上游的 DNAT 規則一直存在；TCP 不一定可用（`tcp_ok`）；狀態頁只能寫「閘道或更上游」。

**設計**（狀態機的細部由 Fable 定）

- 新的 IO `Io::ProbeGateway { addr }` 與事件 `Event::GatewayProbed(SocketAddr, Probe)`。
- 觸發：`State::Chained`、`bound.via == Via::Intercept`、`view.gateway` 有值而且不等於 `bound.addr`，在 (a) 新的 `Event::Report` 進來時，或 (b) 心跳成功時（但距離上次嘗試超過 10 分鐘）。
- `Event::GatewayProbed`：探測沒有錯誤、`public == bound.public`（同一把金鑰＝同一台上游）、鏈上沒有自己（`judge()` 照跑）→ 換綁：`bound.addr = 閘道`、`via = Via::Gateway`、`tcp_ok = true`，`since_ms` 不動，回 `Io::Bind { … }`（`Manager::set_chain()` 換上游位址）。**先驗證成功才換，中間沒有空窗**；任何一項不符就維持經攔截，什麼都不改。
- 防來回：
  - 換成直連之後，如果直連的心跳或查詢失敗走到解除（既有流程），重新探測時照既有規則（可能又綁成經攔截）。記下「這個閘道直連失敗過」，1 小時內不再嘗試升級；連續 3 次升級後又失敗 → 這次行程不再嘗試（直到 WAN 變動或重新啟動）。
  - 嘗試的頻率上限：10 分鐘一次，每次一筆探測查詢。
- 閘道不是那台上游（兩層 NAT、攔截者在更上游）：公鑰不同或沒有回應 → 維持經攔截，這本來就是對的。
- `/api/chain` 的 `via` 會從 `intercept` 變成 `gateway`；事件記錄加一筆「改成直連閘道」。

**注意事項與預防問題**

- **安全**：換綁前一定要用節點金鑰的簽章驗證（跟初次綁定同一個標準），而且公鑰要跟目前綁定的一樣。不能因為「閘道有回應」就換。`chainPin`（指紋鎖定）照舊檢查。
- **最壞情況**是維持現狀（經攔截）或退回單獨運作，符合原則 5。
- 換綁會讓 `Up`（串接上游）換成新的物件，連續失敗計數歸零——要確認不會因此繞過 `CHAIN_RELEASE_TRIPS` 的保護（建議沿用舊的 `Stats`，或把 `trips` 帶過去）。
- 共用結果的同步（`chain/share.rs`）是對綁定位址發查詢：換綁後下一次同步用新位址，`chain-share.json` 的雜湊紀錄不受影響（同一台上游）。
- 放行登記（`chain/grants.rs` 的 `reg`）：上游是依來源位址登記下游；下游換目的位址不影響來源位址，不用重新登記，但要有測試確認。
- 舊版上游（3.4.x）：探測與驗證的協定沒變，相容。
- 測試：`step()` 是純函式，全部可以用單元測試；時間用 `Now`。

**測試**（`client.rs` 單元測試＋`tests/chain_client.rs`）

- `intercept_bound_upgrades_to_gateway_when_gateway_appears`。
- `no_upgrade_when_gateway_key_differs`、`no_upgrade_when_gateway_silent`、`no_upgrade_when_pin_mismatch`。
- `upgrade_attempts_rate_limited`、`upgrade_blocked_for_an_hour_after_direct_failure`、`upgrade_gives_up_after_three_failed_cycles`。
- `upgrade_keeps_since_and_trip_count`。
- `chain_e2e.rs`：兩台本機實例，先不給閘道、再給，確認換綁後查詢與同步照常。
- 實測：D3 接在主路由器後面重新開機，看是不是幾分鐘內從「經攔截」變成直連。

**文件**：`10-chain.md` 第 1.4、1.6 節、`docs/integration.md` 的串接狀態。

**實作（3.5.0，定案在 [10-chain.md](10-chain.md) 第 1.6 節）跟上面規劃不同的地方**

- **「直連失敗」不分升級來的還是初次綁定的**：直連的綁定不到 1 小時就因為沒回應／驗證不過而解除，都記一次，接下來 1 小時驗證時不試閘道（綁回經攔截）、也不升級。只記升級來的話，解除後重新驗證會直接又綁成直連，繞過「1 小時內不再嘗試」。
- **連續 3 次之後不是「這次行程不再嘗試」，是 24 小時一次**：直連的路修好之後會自己恢復（原則 5），頻率仍然有上限。
- **探測沒過時間隔加倍**（10 分鐘 → 6 小時）：閘道不是黑潮（兩層 NAT）時不必每 10 分鐘問一次。心跳成功時的嘗試跟路徑檢查共用同一個間隔。
- **串接上游暫停中不探測、不換**（`GatewayProbeSkipped`，一分鐘後再看）；換位址時 `Manager::set_chain()` 把暫停次數與時間帶到新的上游物件。
- 多了 `no_upgrade_when_gateway_is_another_node`、`direct_failure_falls_back_to_intercept_without_flapping`（`tests/chain_client.rs`）、`stale_gateway_probe_is_ignored`、`heartbeat_triggers_upgrade_probe`、`rebinding_chain_keeps_trip_count`（`upstreams.rs`）。
- `chain_e2e.rs` 的兩台實例測試沒有做：閘道的覆寫（`KUROSHIO_PATH_TARGETS`）是行程啟動時讀的環境變數，沒辦法在執行中「先不給、再給」。改用 `tests/chain_client.rs`（真的 `Client`＋`Manager`＋本機假上游）驗證換綁後心跳、登記照常；共用結果的同步是對 `bound_addr()` 發，測試確認它換成閘道而且 TCP 可用。

### C3　記憶體不足時一次停用多份清單、只重建一次

**目標**：缺口大時一次決定要停用哪幾份清單、重建一次；恢復時也一樣。**不做**：不改停用的順序（`shed_order()`）、不動保護清單的規則。

**現況**

- `memgov.rs` 的 `Governor::tick()`：`Plan::Shed { far, deficit }` 時最多跑 16 步，`far`（離保留量很遠）時連續做到 `freed >= deficit`。`FilterStep::shed()` 每次呼叫 `FilterService::unload_one()`：停用一份、`rebuild_mode(Source::PreferCopy, …)` 重建整個過濾器。缺口大時連續停用 N 份就重建 N 次，每次重建新舊兩份同時在記憶體裡，CPU 與記憶體的尖峰都在最缺的時候發生。
- 恢復：`Plan::Restore(k)` 一次 `restore_one()`，每份重建一次（3.4.2 Windows 實測恢復 7 份清單重建 7 次）。

**設計**

- `FilterService::unload_many(target_bytes: u64) -> Result<Vec<Unloaded>>`：依 `shed_candidates()` 的順序累加 `sizes`，取到合計 ≥ `target_bytes` 為止（至少 1 份，保護清單不在候選裡），一次全部登記到 `unloaded`、重建一次。失敗時把這次登記的全部撤回（同 `unload_one()` 的錯誤處理）。
- `FilterStep::shed()`：`far` 而且有缺口時呼叫 `unload_many(deficit × 1.3 − 這一輪前面步驟已經釋出的)`；否則照舊一份。`Step::shed()` 的簽章要多帶「還缺多少」（`Outcome` 不變）；`tick()` 把 `deficit - freed` 傳下去。回報的 `detail` 列出幾份與名稱（最多列 5 個）。
- 重建前的安全檢查照舊：新的一份放不進可用記憶體的一半就不做——改成用「停用這幾份之後的大小」算，一次停用多份反而更容易通過。
- `FilterService::restore_many(room: u64)`：從最後停用的開始，取到合計 × 1.3 ≤ `room` 為止（至少 1 份——跟現在的條件相同），重建一次。`FilterStep::restore()` 用 `restore_room()` 算出的空間呼叫它。恢復之後的等待（`next_restore_at`、`flap` 退避）不變。
- `unload_one()`／`restore_one()` 留著給測試與手動路徑，內部改成呼叫多份的版本。

**注意事項與預防問題**

- **不要過頭**：一次停用太多會讓防護掉得比需要的多。目標量用缺口的 1.3 倍，而且扣掉同一輪前面步驟（快取、CDN 冷資料）已經釋出的。
- **不反覆**：恢復一次多份後如果又不足，會再停用——既有的 `flap` 退避（恢復後 10 分鐘內又吃緊就把恢復間隔加倍）要照樣生效，測試要涵蓋「恢復多份 → 立刻又不足」。
- 重建期間舊的過濾器照常服務，查詢路徑不受影響；`rebuild_lock` 保證同時只有一個重建。
- 沒有本機副本的清單在恢復時要下載：一次恢復多份＝一次下載多份，但 3.4.2 的「留在記憶體的副本」機制讓每份最多下載一次，照舊。
- 估計值（`sizes`）不準時：實際釋出不到目標，下一輪 `tick()` 會再做一次，最多多重建一次，可以接受。

**測試**（`memgov.rs`、`filtering.rs`）

- `far_deficit_unloads_several_lists_with_one_rebuild`（假的清單來源，數 `rebuild_mode` 被呼叫幾次）。
- `near_deficit_still_unloads_one`。
- `unload_many_never_includes_protected`、`unload_many_rolls_back_on_failure`。
- `restore_many_fits_room_and_rebuilds_once`、`restore_then_pressure_again_backs_off`。
- 既有的 `far_below_reserve_escalates_several_steps_in_one_tick`、`shed_order_never_includes_protected` 繼續過。
- 實測：配合 C9 的測試開關，在 512 MB 的 D3 與 Windows 上觸發「不足」，看日誌是「一次停用 N 份、重建 1 次」。

**文件**：`09-memory.md`（第 4 步的描述）、README 的記憶體段。

### C4　查詢紀錄 API

**目標**：管理介面可以看最近的查詢（網域、類型、來源、結果、延遲、答案來源），用來除錯。只在管理 API、只在記憶體、有上限（筆數、位元組、時間）。**不做**：不寫到磁碟、不進備份、不給公開頁、不傳給上游／下游／好友。

**現況**：`defaults.json` 有 `log.queryLog`（預設 false）與 `system.queryLogRing`（20,000），但 3.x 的 Rust 核心裡**沒有任何程式用它們**（只有設定測試與 `compare.rs` 讀 2.x 的紀錄檔格式）。`stats.rs` 只有彙總統計。`logring.rs` 是日誌行的環狀緩衝（`/api/log`）。

**設計**

- 新檔 `crates/kuroshio/src/querylog.rs`：
  - 固定大小、預先配置的環狀緩衝：每筆一個固定長度的結構（時間 `u32` 秒、類型 `u16`、回應碼與結果旗標、延遲 `u16` 毫秒、來源位址 16 位元組、答案來源代碼 `u8`、網域 `[u8; 80]` 加長度，超過截斷）——每筆約 112 位元組，**寫入時不配置**。
  - 筆數上限：`system.queryLogRing`（沿用既有設定，預設 20,000 ≈ 2.2 MB）；`"auto"` 式的收緊在 `app.rs`：實體記憶體小於 160 MB → 最多 1,000 筆（約 110 KB）、小於 512 MB → 5,000 筆。位元組上限就是筆數 × 固定大小。
  - **預設關閉**。關閉時查詢路徑只多一次 `AtomicBool` 的讀取（`Relaxed`）。
  - 開啟方式：(a) `log.queryLog: true`（常開）；(b) `POST /api/querylog/enable?minutes=N`（1～60，預設 10）暫時開啟，到時間自動關閉並釋放緩衝。時間上限用 `AtomicU32` 存「到期的相對秒數」。
  - 寫入：`Mutex` 用 `try_lock()`；拿不到鎖就丟掉這一筆並累加 `dropped`（`AtomicU32`）——**查詢絕不等這把鎖**。
  - 讀取：`GET /api/querylog?limit=200&name=&client=&since=`（`limit` 最多 1,000；回應大小因此有上限），回 `{ enabled, until, size, dropped, entries: [...] }`。讀的時候拿鎖、複製需要的那幾筆就放掉。

- 記憶體控制：`DiagStep`（「縮小診斷緩衝」）釋放查詢紀錄的緩衝並關閉暫時開啟；恢復時不自動再開（暫時開啟的要使用者重新按）。

### C5　小 Flash：CDN 網域資料與清單副本的取捨、關機寫得完

**目標**：狀態分割區很小（D3 是 7.5 MB）時，CDN 網域資料不無限長大、也不丟掉值得留的驗證結果；關機 10 秒內寫得完。**不做**：不把 CDN 網域資料降成「可重建」任由空間管理刪除（重新驗證每個網域約 90 KB 流量，還有對 CDN 的連線）。

**現況**

- `space.rs` 的 `tier_of()`：`cdn/domains/*`（最多 `MAX_SHARDS` = 256 個分片）是 `Core`，絕不自動刪；`filter-lists/*` 是 `Optional`，空間不夠最先被擠掉（`Persister::has_room_for_optional()`、`make_room_below()`）。
- CDN 網域資料只有筆數上限 `cdn.maxEntries`（預設 200,000；壓縮後每筆約 `COMPRESSED_BYTES_PER_ENTRY` = 115 位元組 → 上限約 23 MB，遠大於 7.5 MB 的分割區）。`Db::prune()` 超過上限才刪最久沒出現的。
- 實測：D3 解除串接期間自己做 CDN 驗證，網域資料長大，擠掉一份過濾清單副本（之後每次重啟多下載約 2 MB）。
- 關機：`AppRun::shutdown()` → `flush_for_shutdown()`（`force = true`）把所有待寫的都寫，包括只有計數變動（`Opts.lazy`，`cdn_source()` 依 `Mark::Counters` 標的）的分片；`SHUTDOWN_BUDGET` 10 秒內 94 份寫不完，剩下的放棄。寫的順序是（有沒有相依、大小、名稱），沒有分重要性。

**設計**（由 Fable 定案；下面是建議的方向與初值）

1. **磁碟預算**：新設定 `cdn.dbDiskBudgetKB`（`"auto"` 或數字）。`auto`：狀態目錄所在的檔案系統總容量（`space::total_bytes()`）小於 64 MB 時，預算＝總容量的 30%（7.5 MB → 約 2.2 MB ≈ 19,000 筆）；大於等於 64 MB 時不限（只受 `maxEntries`）。換算在 `app.rs`，傳給 `Cdn`。
2. **依價值淘汰**（新的 `Db::prune_to_budget(max_entries_by_budget)`，只在背景的快照登記時呼叫，不在 `touch()` 裡）：估計大小（筆數 × 115）超過預算時刪到預算的 90%。刪除順序：
   1. 只問過 1 次、沒有任何成功的驗證結果的（一次性的網域）。
   2. 驗證失敗、而且超過 7 天沒再出現的。
   3. 其餘依 `last_seen` 最舊的。
   - 永遠不刪：手動設定過政策的（同既有的 `drop_oldest()`）；30 天內出現過而且有成功驗證結果的排在最後。
   - 為什麼這樣排：一筆 115 位元組的成功驗證紀錄，省下的是下次約 90 KB 的重新驗證；一份清單副本約 0.3～1 MB，省下的是重啟時一次約 2 MB 的下載。所以「有成功結果、最近用過」的網域每個位元組最值錢，「一次性、失敗」的最不值錢——先丟後者，把空間讓給清單副本。
3. **分片數不跟著預算變**：`shards_for(max_entries)` 照舊（改分片數會重寫所有分片，在小 Flash 上是大量寫入）。預算只控制筆數。
4. **關機寫入**：`flush_inner()` 的 `shutdown` 模式：
   - 只有計數變動的（`lazy`）不寫——它們平常就要等到「最久未存上限」才寫，關機時丟掉的只是 `hits`／`last_seen` 的最新值。
   - 排序改成（有沒有相依、是不是分片、大小）：非分片的小檔（排程紀錄、節點池）先寫，再寫重要變動的分片。
   - 寫不完的照舊留到下次；日誌寫明「重要變動 N 份寫了 M 份、只有計數變動的 K 份沒寫」。
5. **平常就把重要變動寫掉**：解除串接、自己開始做 CDN 驗證時，重要變動的分片會快速累積。Flash 上的寫入間隔受每日額度（`system.flashWriteBudgetKB`）限制；要確認「重要變動」的分片在額度內優先於計數變動的（現況 `lazy` 已經排在後面），並在 `/api/status` 的 `persist` 顯示「待寫的重要分片數」，讓實測看得到關機前還剩多少。
6. **清單副本的最低保障**：不新增機制。預算把 CDN 資料限制在 30% 之後，7.5 MB 的分割區扣掉保留量還有空間放大部分清單副本；實測（第 6 節）確認 10 份清單存得下幾份，再決定 30% 要不要調。
7. 狀態：`/api/status` 的 `cdn` 加 `dbBudgetKB`、`dbDiskKB`（估計）、`prunedForBudget`（累計）。

**注意事項與預防問題**

- **資料遺失風險最高的一包**。`prune_to_budget()` 刪的是 `Core` 資料，一旦預算算錯（例如 `total_bytes()` 在某個平台回了很小的值）會把累積的驗證結果刪光。保護：預算下限 512 KB；`total_bytes()` 讀不到時不啟用預算；第一次啟用（升級後）如果要刪超過一半，分 4 次快照週期刪完並寫 WARN；整個行為可以用 `cdn.dbDiskBudgetKB: 0` 關掉。
- **Flash 寫入**：淘汰會讓很多分片變成「重要變動」（內容少了）。分批刪就是為了不在一個週期內重寫所有分片；每次淘汰的寫入量要算進每日額度的估計。
- 記憶體控制移出的冷資料（`evict_cold()`）在磁碟上還算筆數：估計大小要用「記憶體裡的＋移出的」。
- 備份匯入、種子、從上游匯入的網域資料都走同一個上限。
- 關機不寫 `lazy` 的分片：`hits` 少算一點會影響 `cdn.lite` 的「問過 2 次才驗」與淘汰順序，影響很小；但 `last_seen` 太舊可能讓常用的網域被當成冷的——所以平常的「最久未存上限」（`persistMaxAgeHours`，上限 24 小時）仍然保證一天內會寫一次。
- Windows（空間大）不啟用預算，但關機寫入的改動（C1 的 3 秒預算）同樣受益。
- 這一包不碰查詢路徑：淘汰在快照登記的背景週期做，拿的是既有的狀態鎖，要分批（同 `DUMP_CHUNK` 的作法）避免長時間佔鎖。

**測試**

- `budget_auto_from_fs_total`（7.5 MB → 約 2.2 MB；64 MB 以上不限；讀不到不啟用；下限 512 KB）。
- `prune_order_one_shot_then_failed_then_oldest`、`manual_policy_and_recent_verified_kept`。
- `first_prune_over_half_is_spread_over_four_rounds`。
- `prune_counts_evicted_cold_entries`。
- `shutdown_skips_lazy_and_writes_small_files_first`（`persist.rs`，延伸既有的 `shutdown_batch_flush`）、`shutdown_log_reports_skipped_lazy`。
- `shard_count_unchanged_by_budget`。
- `budget_zero_disables`。
- 實測（最重要）：D3 解除串接跑 24 小時，看網域資料大小、清單副本份數、重啟後下載量、關機寫了幾份花幾秒。

**文件**：`05-resources.md`（儲存類別表、小 Flash 一節）、`docs/hardware.md`、README 的儲存段、`fields.json`／LuCI 進階設定。

**實作（3.5.0，定案在 [05-resources.md](05-resources.md) 第 5.3、5.7 節）跟上面規劃不同的地方**

- **換算筆數不用「筆數 × 115」**：小 Flash 上還是 256 片，每片只有幾十筆，每個檔固定的開銷不能忽略。實測（`BENCH_SHARDS=256` 的 `bench_persist`）≈ 每片 1.1 KB ＋ 每筆 123 bytes，所以筆數 =（預算 − 分片數 × 1,100）÷ 125，下限 2,000 筆。7.5 MB 的 30% → 約 16,000 筆（不是 19,000）。
- **依分片的額度淘汰，不做全域排序**：每片額度 = 筆數 ÷ 分片數，超過的淘汰到 90%。這樣可以「只在分片本來就要寫的時候順便淘汰」，平常不多寫任何檔；全域排序每次都會動到幾乎所有分片。
- **分輪不是固定 4 次**：超過預算 110% 而且磁碟上實際也超過時，每 5 分鐘主動重寫最多「分片數 ÷ 16」片（256 片 → 約 80 分鐘），每片只重寫一次。分 4 次等於每次重寫 64 片；分得更細對 Flash 的總寫入量一樣，出問題時來得及關。
- **淘汰順序多一級「一天內出現過的排最後」**：照原本的三級，剛出現、只問過一次的網域是最先淘汰的，小機器減量（問過 2 次才驗）時新網域每一輪都被淘汰、永遠驗不到。「一次性」改成還要超過一天沒再出現。
- **關機時只有計數變動的不是完全不寫**：排在所有重要變動之後、只用時限的一半。過濾清單的命中次數（`filter-hits`）也是這一類的小檔，完全不寫的話每次關機都少一段；最後出現時間也影響淘汰順序。
- 測試名稱：`first_prune_over_half_is_spread_over_four_rounds` → `first_prune_over_half_is_spread_over_rounds`；另加 `budget_piggybacks_on_shards_already_being_written`、`dirty_db_is_pruned_before_the_full_rewrite`、`budget_round_sweeps_in_rounds_and_survives_restart`、`budget_keeps_what_is_in_use`、`budget_entries_model`。
- 「待寫的重要分片數」放在 `system.persist.pendingImportant`／`pendingCountersOnly`（所有檔，不只分片）。

### C6　「稍後下載」從 63 秒縮短

**目標**：開機用本機副本先建好過濾器後，沒有副本的清單盡快補上。

**原因（已找到）**：`filtering.rs` 的 `FilterService::spawn()`：啟動 2 秒後 `build_from_copies()`，成功（`built == true`）就固定 `sleep(60 秒)` 才往下走到 `update_lists()`。這 60 秒原本是給「全部都有副本」的情況（一分鐘後再問有沒有更新，3.4.2 之後還會再等到更新間隔）。但「有幾份沒副本」（`self.missing` 不是空的）也走同一條路，所以缺的清單要 2＋建置時間＋60 ≈ 63 秒才開始下載。在 7.5 MB 的 D3 上，存不下副本的那幾份清單每次開機都缺，這 63 秒它們的規則都不在。

**設計**

- `built == true` 而且 `missing` 不是空的：等待改成 10 秒加 0～5 秒亂數（讓開機時的路徑檢查、bootstrap、對時先跑），之後照既有流程（等對時、`update_lists()`）。`missing` 是空的：維持 60 秒。
- 這一次更新只需要補缺的：`update_lists(false)` 對有副本、而且還沒到更新間隔的清單不該發請求。要確認 `first_check_delay()` 與 `update_lists()` 在「有缺」時的行為——現況是有缺就整輪檢查（3.4.2 的說明：「新加的清單、上次有清單下載失敗時，照舊開機後就檢查」）。建議加一個只補缺的模式（`update_missing()`：只下載 `missing` 裡的，其他沿用現有的），避免每次開機都把所有清單問一遍（多半是 304，但還是請求；原則 2 的「不重複」）。
- 日誌把時間寫明：「N 份沒有副本的 10 秒後下載」。

**注意事項與預防問題**

- 開機時記憶體與 CPU 最緊：下載後要重建（新舊兩份同時存在）。既有的保護（記憶體不足時延後、`rebuild_lock`）照舊；10 秒不要再縮短。
- 系統時間還沒對時（路由器開機常見）時 TLS 會失敗：既有的「等對時，最多 10 分鐘」在 10 秒之後照樣生效。
- 串接中：3.4.3 起清單一律自己下載，不用等串接確定。
- 不能因為縮短等待造成重複下載：只補缺的模式要有測試確認「有副本的清單沒有被請求」。

**測試**（`tests/filtering.rs`，本機假的清單伺服器＋暫停時鐘）：`missing_lists_fetched_within_15s_after_copy_build`、`only_missing_lists_requested`、`all_copies_present_keeps_60s_then_interval`、`missing_fetch_waits_for_clock_sync`。實測：D3 重啟後看日誌的時間。

**文件**：README 過濾清單段、release notes。

### C9　記憶體「不足」路徑的測試開關

**目標**：讓測試者在記憶體很多的機器（512 MB 的 D3、Windows）上觸發「吃緊／不足」的整套流程。**正式使用不能誤開**。

**現況**：`memgov.rs` 的 `Governor::set_reader()` 可以換掉量測函式（測試用），`Reading` 可以直接造。主程式裡 `app.rs` 有幾個地方直接呼叫 `Reading::now()`（不經過 `Governor::read()`），`benchjob.rs` 的 `with_headroom()` 也是。現在要觸發只能真的把記憶體吃掉。

**設計**

- 管理 API `POST /api/memory/simulate?availMB=N&minutes=M`（`M` 1～30，預設 5）：到期前，記憶體控制讀到的「系統可用記憶體」＝`min(真實值, N MB)`。只會讓讀數變小（模擬不足），不能模擬成比真實更寬裕。`POST /api/memory/simulate?off=1` 立刻取消。
- **兩道保險**才會生效：
  1. 設定 `system.testHooks: true`（預設 false；不放進 LuCI、`fields.json`、UCI 的範例設定，只寫在測試文件裡）。沒開時 API 回 HTTP 403 與說明。
  2. 每次都有時間上限（最長 30 分鐘），到期自動恢復；重新啟動後不保留。
- 生效期間：每分鐘一行 WARN（「測試模式：模擬可用記憶體 N MB，還有 X 分鐘」）；`/api/status` 的 `memory.simulated: { availMB, until }`；狀態頁顯示橫幅。
- 實作：模擬值放在 `memgov.rs` 的行程層級（`AtomicU32` 存 MB、`AtomicU32` 存到期的相對秒數），在 `Reading::now()` 的最後套用——這樣所有直接呼叫 `Reading::now()` 的地方都一致。`Reading::now()` 只在背景的監看迴圈與工作裡呼叫，不在查詢路徑上。
- 不走環境變數：環境變數會留在服務設定裡被忘記；API＋到期時間比較不會誤留。
- `rpcd.sh` **不加**這個路徑（LuCI 不需要）；指令列加 `kuroshio notify simulate-memory`（包同一個 API）方便 padavan 上用。

**注意事項與預防問題**

- 模擬時真正的記憶體是夠的，所以所有「讓出」的動作都安全；恢復是到期後由既有的流程自己做（剛好也測到恢復路徑）。
- 模擬不影響評測子程序的 OOM 設定等系統層的東西，只影響黑潮自己的判斷。
- `system.testHooks` 是布林設定，會出現在 `/api/config`；`kuroshio check-config` 在它開著時提醒一行。
- 不要讓這個開關變成其他「測試後門」的入口：3.5.0 只有這一個用途，名稱泛用是為了以後不用再加設定，但每個新用途都要走同樣的兩道保險。

**測試**：`simulate_requires_test_hooks`（403）、`simulate_only_lowers_reading`、`simulate_expires_and_restores`（注入時鐘）、`simulate_capped_at_30_minutes`、`status_shows_simulated`、`admin_security.rs`（POST、要登入）。實測：D3 與 Windows 各跑一次「模擬 20 MB、5 分鐘」，配合 C3 看日誌。

### C11　重新啟動後第一次同步不再固定等 30 秒

**目標**：下游重新啟動後第一次跟上游同步，不要「一定 refused、30 秒後才成功」。**不能形成風暴**。

**現況**（`chain/share.rs`）

- 上游：`Shared::manifest()` 沒有建好的清單時回 None（回應器回 REFUSED）並 `spawn_build()`；清單閒置超過 `IDLE_RELEASE_MS`（30 分鐘）會釋放。`spawn_build()` 用 `building` 旗標保證同時只有一個建置。啟動時會先在背景建一次。
- 下游：綁定後等 `t.first`（30 秒）做第一次 `sync_once()`；回 `refused` 時再等 `t.first`、最多連續 3 次，之後回到正常間隔。
- 所以上游閒置超過 30 分鐘（只有一台下游、下游重啟前沒同步）時：第一次同步觸發建置、拿到 REFUSED，30 秒後才成功。這 30 秒下游還不知道上游提供哪些結果，補跑與清單更新都在等（3.4.2 的「等第一次同步」）。

**設計**（兩邊都做，各自獨立生效）

- **上游先建好**：下游的登記（`reg`，`chain/responder.rs` 的登記處理成功時）與驗證挑戰成功時，呼叫 `Shared` 的預熱（沒有建好的清單就 `spawn_build()`、更新 `last_used`）。下游綁定後 30 秒才第一次同步，清單通常已經建好。只對通過驗證的下游做；`spawn_build()` 本來就是單一進行。舊版下游（3.4.x）接新版上游也受益。
- **下游重試更快**：第一次同步遇到 `refused` 時的等待改成 5 秒、15 秒、30 秒（各加 0～20% 亂數），仍然最多連續 3 次，之後回到正常間隔。新版下游接舊版上游時受益（最快 5 秒後成功）。
- 上游記憶體壓力不是 Normal 時 `manifest()` 也回 None：這種情況重試也沒用，三次之後照舊回到正常間隔，不變。

**注意事項與預防問題**

- **風暴檢查**：一台下游最多多 2 筆重試查詢（5、15 秒），總次數上限沒變（3 次）。上游的建置不因為重試而重複（`building` 旗標）。多台下游同時重啟：各自 3 次，亂數錯開。
- 預熱讓上游在「有下游登記」時多建一次清單（讀幾個檔、算雜湊、簽章），成本在背景；登記本身有速率限制（`refused_rate`），不會被外部觸發放大。非區網來源本來就被拒絕。
- 不要改成「REFUSED 就立刻重試」或「上游同步建置後再回應」：前者是迴圈，後者讓回應器（在查詢路徑上）等建置。
- 相容：協定不變。

**測試**（`tests/chain_share.rs`）：`reg_prewarms_manifest`、`first_sync_succeeds_without_refused_after_prewarm`、`refused_retries_at_5_15_30_then_normal`（注入 `timing`）、`retry_count_still_capped_at_three`、`pressure_refused_does_not_spin`。實測：D3 接主路由器，上游閒置 30 分鐘以上後重啟下游，看第一次同步的時間。

**文件**：`10-chain.md` 第 3.3、3.4 節。

### C12　單獨運作時 D3 的效能檢查

**目標**：找出 3.4.2 測試裡「D3 單獨運作、每秒 20 筆時延遲高、CPU 閒置只剩 12～18%」的原因，有證據再改。**3.5.0 第 1 批只做量測**；修改依結果在第 3 批決定。

**現況與假設**

- `kuroshio-config/src/lib.rs` 的 `auto_parallel()`：沒有 AES 的機器 `resolver.parallel` = 2（每筆先問 2 台）；`resolver.backfill`（預設 `cdn`）在回答後背景補問沒問到的上游（`backfillSample` 16 筆抽 1）。
- 加密上游的連線：`kuroshio-net/src/tls.rs` 的 `Dot`（每個上游一條連線、閒置 30 秒關閉、斷了重連）、`Doh`（HTTP/2 連線重用）；`build_client_config()` 用 ring 的預設密碼套件順序，共用 session 快取。
- 假設（未證實）：
  1. 沒有 AES 指令時，AES-GCM 的加解密與握手很慢；rustls 預設把 AES 套件排在 ChaCha20-Poly1305 前面，伺服器多半就選了 AES。
  2. 連線被關閉後重新握手的次數比預期多（閒置逾時、伺服器端關閉、HTTP/2 的 GOAWAY）。
  3. 每筆查詢實際問的上游數比 `parallel` 多（避險加問、背景補問、CDN 驗證的解析）。
  4. 不是 TLS：CDN 驗證（每個新網域一次 HTTPS 探測）、測速排序（`resolver.rankIps` 的 TCP 連線）、過濾比對、快照寫入。

**量測計畫**

- 計數器（全部 `AtomicU32`，在連線建立／握手完成這些本來就慢的地方累加，不在每筆查詢的熱路徑上加鎖）：每種上游協定的「新連線數、完整握手數、session 續用數、協商到的密碼套件（AES／ChaCha 各幾次）、被對方關閉數」；解析器的「每筆查詢實際送出的上游查詢數」分布（1、2、3、4 以上四個桶）；背景補問數。放在 `/api/status` 的 `resolver.perf`（`lite=1` 時不回）。
- 老毛子的測試矩陣（每格每秒 20 筆、10 分鐘、記延遲中位數／P95 與 CPU 閒置）：
  1. 只用一般 DNS 的固定上游（沒有 TLS）——基準。
  2. 只用 DoT、只用 DoH、只用 DoH3，各一輪。
  3. `resolver.parallel` 1、2。
  4. `cdn.enabled` 開／關；`resolver.rankIps` 開／關；`resolver.backfill` 關。
  5. 查詢內容：全部重複（快取命中）對全部新網域。
- 判讀：1 與 2 的差就是 TLS 的成本；計數器看是握手多還是純加解密；4 分離出 CDN 與測速的成本。

**可能的修改（依量測結果，逐項另外評估，不預先承諾）**

- 沒有 AES 的機器把 ChaCha20-Poly1305 排在用戶端密碼套件順序的最前面（`build_client_config()` 依 `kuroshio_config::has_aes()`；QUIC 的設定同樣）。這是最可能有效、風險也最低的一項：不改行為，只改偏好。
- DoT 閒置關閉時間拉長、或在低流量時保持一條熱連線（要算對上游的負擔）。
- 避險加問的等待時間在沒有 AES 的機器上拉長。
- 沒有 AES 的機器上自動上游的選擇偏好（評測時把握手成本算進去）。

**注意事項與預防問題**

- **先量再改**：原則 6 是「不做讓效能變差的修改」，沒有數據時任何「優化」都可能是反效果；原則 5 不做激進優化。
- 計數器本身不能拖慢：只用 `AtomicU32` 的 `fetch_add(Relaxed)`，放在握手完成與連線關閉的地方；「每筆查詢送出幾個上游查詢」在 `ask()` 結束時累加一次（既有的 `picks` 計數器旁邊）。
- 改密碼套件順序要確認所有支援的上游都能握手成功（ChaCha20-Poly1305 是 TLS 1.3 必備套件之一，TLS 1.2 的伺服器不一定有——只調順序、不移除 AES，就不會連不上）。
- 單獨運作的效能改善不能犧牲原則 1：不能用「少驗證、少換台灣節點」換數字。

**測試**：`perf_counters_count_handshakes_and_resumptions`（本機假的 TLS 伺服器，`tests/tls.rs`）、`fanout_histogram_buckets`、`status_lite_omits_perf`；若改密碼套件順序：`no_aes_prefers_chacha_but_keeps_aes`。實測就是上面的矩陣。

**文件**：`docs/hardware-details.md`（MT7621 的量測結果）、`06-optimizations.md`、`docs/integration.md`（`resolver.perf`）。

## 5. E 組：觀測與線路感知

（工作包的字母跳過 D：D1、D2… 已經是實測清單裡老毛子 D3 的項目編號。）

這一組回答兩個問題：「這台現在的資料新不新、有沒有哪裡不對」（E1、E2、E8、E9），以及「這條線路實際到得了哪些台灣機房、該怎麼用」（E3～E7、E10）。來源是觀察某台灣即時服務的公開狀態頁：它的使用者幾乎都在台灣，但流量進 Cloudflare 的機房分布是 TPE 45%、SJC 38%、NRT 9.5%、SIN 4%、KHH 0.9%——一半以上（約 52%）被送出國，進得了高雄的不到 1%。

### 5.0 核心前提與共同規定

**機房是「IP × 這條線路」量出來的，不是 IP 的屬性。**

- 任播 CDN 的同一個 IP，從不同業者的線路進去會落在不同機房；業者機房內的快取節點可能只服務那一家業者。
- 大多數線路只到得了一個台灣機房（例如固網只到得了 TPE）。「到不了高雄」是線路的事實，不是要修的問題：**不為了找第二個機房多發任何探測**。
- 所以別人量到的機房（好友的、上游的）只能當參考；這台用的機房標示一律是這台自己量到的（E4）。

**這一組共同的限制**（第 0 節之外再加）

- **不新增背景工作、不新增對外探測**。例外只有兩個，都有明寫的上限：E4 串接中的機房抽查（搭既有抽查的名額，一天最多 24 個請求）、E7 判斷「比原本慢」之前的複測（每次驗證最多 2 條連線，只有第一次量到明顯較慢時才發）。
- **查詢路徑不動**。E9 在 `Stats::with()` 既有的鎖裡多一次整數比較；E5、E6 改的是背景健檢排序的結果，`serve_ips()`（`pools.rs:1143`）不改；其餘都在背景工作結束時或管理 API 被讀的那一刻計算。
- **不寫 Flash**。新增的狀態都在記憶體、重新啟動清空；例外是 `scheduler` 狀態檔多一個 `failStreak` 數字（E1）與 `pools.json` 節點上多一個 `upPop` 字串（E4），都在既有的檔裡、不增加寫入次數。
- **新 API 都放在既有路徑裡**（`/api/status`、`/api/dashboard`、`/api/chain`、`/api/cdn/pools`、`/api/cdn/explain`），不新增路徑：`rpcd.sh` 的白名單（`:79`～`:83`）不用改，padavan 韌體也不用加路徑。`/api/status` 的 `warnings` 格式與內容不變。

### E2　發現清單

**性質**：只增加觀測。**預設**：一律有。

**做什麼**：`/api/status` 保留 `warnings`（字串陣列、內容與格式都不動，padavan 韌體在讀），另外新增 `findings`：每一筆有嚴重度（`warn`／`info`）、一句話、次數、第一次與最近一次的時間；用 `key` 去重、最多 32 筆、不再發生就過期消失。

**為什麼**：`warnings` 只能說「現在有事」，沒有「什麼時候開始、發生幾次、已經好了沒」；而且很多現象（靠過期快取撐著、只到得了一個機房、上游給的機房跟本機量的不一樣）不是「要使用者馬上處理的事」，放進 `warnings` 只會變成噪音。分工：`warnings`＝現在需要處理；`findings`＝觀察到的現象與它的經過。**同一件事不兩邊都放。**

**資料從哪來**（第一批；每一條規則都是「讀現有狀態 → 有或沒有」的純函式）

- `/api/status` 被讀時評估，兩次評估至少間隔 30 秒（中間的請求回上一次的結果，LuCI 每幾秒讀一次也不會重算）。

- `active`：這一次評估條件還成立。

**上限與恢復**

- 最多 32 筆；`text` 最長 200 個字元；`count` 飽和到 9,999。

### E3　這條線到得了哪些台灣機房

**性質**：只增加觀測。**預設**：一律有（CDN 開著時）。

**做什麼**：依節點池裡**本機確認過**的節點，統計這條線路到得了哪些台灣機房，IPv4、IPv6 分開：每個機房有幾個節點、幾個網段（IPv4 用 /24、IPv6 用 /48）、幾家 CDN。給一句白話：「這條線目前只到得了台北機房」。

**為什麼**：見 5.0。使用者看到「高雄 0 個節點」會以為黑潮沒找到；實際上是這條線路進不去。把它說清楚，也讓 E5 知道這條線需不需要做機房層級的事。

**資料從哪來**（不發任何新探測）

- `Pools` 的 `pool4`／`pool6`（`pools.rs:303`）：每個節點的 `pop`（`PoolNode.pop`，`pools.rs:44`）是健檢時本機量到的——`health_check()` 每一輪對每個節點做 HTTP 探測、把 `x.pop` 設成量到的值（`health.rs:164`）；節點池工作的階段 B 也是本機量的（`jobs/pool.rs:637`～`:654`）。
- 只算：不在 `bad` 裡、`is_tw_pop()`（`providers.rs:297`）、不是種子（`pop == "seed"`）、不是還沒確認的上游節點（E4 的 `upPop` 還在的另外計成 `unconfirmed`）。
- 機房代碼合併成城市再造句：TPE、TSA → 台北；KHH → 高雄；RMQ、TXG → 台中；TNN → 台南（代碼照樣列在資料裡）。
- 沒有台灣 POP 的 CDN（Fastly）另外列在 `nearby`，資料直接讀既有的 `PopView`（`pools.rs:474`、`pop_view()` `:848`，已經依品質排好），**不另外算一份、不改它**。
- 另一個既有的角度是 `/api/dashboard` 的 `toPops`（`site.rs` 的 `dashboard_stats()`：依網域的驗證結果、用查詢次數加權）。兩個都留：`reach` 回答「線路到得了哪裡」，`toPops` 回答「流量實際去了哪裡」。

**什麼時候算**：節點池內容變動的那幾個背景時刻結束時順便算（都已經拿著狀態鎖）：`health_check()` 結束（`health.rs:240` 附近）、`Pools::replace()`、`merge_shared()`、`import_shared()`。結果放成一份 `Arc`，`/api/status` 直接讀。**WAN 變動**（`/api/notify/wan-changed`，`admin.rs:832`）：呼叫新的 `Cdn::on_wan_changed()`，把 `wanEpoch` 加 1、`reach.stale` 設成 `true`、清掉 E5 的連續計數與暫緩；**不因此補跑健檢或掃描**，等下一輪定時健檢（最多 30 分鐘，`cdn.healthIntervalMin`）自然更新。平常每一輪健檢只是重算統計；「要不要做機房層級的事」（E5 的資格）只在 `wanEpoch` 變了、或啟動後的頭兩輪重新判斷，之後沿用。

**介面**（`/api/status` 的 `cdn.reach`，由 `Cdn::status_lite()` `cdn.rs:1190` 帶出；`/api/cdn/pools` 也帶同一份）

```json
"reach": {
  "at": 1795486200000, "wanEpoch": 2, "stale": false, "unconfirmed": 0,
  "v4": { "text": "這條線目前只到得了台北機房", "multi": false,
          "pops": [ { "pop": "TPE", "city": "台北", "nodes": 31, "prefixes": 22, "providers": 4, "medianMs": 4.1 } ] },
  "v6": { "text": "這條線的 IPv6 目前只到得了台北機房", "multi": false, "pops": [] },

```

- `multi`：這個家族有兩個以上的城市、每個城市至少 2 個節點而且分布在 2 個以上的網段（一個節點的機房不算「到得了」到可以切換的程度，E5 用）。

### E4　機房以本機量到的為準（好友節點、串接節點）

**性質**：行為改變（小）。**開關**：`cdn.popAudit`（布林，預設 `true`）；`false`＝不記上游宣稱的機房、不做串接中的機房抽查，跟現在一樣。

**確認的現況**

- **好友分享的節點：只收 IP 當候選，對方的機房與延遲丟掉。這是對的，不改。** 線上格式其實有帶：分享端 `CdnData::local_records()`（`community_bridge.rs:47`）把節點的 `pop`、`ms` 都放進 `LocalRecord::Node`，接收端的 `NodeCandidate`（`provider.rs:67`）也有這兩個欄位；但 `on_received()`（`community_bridge.rs:144`）只把 `(p, ip)` 交給 `Cdn::add_friend_nodes()`（`cdn.rs:557`）：檢查在官方範圍裡、節點池還沒有、每家每個家族一次最多 `FRIEND_MAX_NODES` = 500（`cdn.rs:61`），放進候選名單 `harvest`（`db.rs:2002` 的 `add_harvest_candidate()`，上限 `HARVEST_MAX` = 3,000，滿了不放、不擠掉自己收集的），等每日節點池工作在本機量延遲、確認機房之後才會用。3.5.0 補一個回歸測試釘住這件事，並寫進 README 與規格 03。
- **串接上游給的節點：照收上游的機房與延遲。** `Cdn::import_shared()`（`cdn.rs:1499`）檢查官方範圍與每家上限後交給 `Pools::merge_shared()`（`pools.rs:696`）：上游的節點在前、這台原本的接在後面，`PoolNode` 的 `pop`、`ms`、`speed`、`slow` 都是上游量的。理由是同一條 WAN 出口，上游量的就是這台會走的路。
- **例外**：上游有多條對外線路（多 WAN 負載平衡、策略路由）時，下游的連線不一定走上游量測時的那一條，機房可能不同。
- 現在已經有的保護：串接解除後，定時健檢會用本機量到的機房蓋掉 `x.pop`（`health.rs:164`），不是台灣機房的標成壞節點；但這是靜靜發生的，沒有紀錄，而且**串接中完全不量**（3.4.2 為了不重複探測而關的，`chain/share.rs:1325`）。

**做什麼**

1. **記下上游宣稱的機房**：`import_shared()` 匯入的節點，在 `PoolNode.extra`（`pools.rs:72`，不認得的欄位原樣保留）放 `upPop`＝上游給的 `pop`。這台自己原本就有、而且機房一樣的節點不放。
2. **本機量到時比對**（兩個時機，都是既有的量測）：
   - 定時健檢與節點池工作（沒有串接、或串接解除之後）：`health_check()` 套用結果時，節點有 `upPop` 就比前三碼：一樣 → 拿掉 `upPop`、`popConfirmed += 1`；不一樣但還是台灣機房 → `x.pop` 用本機的（本來就是）、拿掉 `upPop`、`popMismatch += 1`；不是台灣機房 → 照既有的流程標成壞節點，`popMismatch += 1`。
   - **串接中的機房抽查**（搭直系血親的答案抽查，規格 10 第 3.8 節、`chain/audit.rs`）：既有的抽查每 16 筆抽 1、每 30 秒最多 1 個、同時 1 個，對上游給的 IP 做 TLS 握手檢查憑證（`resolver.rs:910`）。握手通過之後，如果那個 IP 是節點池裡 `upPop` 還在的節點，用**同一個抽查名額**再對它做一次那家 CDN 的機房探測（`Net::http_probe()` 打 `Provider.probe` 的路徑，同健檢 `health.rs:118`），把量到的機房交給新的 `Cdn::note_local_pop(provider, ip, pop)` 做上面同樣的比對。
3. **以本機為準**：比對過的節點 `pop` 是本機的；E3 的 `reach` 只算本機確認過的（還沒確認的計在 `unconfirmed`）。
4. **不一致時**：列入 E2 的 `pop-mismatch`（「上游給的節點有 N 個從這台量到的機房不一樣（上游可能有多條對外線路）；已經改用這台量到的」）。24 小時內比對過的節點有一半以上不一致（至少 4 個）→ 這台標 `chainPopUnreliable`：E5 的機房切換不啟用（機房標示在這條路上不穩定，切了沒有意義）；24 小時沒有新的不一致就自己解除。
5. **不因此解除串接**：機房不同不是「上游不可信」（憑證是對的、節點在官方範圍裡），只是線路拓樸；`audit` 的可疑計數不動。

**介面**

- 設定：`cdn.popAudit`（預設 `true`）。
- `/api/status` 的 `cdn.popAudit`：`{ "enabled": true, "pending": 9, "confirmed": 31, "mismatch": 0, "probes24h": 12, "lastMismatchAt": null, "chainPopUnreliable": false }`。
- `/api/cdn/pools` 的節點：還沒確認的多 `upPop`（因為 `extra` 本來就會序列化出來）。
- 下游再往下分享時（`export_shared()`，`cdn.rs:1437`）不帶 `upPop`（那是這台的查核狀態，不是資料）。

**上限與恢復**

- 機房抽查用的是既有抽查的名額（不多佔一個同時數、不縮短 30 秒的間隔），另外再限：10 分鐘最多 1 個、一天最多 24 個、每個節點只量一次（量到就拿掉 `upPop`）。節點池一家十幾個節點，所以匯入一次之後抽查量會自己歸零；上游的節點池一天更新一次。
- 記憶體壓力不是 `Normal`、系統時間沒對時、這台關掉 CDN、`cdn.lite`（小機器減量）時的抽查：前三者不做；`cdn.lite` 改成 30 分鐘最多 1 個、一天最多 8 個（減量，不是關掉）。
- `upPop` 跟著 `pools.json` 存（幾個位元組），舊版讀到會原樣保留、不影響舊版的行為。
- 判斷錯的最壞情況：`reach` 少算幾個還沒確認的節點、機房切換暫時不啟用——都是回到現在的行為。

**MT7621**：串接中一天最多多 24 個 HTTPS 請求（每個一次沒有 AES 的握手，約等於一次 CDN 驗證的十分之一流量）；不在查詢路徑上（抽查本來就是答案存進快取之後另外排的工作）。健檢時的比對是每個節點多一次字串比較。

**測試**

- `import_shared_records_up_pop`、`own_node_with_same_pop_has_no_up_pop`。
- `health_check_confirms_or_corrects_up_pop`（一樣、不一樣但在台灣、不在台灣三種）。
- `chained_pop_probe_uses_audit_slot_and_is_capped`（10 分鐘 1 個、一天 24 個、每個節點一次；假的 `Net` 計數）。

### E5　機房層級的健康與切換

**性質**：行為改變。**開關**：`cdn.popSwitch`（布林，預設 `true`）；`false`＝只彙總、不切換。**大多數線路只到得了一個機房，這一包對它們只有彙總，不會有任何切換。**

**做什麼**

1. 彙總每個（CDN、家族、機房）的健康：節點數、壞節點數、失敗率、延遲中位數。
2. **只有這條線到得了兩個以上台灣機房時**，某個機房持續變差、另一個明顯正常，就把變差的機房的節點暫時排到後面；幾小時後自己恢復原本的順序。

**為什麼**：現在的保護是節點層級的（壞節點進 `bad`、健檢依延遲重排）。機房整個出狀況（維護、對某家業者的互連壅塞）時，節點是一個一個被標壞的，中間那段時間使用者會一直被分到同一個機房裡還沒被標壞的節點。

**資料從哪來**

- 每一輪 `health_check()`（`health.rs:100`，預設每 30 分鐘、每秒最多開始檢查 20 個節點）的結果 `HResult`：每個節點的狀態（`Tw`／`NotTw`／`Dead`）、延遲、**檢查前的機房**（`old_pop`，壞掉的節點算在它原本的機房頭上）。套用結果時（已經拿著狀態鎖）順便彙總，**不多做任何探測**。
- 網域驗證的失敗**不**算進機房（`verifier.rs`）：那多半是「這個網站不服務這個節點」（網站層的限制、特定錯誤頁），算進來會冤枉機房；連線層的失敗已經由 `mark_bad()`（`pools.rs:1161`）反映在節點上，下一輪健檢就會算到。這樣同一次失敗不會被算兩次。

**切換的規則**（全部是保守的初值，等實測，第 7 節 Q9）

- **資格**（都要成立）：`cdn.popSwitch` 開著；這家 CDN 不是最近節點型（Fastly 這類已經有 `PopView`／`keep_pop()` 的 POP 切換，`pools.rs:474`、`health.rs:435`，**E5 完全不碰它們**）；E3 的 `reach.<家族>.multi` 連續兩次是 `true`；沒有串接；E4 沒有標 `chainPopUnreliable`；記憶體壓力 `Normal`。
- **機房變差**：這一輪失敗率 ≥ 20%，而且（節點數 ≥ 3，或壞的 ≥ 2 個）。連續 3 輪（預設約 90 分鐘）才算。
- **另一個機房明顯較好**：同樣這 3 輪失敗率都是 0、可用節點 ≥ 2 個而且分在 2 個以上的網段、延遲中位數不比變差那個機房（可用節點）的多 20 毫秒以上。
- **動作**：把變差機房的節點「暫緩」4 小時：健檢排序時排在其他可用節點後面、壞節點前面。**不移出節點池、不標壞、照常健檢。** 寫一行 WARN。
- **恢復**：4 小時到期，回到原本依延遲的排序，連續計數歸零；要再暫緩得重新連續 3 輪變差（所以最快約 5.5 小時才可能切第二次）。不提早結束（提早結束再變差就是來回）。
- **兩邊都差時不動**：暫緩期間另一個機房也變差（失敗率 ≥ 20%）→ 立刻取消暫緩，回到現在的行為（節點層級的 `bad` 與延遲排序）。
- **不來回**：同一個（CDN、家族）24 小時內最多暫緩 2 次；第 3 次不切、列入 `pop-flapping`。
- 同一個（CDN、家族）同時只暫緩一個機房。
- **安全底線**：暫緩的節點還在節點池裡；其他機房的可用節點不到 `serveCount` 個時，`serve_ips()` 本來就會往後取到它們，不會沒有節點可回。

**怎麼做（不動查詢路徑）**：`serve_ips()`（`pools.rs:1143`）照舊取節點池前面 `serveCount` 個可用節點，不改。順序是健檢排出來的：`health.rs:223` 的排序鍵從（壞的在後、延遲）改成（壞的在後、暫緩的在後、延遲），`:413` 新 IPv6 節點加入時的排序用同一個比較。比較時用 `pop3_is()`（`pools.rs:159`，不配置）。節點池工作換上新的節點池（`Pools::replace()`）15 秒後本來就會跑一輪健檢（`app.rs:956`），順序會跟上。

**介面**

- 設定：`cdn.popSwitch`（預設 `true`）。
- `/api/status` 的 `cdn.popHealth`（陣列，最多 64 筆）與 `cdn.popSwitch`：

```json
"popHealth": [
  { "provider": "cloudflare", "family": 4, "pop": "TPE", "nodes": 9, "bad": 0, "failRate": 0.0,
    "medianMs": 4.2, "badStreak": 0, "held": false, "heldUntil": null }
],
"popSwitch": { "enabled": true, "eligible": false, "reason": "single-pop", "switches24h": 0 }
```

- `reason`：`single-pop`、`nearest-provider`（只對那一家）、`chained`、`chain-pop-unreliable`、`memory`、`disabled`、`ok`。
- 發生切換、反覆想切換時列入 E2（`pop-switched`、`pop-flapping`）。

**上限與恢復**：彙總最多 64 筆、每筆幾個數字，只在記憶體；重新啟動、WAN 變動（E3 的 `on_wan_changed()`）、重新載入設定都清掉連續計數與暫緩。暫緩有期限（4 小時）、有每日次數上限、兩邊都差時取消。判斷錯的最壞情況：四小時內優先回另一個「本機確認過、健檢正常、延遲差不到 20 毫秒」的台灣機房的節點。

**MT7621**：每一輪健檢結束時多一次分組統計（節點數等級的迴圈），沒有新的連線。排序多比一個鍵。

**測試**（`crates/kuroshio-cdn/src/tests/`；注入時鐘、假的 `Net`）

**要改的檔案**：`crates/kuroshio-cdn/src/reach.rs`（`PopHealth`、規則的純函式）、`crates/kuroshio-cdn/src/health.rs`（彙總、排序鍵）、`crates/kuroshio-cdn/src/pools.rs`（暫緩的狀態放在 `ProviderPools`，不序列化）、`crates/kuroshio-cdn/src/config.rs`、`crates/kuroshio-cdn/src/cdn.rs`（`status_lite()`）。

### E6　同機房內的網段分散

**性質**：行為改變（只影響節點池前幾名的順序）。**開關**：`cdn.spreadPrefixes`（布林，預設 `true`）；`false`＝現在的順序。

**做什麼**：只到得了一個機房的線路沒有機房可以換，能分散風險的是網段：讓回給裝置的那幾個節點（`serveCount`，預設 4）盡量來自不同的 /24（IPv6 是 /48）。

**先查現在有沒有分散（結論：建立時有，之後會被打破）**

- IPv4：節點池工作階段 B 之後「每個 /24 只留最快的一個」（`jobs/pool.rs:651`～`:654`），所以**自己建的 IPv4 節點池本來就是一個網段一個節點**。這一點不用加。
- IPv6：節點池工作一樣每個 /48 只取一個（`jobs/pool.rs:903`～`:904`）；**但接著把永久保存的台灣 IPv6 節點全部併進來、只依延遲排序**（`jobs/pool.rs:940`～`:950`；載入時 `pools.rs:562`～`:572`、健檢發現新節點時 `health.rs:400`～`:416` 也是）。永久節點多的那一家（實測有 585 個）前 4 名可能全在同一個 /48。
- 串接：`merge_shared()`（`pools.rs:696`）把上游的節點與這台原本的接在一起，只用 IP 去重，兩邊可能各有一個同網段的節點。
- 定時健檢只依延遲重排（`health.rs:223`），同網段的幾個節點延遲幾乎一樣，會排在一起。

**設計**：新的純函式 `pools::spread_head(pool, bad, n, key)`，在健檢排序之後呼叫（跟 E5 同一個地方）：

- 只看可用（不在 `bad`、沒被 E5 暫緩）的節點、只調整前 `n` = `serveCount` 個位置。
- 由前往後：第 i 個位置的節點如果跟前面已經放的某一個同網段，就從後面找第一個「不同網段、而且延遲不超過這個位置原本節點的 1.5 倍＋5 毫秒」的節點換上來；找不到就不換。
- 其餘節點的相對順序不變。不新增、不移除節點，不發任何探測。
- 最近節點型的 CDN（Fastly）不套用（它的網段選擇在 `PopView`／`map_ips()`，`pools.rs:979`）。

**介面**：設定 `cdn.spreadPrefixes`（預設 `true`）。`/api/cdn/pools` 不變（順序就是結果）；`cdn.reach.<家族>.pops[].prefixes` 看得到每個機房有幾個網段可用。

**上限與恢復**：只動前 `serveCount` 個位置；延遲條件保證不會為了分散把明顯較慢的節點換上來；每一輪健檢重新算，節點恢復或消失都會自己調整。

**MT7621**：每輪健檢一次、最多 `serveCount × 節點數` 次比較；查詢路徑不變。

**測試**（`pools.rs` 的單元測試）

- `own_v4_pool_is_already_one_per_24`（釘住現況：節點池工作的結果每個 /24 一個）。
- `spread_head_picks_distinct_48_among_permanent_v6`（前 4 名原本同一個 /48）。
- `spread_head_keeps_order_when_alternative_too_slow`、`spread_head_noop_when_already_distinct`。
- `spread_head_skips_bad_and_held`、`spread_after_merge_shared_same_24`。
- `spread_off_keeps_latency_order`、`fastly_not_spread`。

**要改的檔案**：`crates/kuroshio-cdn/src/pools.rs`（`spread_head()`）、`crates/kuroshio-cdn/src/health.rs`（兩個排序的地方）、`crates/kuroshio-cdn/src/config.rs`。

### E7　最後退路：台灣節點實測比原本慢就用原本的答案

**性質**：行為改變。**開關**：`cdn.slowerFallback`（布林，預設 `true`）；`false`＝驗證通過就換，跟現在一樣。

**做什麼**：驗證「台灣節點能不能服務這個網站」的同時，已經量了原本答案的那個 IP。如果台灣節點的請求時間**明顯**比原本的慢，這個網站暫時用原本的答案，幾小時後重測。

**為什麼**：只到得了一個機房的線路，那個機房對某些網站慢的時候（尖峰、某家 CDN 的台灣節點壅塞）沒有別的機房可以換；現在只要驗證通過就換，不看有沒有比較快。目的是「帶回台灣而且快」，換了更慢就違反原則 1 的「快」。

**能重用的與現況**

- 驗證流程本來就先探測原本的 IP（`verifier.rs:258`～`:300`，結果存成 `Base`：`ok`、`pop`、`ms`，`db.rs:384`），再探測台灣節點（結果存成 `Verdict`，`db.rs:331`）。兩次探測的 `ProbeResult.timing`（`kuroshio-net/src/probe.rs:38`）都有分段時間，`Timing::request_ms()`（`probe.rs:54`）＝連線＋握手＋TTFB——**就是 B4 跨 CDN 實測分數用的同一個量**（`cross.rs:459`）。
- B4 的做法（`cross.rs:182`～`:216`、`:471`～`:484`）：一次樣本雜訊大，所以兩邊各再量一次取小的（`SCORE_EXTRA_PROBES` = 2）；已經在用的門檻放寬（遲滯）。**E7 重用量法與「複測取小、遲滯」的作法**，門檻另外定：B4 是「要比原站快才換過去」（0.95），E7 是「明顯比原本慢才不換」，方向相反。
- 最近節點型（Fastly）已經有「沒有明顯比原本快就不換」（`optimizer.rs:656`～`:675`，`cdn.nearestMinGainMs`），**E7 不套用**。
- B1 的相對評分是節點池層級（哪些台灣節點算慢），E7 是網站層級（這個網站走台灣節點有沒有比原本慢），不重疊。
- 驗證失敗時查詢路徑本來就回原本的答案（`optimizer.rs:677`～`:684` 的 `VState::Fail`）。E7 用這條既有的路，**`optimizer.rs` 不用改**。

**設計**

- 只處理：IPv4、非最近節點型、原本的 IP 探測成功、兩邊的 `request_ms()` 都量到、網域不是手動設成「一定換」（`Policy::Always`）。
- 判斷「明顯較慢」：`台灣 > 原本 × 1.5 + 30 毫秒`。第一次量到符合時，兩邊各再探測一次、各取小的再比一次（最多多 2 條連線）；還是符合才算。
- 上一次的結果已經是「比原本慢」時，要回到換台灣節點的門檻比較嚴：`台灣 ≤ 原本 × 1.2 + 30 毫秒`（遲滯，不在門檻附近來回）。
- 記錄：沿用 `done()`（`verifier.rs:647`）記成 `fail`，`reason` 寫「台灣節點實測比原本慢（N 毫秒對 M 毫秒）」，`extra` 放 `slower: true`、`score`、`origScore`（欄位名同 B4 的 `Cross`）；到期時間用 `Done.retry_at` 設成 6 小時後（不走失敗的逐次拉長）；**不增加 `fails`、不對節點呼叫 `mark_bad()`（節點沒有壞）、不向好友的提示回報失敗（`hint_result`）**。
- IPv6 不做：IPv6 驗證失敗在 `v6Policy = drop` 時會把 AAAA 丟掉（`optimizer.rs:679`～`:683`），「比較慢」不該觸發丟棄。
- **保險絲**：最近一小時的驗證裡「比原本慢」超過 30%（至少 10 次）→ 多半是線路當下壅塞或量測有問題，不是節點的問題：6 小時內不再判「比原本慢」（照驗證通過處理）、寫 WARN、列入 E2 的 `slower-fuse`。
- `explain`（B7）：新的決定代碼 `slower`（「這個網域用 ○○，台灣節點能用，但實測比原本的答案慢（N 對 M 毫秒），暫時用原本的答案；到期後重測。」），加在 `explain.rs:13` 的 `decision` 與 `text_of()`。

**介面**

- 設定：`cdn.slowerFallback`（預設 `true`）。
- `/api/status` 的 `cdn.stats`：多 `verifyOk`、`verifyFail`（E2 用）、`slowerFallback`（累計）；`cdn.slowerFuseUntil`（跳了才有）。
- `/api/cdn/domain`、`/api/cdn/explain`：`v4` 多 `slower`、`score`、`origScore`。

**上限與恢復**：每次驗證最多多 2 條連線，而且只在第一次樣本就明顯較慢時；重測 6 小時一次；保險絲限制一次能影響的比例；到期重測通過就自己換回台灣節點。判斷錯的最壞情況是某些網站 6 小時走原本的答案（就是沒有黑潮時的樣子）。

### E9　24 小時歷史

**性質**：只增加觀測。**預設**：一律有。

**做什麼**：每 5 分鐘一點、288 點的固定大小環形陣列，記少數幾個欄位；API 帶出、狀態頁畫小圖。不寫 Flash，重新啟動清空。

**為什麼**：現在有最近 90 分鐘每分鐘（`Inner.minutes`，`MINUTES_KEPT` = 90，`stats.rs:30`；只有查詢、攔截、加速三個數）與每日歷史（`RETENTION_DAYS` = 31）。「昨天晚上是不是慢過」「凌晨上游是不是掛過」兩個都看不到。

**設計（從既有的計數衍生，不重複計數）**

- 今天的累計值本來就在 `Day`（`stats.rs:83`：`query`、`blocked`、`servfail`、`stale`、`miss`、`lat_miss` 直方圖、`route` 的 `abroad`／`acc`）。**查詢路徑上不加任何新的累加**；每 5 分鐘把「現在的累計值 − 上一格結束時的累計值」存成一格。
- 觸發點：`Stats::with()`（`stats.rs:703`，每次計數本來就會進來、已經拿著鎖、已經讀了時鐘）。它現在比對「日序有沒有變」；多比對一個「5 分鐘槽號（`now ÷ 300`）有沒有變」。變了就關掉上一格（一次十幾個數字的減法）。順序：**先關格、再換日**（台北午夜也是 5 分鐘的邊界，換日前先用舊的 `Day` 算完差值，換日後基準歸零）。
- 讀取時（API）也先走一次 `with()`，所以很久沒有查詢時讀到的也是對的；中間沒有查詢的格子補 0。
- 一格的欄位（都是 `u32`／`u16`，32 位元 MIPS 沒有 64 位元原子操作——這裡在既有的 `Mutex` 裡，用 `u32` 是為了省空間與一致）：

| 欄位 | 型別 | 來源 |
|---|---|---|
| `q` 查詢 | `u32` | `Day.query` |
| `blocked` 攔截 | `u32` | `Day.blocked` |
| `servfail` 失敗 | `u32` | `Day.servfail` |
| `stale` 過期快取 | `u32` | `Day.stale` |
| `miss` 問上游 | `u32` | `Day.miss` |
| `p50`、`p95` 問上游的延遲（毫秒） | `u16` × 2 | `Day.lat_miss` 直方圖兩格之間的差，取百分位（`Histogram::percentile()`，`stats.rs:52`） |
| `abroad` 原本會出國的 CDN 回應 | `u32` | `Day.route` 各家的 `abroad` 加總 |
| `tw` 其中換成台灣的 | `u32` | `Day.route` 各家的 `acc` 加總（比率＝`tw ÷ abroad`） |

- 「平均延遲」用 `p50` 代替：直方圖沒有存總和，要平均就得在每筆查詢多加一次——不做。直方圖只有 12 個桶（0.5、1、2、5、10、20、50、100、200、500、1000 毫秒、以上），圖上是階梯狀的；夠不夠細等實測（Q11）。
- 記憶體：288 格 × 32 位元組 ≈ 9.2 KB，啟動時配置一次（`Box<[Slot; 288]>`），加一份「上一格結束時的累計值」（約 150 位元組）。記憶體控制不釋放它（固定而且很小）。
- 不進快照（`Stats::snapshot()`，`stats.rs:987`）：重新啟動清空；啟動後第一次 `with()` 把基準設成還原回來的 `Day` 累計值（不會出現一格「今天到目前為止的總和」）。
- 時鐘倒退、或跳了超過 288 格：清空環形陣列、基準重設（不補一整圈的 0）。

**介面**

- `/api/dashboard` 的 `history`（管理 API 才有，見 E8）；`/api/status?history=1` 也帶同一份（不帶參數時沒有這個欄位——LuCI 與韌體每幾秒讀一次 `/api/status`，不能每次多 6 KB）。`history=1` 落在 `rpcd.sh` 的 `valid_query()` 允許的字元裡。

### E10　ISP 群組（預設關）

**性質**：行為改變（開了才有）。**開關**：`community.shareIspGroup`（布林，預設 `false`；UCI `share_isp_group`）；關著時完全是現在的行為（不送、收到也不看）。

**做什麼**：開了之後，好友同步時多帶一個「ISP 群組」（`data/geo/tw-ip.json` 的群組 `id`，例如 `cht`；只到群組，不帶 IP）。收到的一方只用它決定**好友候選的驗證先後**：同群組的先驗，別群組的排後面、額度少。

**為什麼**：見 5.0——別家業者線路上量到的節點，在這條線路上有用的機率比較低；同一家業者的好友給的候選比較可能就是這條線到得了的。但這只是「先試誰」，**信任永遠來自本機驗證**。

**怎麼得知這台 WAN 的 ISP 群組**（查過的結果）

- 對外 IPv4：`spawn_wan_subnet()`（`app.rs:1220`）啟動時與 WAN 變動時向 Cloudflare 的 trace 讀對外 IP，把 /24 存在 `resolver.ecs_subnet`（`resolver.rs:196`）。這是已經有的偵測，不多發請求。
- 台灣 IP 資料：`Access::data()`（`ipfilter.rs:566`）拿到載入的 `TwIp`（`geo.rs:354`），每個 `Group` 有 `id` 與 `nets`（`geo.rs:344`）；`nets.contains(ip)`（`geo.rs:276`）就知道是哪一群。資料檔目前有 12 群（`cht`、`twm`、`fet`、`kbro`…、`other`）。
- 規則：`ecs_subnet` 落在某一群而且不是 `other` → 那一群的 `id`；偵測不到對外 IP、不在任何一群（國外、VPN）、落在 `other`、台灣 IP 資料讀不到 → **不帶**。結果在 `ecs_subnet` 或台灣 IP 資料變動時重算一次、存成一個字串。
- 路徑檢查、DDNS 都不需要：DDNS 沒開的機器很多，路徑檢查不查業者。串接中的下游量到的是上游的對外 IP，群組是對的（同一條線）。

**協定（向後相容）**

- 社群協定其實已經有「觀測者的網路」：`NetInfo { asn, colo }`（`envelope.rs:221`），放在身分文件的 `net` 與同步回應的 `ctx`（`envelope.rs:377`，規格 03 第 204 行）。**現況是主程式沒有實作 `DataProvider::net_ctx()`（`provider.rs:126` 的預設值），所以實際送出去的 `ctx` 是空的。** 3.5.0 不去補 `asn`、`colo`（那比群組更細）。
- `NetInfo` 加一個欄位：`isp: Option<String>`（`#[serde(default, skip_serializing_if = "Option::is_none")]`；最長 16 個字元，只能是小寫英數、`-`、`_`，不符就當沒有）。**只放在同步回應的 `ctx`**（`node.rs:1106`；只有已經是好友才拿得到），**身分文件的 `net` 不放**（`node.rs:431`；加好友之前對方就看得到）。
- 舊版：`NetInfo` 沒有 `deny_unknown_fields`，CBOR 多的欄位會被忽略；沒開的時候不序列化這個欄位，位元組跟現在完全一樣（`tests/vectors.rs` 的向量不用改）。新版收舊版：沒有 `isp` ＝不知道。

**怎麼用（只影響先後與額度，總量不增加）**

1. **網站提示的順序**：`collect_hints()`（`client.rs:1004`）現在依好友的資料品質分數排。開了之後，同群組好友給的 IP 排在前面，其餘照原本的順序。回傳幾個、驗證幾個都照舊（呼叫端原本就會截斷）。
2. **節點候選的額度**：`on_received()`（`community_bridge.rs:144`）交給 `add_friend_nodes()` 的每批上限，同群組與「不知道」的維持 `FRIEND_MAX_NODES`（500）；**確定是別群組**的降成四分之一（125）。只會變少，不會變多；候選名單的總上限（3,000）不變。「不知道」不降：舊版好友、沒開分享的好友不能因為這個功能被懲罰。
- 這台自己沒有群組（偵測不到）時兩項都不做。
- 自己報的群組可以亂填：最多是讓自己的候選先被驗證或多放幾個，驗證不過一樣不會用，資料品質分數照舊會扣（`score.rs`）。

**介面**

- 設定：`community.shareIspGroup`（預設 `false`）；UCI 的 `community` 區段要手動對應（`uci.rs` 的 `apply()`）；LuCI 的 `community.js`、`data/admin/fields.json` 各一個開關，說明寫清楚「開了之後好友會知道你用哪一家業者（群組），不含 IP」。

**上限與恢復**：一個字串；WAN 變動時重算；關掉開關後下一次同步就不送，對方的紀錄跟著好友資料的更新被蓋掉。

**MT7621**：沒有新的請求；群組判斷是一次區間查找，只在 WAN 變動時做。

**確認的現況**（`chain/client.rs:1551` 的 `upstream_json()`、`:1610` 的 `status_json()`、`chain/responder.rs:515` 的 `serving_json()`、`chain/grants.rs:220`）

- 往上：`upstream` 有 `address`、`nodeId`、`fingerprint`、`version`、`via`、`viaNat`、`since`、`lastOkAt`、`failures`，以及 `path`（更上層每一台的節點 ID，由近到遠）與 `depth`。

```json
"chain": { "self": { "nodeId": "…", "fingerprint": "…", "version": "3.5.0", "depth": 2 }, … }
```

- **不做**：下游的下游（要改登記協定，等真的畫圖時再定）；`path` 裡更上層的版本與位址（上游沒有給，也不該轉述）。

### 5.1 與既有功能的衝突檢查

| 對象 | 會不會衝突 | 結論 |
|---|---|---|
| **B1 相對評分**（`speed.rs`、`PoolNode.slow`） | B1 決定「同一家裡哪些節點算慢」；E5 看機房的失敗率、E6 看網段、E7 看網站 | 不重疊。E5／E6 都排在 B1 的結果之後（健檢排序只多兩個鍵），不改 `qscore`、`slow`、`speedRef`。E6 換上來的節點有延遲條件（1.5 倍＋5 毫秒），不會把 B1 判慢的節點換到前面——實作時 `spread_head()` 的候選要排除 `is_slow() == Some(true)` 的 |
| **B2 工作負載分數**（延後） | E7 用的 `request_ms()` 是 B2 的量測基礎之一 | 不衝突；B2 上線時 E7 的比較可以改用它，門檻另定 |
