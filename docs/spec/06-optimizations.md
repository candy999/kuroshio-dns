# 06 · 體驗優化：命中率、回台灣機率、速度

目標分三項，每項都要能量測，LuCI 狀態頁顯示數字，不靠感覺：

| 目標 | 指標 | 怎麼量 |
|---|---|---|
| 命中率 | 快取命中率、預取命中率 | `hit / query`；預取過的項目後來被用到的比例 |
| 回台灣機率 | 拉回台灣率 | CDN 連線裡「原本會出國、我們換回台灣」的比例（2.x 已有 `route` 統計） |
| 速度 | 回應時間 p50 / p95 | 分「快取命中」與「問上游」兩組，用固定區間的直方圖統計（不存每筆紀錄） |

狀態：✅ 已實作 · 🔜 階段 1 內完成 · 2️⃣ 階段 2（CDN）· 💡 研究中

## 1. 命中率

| # | 做法 | 狀態 | 說明 |
|---|---|---|---|
| 1.1 | **自適應預取** | ✅ | 2.x 只在剩 5 秒內、而且 10 分鐘內有人用過才預取。改成：剩餘時間 ≤ max(5 秒, 原始 TTL 的 10%)，而且（10 分鐘內有人用過，或累計被查過 3 次以上）就在背景更新。TTL 長的熱門網域會提早更新，不會等到最後 5 秒才搶 |
| 1.2 | **開機預熱** | ✅ | 定時把最常查的網域名稱（只存名稱與類型，不存答案）寫進快照 `hot-names.json`。重開機後慢慢重新查詢一遍（tiny 每秒 5 筆、其他每秒 20 筆），用戶第一次打開常用網站就是快取命中。份數依等級：tiny 200、small 500、standard 1,000、large 2,000；檔案只有幾 KB，跟著快照排程寫（Flash 上最少 6 小時一次） |
| 1.3 | **斷線時回舊資料（stale-if-error）** | ✅ | 2.x 過期超過 `serveStaleSec`（1 小時）就刪掉。改成保留到 `staleIfErrorSec`（預設 1 天，受快取上限約束）：平常照樣重新查詢，**只有所有上游都失敗時**才回舊資料（TTL 10 秒、附 EDE「Stale Answer」），不回 SERVFAIL。外網斷線、ISP DNS 故障時，常用網站還連得上 |
| 1.4 | 最低 TTL | 💡 | 有些網站給 TTL 0–30 秒，命中率很低。可以設最低 TTL，但會讓換 IP 的服務慢一點生效；CDN 置換過的、自己的網域不套用。預設不開 |
| 1.5 | 快取大小依記憶體 | ✅ | 規格 05 的等級預算；看門狗在記憶體不足時縮小快取 |

## 2. 速度

| # | 做法 | 狀態 | 說明 |
|---|---|---|---|
| 2.1 | **依實測延遲挑上游** | ✅ | 有 `parallel` 限制時（tiny / small），先問「平均延遲最低」的那幾個，不是照設定順序；每 20 次查詢有 1 次先問一個沒在前段的（探索），讓統計保持新鮮 |
| 2.2 | 快速回應 + 背景合併 | ✅ | 第一個正常回應先回，背景再合併所有上游的 IP 並測速（同 2.x） |
| 2.3 | singleflight | ✅ | 同一個名稱同時只問一次上游 |
| 2.4 | **回應時間統計** | ✅ | 快取命中 / 問上游分開，p50 / p95 顯示在 `/api/status`，優化有沒有效看得到 |
| 2.5 | 上游 UDP 連線重用 | 💡 | 每筆查詢開新的 UDP socket 會多幾次系統呼叫，但**來源埠隨機**是防 DNS 快取汙染（偽造回應）的重要防線：固定 socket 後只剩 16 位元的 id。要做就必須搭配 socket 定期輪替（每個最多 100 筆或 10 秒）與 0x20 大小寫隨機化補回隨機性，並在 MIPS 實機量到明顯效益才做。加密上游（DoT / DoH）已經是持久連線，建議優先用加密上游 |
| 2.6 | DoT / DoH 持久連線、管線化 / HTTP/2 多工、TLS session resumption | ✅ | 0-RTT 之後評估 |
| 2.7 | 沒有 IPv6 時快速回應 AAAA | 💡 | 偵測到路由器根本沒有 IPv6 對外連線時，AAAA 直接回空答案，裝置不用等。選項，預設關閉 |
| 2.8 | 快取命中免重新編碼 | 💡 | 實機量測後如果編碼成本明顯（MIPS），快取改存編好的封包，命中時只改 id 與 TTL |

## 3. 回台灣機率（階段 2，CDN 改寫）

2.x 已經有的：節點池（實測延遲、POP、下載速度）、每個網站 HTTPS 實際驗證、ECS 突破、跨 CDN 備援、HTTPS 記錄提示改寫、永久 IPv6 節點。3.0 在這些之上：

| # | 做法 | 說明 |
|---|---|---|
| 3.1 | **ECS 優先用自己 ISP 的網段** | 偵測 WAN 的公網 IP 與 ASN，ECS 先帶自己 ISP 的 /24，再試其他台灣 ISP 的網段。CDN 依網段決定節點，帶自己 ISP 的網段拿到的通常是跟自己 ISP 互連最好的節點。每家 CDN 記錄哪個網段成功率最高，下次直接用 |
| 3.2 | **尖峰時段的品質** | 海纜壅塞在晚上 8–11 點最明顯。節點池在尖峰時段也量測品質，計分時尖峰時段的權重加倍，避免挑到凌晨很快、晚上很塞的節點 |
| 3.3 | 熱門網站優先驗證 | 開機預熱（1.2）的名單也拿來優先驗證 CDN 網站，重開機後最常用的網站最快恢復「拉回台灣」 |
| 3.4 | 擴充 CDN 辨識 | 除了現有的幾家，加上 Akamai、Google、Bunny、騰訊 EdgeOne、阿里雲等的 CNAME 後綴與 IP 範圍；LuCI 列出「看起來像 CDN 但不認識」的 CNAME 後綴，方便新增 |
| 3.5 | 每個網站記住最好的策略 | 直接換節點 / ECS / 跨 CDN 哪一種成功，就記下來，之後直接用那一種，不必每次重新嘗試 |
| 3.6 | 社群共享 | 好友的驗證結果與節點當候選（規格 03），新網站更快找到可用的台灣節點 |
| 3.7 | 失敗偵測 | 💡 換過 IP 之後，如果同一台裝置在很短時間內一直重查同一個網站，可能是連不上；累計多次就暫停這個網站的置換、重新驗證。訊號有雜訊，先只記錄觀察 |
