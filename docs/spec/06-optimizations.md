# 06 · 體驗優化：命中率、回台灣機率、速度

目標分三項，每項都要能量測，LuCI 狀態頁顯示數字，不靠感覺：

| 目標 | 指標 | 怎麼量 |
|---|---|---|
| 命中率 | 快取命中率、預取命中率 | `hit / query`；預取過的項目後來被用到的比例 |
| 回台灣機率 | 拉回台灣率 | CDN 連線裡「原本會出國、我們換回台灣」的比例（2.x 已有 `route` 統計） |
| 速度 | 回應時間 p50 / p95 | 分「快取命中」與「問上游」兩組，用固定區間的直方圖統計（不存每筆紀錄） |

狀態：✅ 已實作 · 🔜 階段 1 內完成 · 2️⃣ 階段 2（CDN）· 💡 研究中

## 1. 命中率

| # | 做法 | 狀態 | 說明 |
|---|---|---|---|
| 1.1 | **自適應預取** | ✅ | 2.x 只在剩 5 秒內、而且 10 分鐘內有人用過才預取。改成：剩餘時間 ≤ max(5 秒, 原始 TTL 的 10%)，而且（10 分鐘內有人用過，或累計被查過 3 次以上）就在背景更新。TTL 長的熱門網域會提早更新，不會等到最後 5 秒才搶 |
| 1.2 | **開機預熱** | ✅ | 定時把最常查的網域名稱（只存名稱與類型，不存答案）寫進快照 `hot-names.json`。重開機後慢慢重新查詢一遍（依 CPU 核心數：單核每秒 5 筆、四核以上 20 筆），用戶第一次打開常用網站就是快取命中。最多 2,000 個名稱；檔案只有幾 KB，跟著快照排程寫（Flash 上最少 6 小時一次） |
| 1.3 | **斷線時回舊資料（stale-if-error）** | ✅ | 2.x 過期超過 `serveStaleSec`（1 小時）就刪掉。改成保留到 `staleIfErrorSec`（預設 1 天，受快取上限約束）：平常照樣重新查詢，**只有所有上游都失敗時**才回舊資料（TTL 10 秒、附 EDE「Stale Answer」），不回 SERVFAIL。外網斷線、ISP DNS 故障時，常用網站還連得上 |
| 1.4 | 最低 TTL | 💡 | 有些網站給 TTL 0–30 秒，命中率很低。可以設最低 TTL，但會讓換 IP 的服務慢一點生效；CDN 置換過的、自己的網域不套用。預設不開 |
| 1.5 | 快取大小依記憶體 | ✅ | 規格 09：系統有餘裕時長大，接近保留量停止長大，低於保留量縮小 |

## 2. 速度

| # | 做法 | 狀態 | 說明 |
|---|---|---|---|
| 2.1 | **依實測延遲挑上游** | ✅ | 有 `parallel` 限制時（單核 / 雙核的自動值），先問「平均延遲最低」的那幾個，不是照設定順序；每 20 次查詢有 1 次先問一個沒在前段的（探索），讓統計保持新鮮 |
| 2.2 | 快速回應 + 背景合併 | ✅ | 第一個正常回應先回，背景再合併所有上游的 IP 並測速（同 2.x） |
| 2.3 | singleflight | ✅ | 同一個名稱同時只問一次上游。**每個工作有總期限 12 秒**（3.5.1 H1，`JOB_DEADLINE`）：超過就放棄，等待的人回 SERVFAIL、鍵拿掉，下一筆重新問；`/api/status.perf.jobTimeouts` 計數，日誌每分鐘最多一行 WARN。以前沒有總期限，卡住的那一筆讓同名同類型的查詢一直跟著等到重新啟動 |
| 2.3a | 查詢路徑的 IP 測速不排隊 | ✅ | 3.5.1 H1（`IpRank::rank_now`）：快取裡沒有的 IP 要**一次拿到全部的測速名額**（`iprank.concurrency`）才測，拿不到就整筆不排序、照上游的順序回答（`perf.rankSkipped` 計數）；整體最多等 `iprank.timeoutMs` + 200 ms。以前查詢路徑跟背景工作一樣排隊等名額、沒有期限：每秒幾百個新網域時（D3 雙核心名額 16、每個最多 800 ms），排在後面的工作等上好幾分鐘，等待中的工作越積越多（記憶體跟著漲），Windows 上 DoH 處理中的名額被佔滿而回 `busy`。背景工作（CDN 節點延遲、ECS、跨 CDN）照舊排隊，它們本來就有自己的同時數上限 |
| 2.4 | **回應時間統計** | ✅ | 快取命中 / 問上游分開，p50 / p95 顯示在 `/api/status`，優化有沒有效看得到 |
| 2.5 | 上游 UDP 連線重用 | 💡 | 每筆查詢開新的 UDP socket 會多幾次系統呼叫，但**來源埠隨機**是防 DNS 快取汙染（偽造回應）的重要防線：固定 socket 後只剩 16 位元的 id。要做就必須搭配 socket 定期輪替（每個最多 100 筆或 10 秒）與 0x20 大小寫隨機化補回隨機性，並在 MIPS 實機量到明顯效益才做。加密上游（DoT / DoH）已經是持久連線，建議優先用加密上游 |
| 2.6 | DoT / DoH 持久連線、管線化 / HTTP/2 多工、TLS session resumption | ✅ | 0-RTT 之後評估 |
| 2.7 | 沒有 IPv6 時快速回應 AAAA | 💡 | 偵測到路由器根本沒有 IPv6 對外連線時，AAAA 直接回空答案，裝置不用等。選項，預設關閉 |
| 2.8 | 快取命中免重新編碼 | 💡 | 實機量測後如果編碼成本明顯（MIPS），快取改存編好的封包，命中時只改 id 與 TTL |

## 3. 回台灣機率（階段 2，CDN 改寫）

2.x 已經有的：節點池（實測延遲、POP、下載速度）、每個網站 HTTPS 實際驗證、ECS 突破、跨 CDN 備援、HTTPS 記錄提示改寫、永久 IPv6 節點。3.0 在這些之上：

| # | 做法 | 說明 |
|---|---|---|
| 3.1 | **ECS 優先用自己 ISP 的網段** | 偵測 WAN 的公網 IP 與 ASN，ECS 先帶自己 ISP 的 /24，再試其他台灣 ISP 的網段。CDN 依網段決定節點，帶自己 ISP 的網段拿到的通常是跟自己 ISP 互連最好的節點。每家 CDN 記錄哪個網段成功率最高，下次直接用 |
| 3.2 | **尖峰時段的品質** | 海纜壅塞在晚上 8–11 點最明顯。節點池在尖峰時段也量測品質，計分時尖峰時段的權重加倍，避免挑到凌晨很快、晚上很塞的節點 |
| 3.3 | 熱門網站優先驗證 | 開機預熱（1.2）的名單也拿來優先驗證 CDN 網站，重開機後最常用的網站最快恢復「拉回台灣」 |
| 3.4 | 擴充 CDN 辨識 | 除了現有的幾家，加上 Akamai、Google、Bunny、騰訊 EdgeOne、阿里雲等的 CNAME 後綴與 IP 範圍；LuCI 列出「看起來像 CDN 但不認識」的 CNAME 後綴，方便新增 |
| 3.5 | 每個網站記住最好的策略 | 直接換節點 / ECS / 跨 CDN 哪一種成功，就記下來，之後直接用那一種，不必每次重新嘗試 |
| 3.6 | 社群共享 | 好友的驗證結果與節點當候選（規格 03），新網站更快找到可用的台灣節點 |
| 3.7 | 失敗偵測 | 💡 換過 IP 之後，如果同一台裝置在很短時間內一直重查同一個網站，可能是連不上；累計多次就暫停這個網站的置換、重新驗證。訊號有雜訊，先只記錄觀察 |
| 3.8 | 輪流抽驗 | 「驗證通過」要 24 小時（`cdn.verifyOkHours`）才到期，期間節點健康、但某個網站開始不讓它服務（Cloudflare 1034）時會一路回壞節點。每小時除了即將到期的，再從「最近一天有換節點、上次驗證超過 1 小時」的網域抽「改寫中網域數 × `cdn.reverifyRatio`（0.02）」個（`cdn.reverifyMin` 5～`cdn.reverifyMax` 50）重新驗證，熱門 × 放越久的越先；失敗就跟判定過期一樣立刻改回原始結果。走原本的驗證併發上限 |

### 3.9 多來源 CDN 與第一層 CNAME（3.5.0，B3）

網站自己用 DNS 在多家 CDN 之間分流時，黑潮不把它硬綁在其中一家，也不替它選（`cdn.multiCdn`，預設開）。

**資料**（`db.rs`）

- 每個網域最多兩格：目前這一家（`provider`、`via`、`cname`、`c1`、`ips4`、`ips6`、`v4`、`v6`、`base`）與另一家（`src.alt`，同樣的欄位加 `last`）。跨 CDN（`cross4`）、ECS（`ecs`）、最佳策略（`best`）、手動策略不分業者，每個網域一份。
- `c1`：第一層 CNAME 的鍵＝查詢名稱的第一個 CNAME 目標取最後三段（`c1_key()`，最長 64 位元組）。直接放在網域紀錄上（共用字串）；`src`（防抖動狀態與另一格）只有看過第二家或第一層換過的網域才有，其他網域只佔一個指標。
- 目前這一格永遠是「最後回答的那一家」，所以改寫、驗證、健檢、複驗的程式都不用知道有兩格。背景的驗證寫結果時用 `Db::with_slot()` 寫回自己那一家的格子；那一家已經沒有格子就不寫、也不驗證。

**規則**（`Db::touch_at()`，每筆 CDN 回應一次，只有比較與指標對調，不配置）

| 情況 | 做什麼 | 上限 |
|---|---|---|
| 舊資料沒有 `c1` | 補上，不算變動、不算重要變動 | — |
| 回答的業者＝目前這一格 | 照常 | — |
| 回答的業者＝另一格 | 兩格對調（只算計數，不觸發寫入）。剛剛那一家 24 小時內才回答過 → 標成多來源（`multiAt`） | — |
| 回答的業者沒有格子 | 開一格（擠掉另一格裡的那一家），從試用期驗證；清掉 `cross4`、`ecs`、`best` | 每個網域 6 小時一次；超過的照原始答案回（`held`），不驗證 |
| 同一家、`c1` 是新的 | 連續 3 次、相隔 10 分鐘以上、中間沒有再看到舊的 → 確認，清掉 `cross4`、`ecs`、`best`，驗證結果留著 | 每個網域 6 小時清一次；24 小時內看過的鍵（最多記 3 個）不算新的 |
| 另一格 24 小時沒回答（不是多來源） | 定下來是「換家」，另一格丟掉 | — |
| 多來源 7 天沒有再輪流 | 取消多來源，另一格丟掉 | — |

- **不做跨 CDN**：多來源、或另一格還在（剛換家還沒定下來）的網域，不排探索、不用既有的跨 CDN 結果；探索開始時再看一次（排進佇列之後才變成多來源的也不連線）。
- **為什麼要看時間**：`apply()` 連快取命中都會走，同一份答案會重複出現，只算次數會被一份快取灌滿。
- **為什麼保留第二家的結果**（規格 11 的 Q5）：只留一家的話，兩家各半的網站有一半的回答是原始答案，而且每換一次就要重新驗證一次（重複做同一件事）。多來源網域占比很小，多一格（兩份驗證結果）的記憶體可以忽略。
- **風暴**：兩家輪流＝對調，零失效、零驗證；三家以上或一直換新的第一層＝每 6 小時最多一次。重新驗證走原本的佇列（同一個網域同時一個）與 `cdn.lite` 的每分鐘上限。

**App 層**（`providers.rs` 的 `app_layer`，`cdn.appLayer`）：由 App 或服務自己排程節點的業者（3.5.0：`google`、`apple`）只做辨識與統計，不改寫、不 ECS、不跨 CDN。手動策略優先：`never` 照舊，`always` 不受這個標記限制。只靠直接 A 記錄、不在任何 CDN 範圍裡的自有節點（例如影音服務自己的快取主機）本來就不會被辨識成 CDN，不在這個名單裡。

### 3.10 節點池測速的相對評分（3.5.0，B1）

程式：`crates/kuroshio-cdn/src/speed.rs`（全部是純函式）、`jobs/pool.rs`（階段 C 與 `build_nearest()`）、`pools.rs`（`qscore_rel()`、`PoolNode::is_slow()`）。開關 `pool.relativeSpeed`（預設開；關掉＝3.4.x）。

| 項目 | 3.4.x | 3.5.0 |
|---|---|---|
| 「幾乎一樣」（量到瓶頸） | 前 4 個都 ≥ 1 MB/s、差 ≤ 5% | 前 4 個量到速度的（> 0，且 ≥ 0.1 MB/s），差 ≤ 這 4 個樣本裡最大的誤差範圍 |
| 誤差範圍 | 固定 5% | `tolerance(秒) = clamp(0.05 + 0.035 ÷ √秒, 0.06, 0.18)`（3.5.0 F16 收緊；測試版是 `clamp(0.06 + 0.10 ÷ √秒, 0.08, 0.35)`） |
| 快測（1 MiB）通過 | ≥ 1 MB/s | ≥ `quick_ref × 0.5 × (1 − tolerance(快測的秒數))`；`quick_ref`＝前 4 個完整測的「前 1 MiB 速度」的中位數（F16）。量不到時退回 `min(參考 × 0.5, 1 MB/s) × (1 − 自己的誤差範圍)` |
| 「慢」 | 速度 < 1 MB/s | `速度 × (1 + 誤差範圍) < 參考 × 0.5`，或速度 < 0.1 MB/s；參考＝這一次量到速度的節點的中位數（至少 3 個） |
| 排序（一般 CDN） | 丟包 → 速度（數字大的在前）→ 延遲 | 丟包 → 速度的級別 → 延遲 |
| 品質分數（Fastly） | 慢的加 80 | 一樣加 80，慢不慢用上面的規則 |

- **速度的級別**：`floor(ln(最快 ÷ 速度) ÷ −ln(1 − 誤差範圍))`，誤差範圍取這一批量到的樣本裡最大的。第 0 級＝跟最快的分不出來。沒量到的 253、慢的 254。
- **快測跟「前 1 MiB」比**（3.5.0 F16）：1 MiB 大半在 TCP 慢啟動階段，量到的速度比完整測低很多（延遲越高越低，每一家 CDN 開頭的快慢也不一樣），不能直接跟「參考的一半」比。測試版用 1 MB/s 的上限補，但 CloudFront 快測 1.15 MB/s 對門檻 0.83 只剩 1.4 倍餘裕（D7 只剩 1.2 倍），誤差範圍一收緊就不夠。改成同類相比：`download_sample()` 在收到第 1 MiB 的那一刻多記一個時間（`SpeedSample.head_secs`；同一條連線、不多收任何東西），前 4 個完整測的樣本各有一個「前 1 MiB 的速度」，取中位數當 `quick_ref`（`/api/cdn/pools` 每家的 `quickRef`）。CloudFront：`quick_ref` 約 1.15 → 門檻約 0.52，餘裕 2.2 倍。`head_secs` 量不到（假的網路、檔案不到 1 MiB、舊資料）時照舊公式，`QUICK_CAP_MBPS` 只在這個退路裡用。
- **誤差範圍收緊**（3.5.0 F16，Q6 定案）：3.4.x 看到的「差 27%」是把 TTFB 算進速度造成的；3.5.0 的 `download_sample()` 從收到標頭之後才開始算。實測（同一個節點或同一級節點、不含 TTFB）：W3 Cloudflare 0.13 秒差 1～9%、CloudFront 1.5 秒差 4%、D7 Cloudflare／CloudFront 3.8 秒差 4～5%。新公式每一段都留實測最大差距的 1.5 倍以上：0.13 秒 0.147（原本 0.34）、0.5 秒 0.099、1.5 秒 0.079、3.8 秒 0.068。影響：瓶頸減量要前 4 個差在約 15% 以內才啟動（原本 34%；前 4 個裡有一個真的比較慢的節點就不啟動，流量最多回到 3.4.x 的水準）；差 15% 以上才算不同級；「慢」稍微容易成立。慢的比例 0.5、絕對下限 0.1 MB/s 不變。
- **被限流時**（3.5.0 F15）：`download_sample()` 回的樣本多 `status`（HTTP 狀態碼，0＝沒連上）。收到 429 或 503 時這一輪**對這一家 CDN 停止測速**（一次就停、不重試，WARN 一行）；其他失敗日誌印「沒量到（HTTP 403）」「沒量到（連線失敗）」。沒量到的節點 `speed` 留 `None`（兩種規則都一樣：新規則排在量到的後面、慢的前面；舊規則不再被當成「低於 1 MB/s」加 80 分）；上一輪有速度與 `slow` 的沿用（`speedAge` +1，最多 3 輪）：先找同一個 IP，沒有就找同一個 /24（每輪在每個 /24 裡隨機抽一個位址，只比 IP 幾乎沿用不到）；Fastly 這類最近節點型只停測、不沿用。`speedRef` 沒算出來時寫原因（`speedRefWhy`：「量到速度的節點只有 N 個（要 3 個）」「被限流（HTTP 429）」）。下一輪照排程自己恢復，只會少發請求。
- **儲存**：節點的 `slow`（布林）與 `sample`（`bytes`、`secs`、`connectMs`、`ttfbMs`、`quick`；3.5.0 F15、F16 多 `status`、`headSecs`）是 `PoolNode` 上的欄位，`speedRef`（與 `quickRef`、`speedRefWhy`）在業者的 `rest`。舊資料沒有 `slow`：沿用舊規則。參考速度每次節點池工作重算，不跨工作沿用；唯一的例外是被限流的那一輪（F15）：量到＋沿用的速度不到 3 個時用上一輪的 `speedRef`，`speedRefWhy` 寫「被限流（HTTP 429），沿用上一輪」。
- **流量**：每個節點最多一次 `download_sample()`（跟以前的 `download_speed()` 是同一條連線、同樣的上限）。
- **誤差範圍的係數**：Q6 依 W3、D7 的節點池日誌定案（上面的 F16）。
- **離線重播**（`tests/speed.rs` 的 `replay_*`，資料是 `data/seed/cdn-pools.json` 裡實機量到的節點池）：結果見 [11-v3.5.0.md](11-v3.5.0.md) 的 B1。

### 3.11 工作負載分數（草案；3.5.0 **還沒有啟用**，規格 11 的 B2）

長期目標：用「各類使用情境的預估完成時間」評節點，取代單一的「延遲＋懲罰」分數。**3.5.0 只做這一節的規格草案與量測基礎，不用它決定任何節點的名次**；分數本身排在 3.6，先收一輪實測資料。

**為什麼不在 3.5.0 上線**

- 分數一上線就會改變所有節點的名次，是 B 組裡風險最高的一項。
- 權重（「慢了多有感」）與參考工作負載的數字目前沒有實測依據，也還沒有人逐一核對出處。
- 3.5.0 才剛把速度的量法改掉（3.10 節）。兩個同時上線，分不出是誰造成的變化。

**量測基礎（3.5.0 已經有的，全部有上限、不多連線、不多收資料）**

| 量測值 | 來源 | 上限 | 存在哪裡 |
|---|---|---|---|
| RTT（TCP 連線時間）、抖動、丟包 | 既有的 `Net::quality()`（節點池工作、健檢） | 每次 3～10 個 SYN | 節點的 `ms`、`jitter`、`loss`（尖峰時段另存 `peakMs` 等） |
| 吞吐 | `Net::download_sample()` 的 `SpeedSample`（3.10 節） | 每個節點一次；8 MiB 或 `pool.speedSeconds` + 3 秒；量到瓶頸後 1 MiB；只測前 `pool.speedTop` 個（小機器 4 個） | 節點的 `speed`、`sample.bytes`、`sample.secs` |
| 連線＋握手 | 同一次下載：開始連線到可以送請求（HTTPS 含 TLS 握手，HTTP 只有 TCP） | 同上 | `sample.connectMs` |
| TTFB | 同一次下載：送出請求到收完回應標頭 | 同上 | `sample.ttfbMs` |
| 單一請求的分段時間 | `ProbeResult.timing`（`connect_ms`、`tls_ms`、`ttfb_ms`）：驗證、健檢、跨 CDN 探索用的 `https_probe()`／`http_probe()` 順便記 | 既有的探測，不多連線 | 跨 CDN 的 `score`／`origScore`（3.12 節）；其他探測目前不存 |

- 只有成功的回應才帶分段時間；失敗、逾時的是 0（「沒量到」），不能拿半套的數字評分。
- 量到的值從 `GET /api/cdn/pools`（每個節點的 `sample`）與節點池日誌的測速行收集。
- 已知的限制（定案前要處理）：
  - 測速的 `connectMs` 是 TCP 與 TLS 合在一起的；要分開得改 `download_sample()` 的連線方式（`ProbeResult.timing` 已經分開）。
  - 快測（`sample.quick`）的吞吐大半在 TCP 慢啟動階段，不能當吞吐用；它的 `connectMs`、`ttfbMs` 可以用。
  - 只有測過速度的節點（前 `speedTop` 個）才有樣本；其他節點只有 RTT、抖動、丟包。
  - 測速用的是各家固定的測速網址（`providers.rs` 的 `speed_url`），TTFB 反映的是那個檔案的來源與快取狀態，不同業者之間不能直接比，只能同一家的節點互相比。

**六類工作負載與估算模型（草案）**

完成時間都是「估計值」，只用來比較同一家的節點，不是保證。下表的數字**全部待人工核對出處**，核對之前不能寫進程式。

**分數怎麼合起來（草案）**

- `節點分數 = Σ 類別權重 × 類別的懲罰(預估完成時間)`，越低越好。
- `類別權重 = 本機查詢統計裡這一類的占比 × 這一類「慢了多有感」的係數`，每一類設上下限（草案 5%～40%〔沒有出處，要從實測決定〕），避免單一類別主導或被歸零。本機查詢統計只用既有的 `stats.rs` 彙總（依 CDN 業者與站台分類的計數），不新增每筆查詢的紀錄。
- 「慢了多有感」用門檻函式，不是線性：通話類延遲超過門檻才開始扣；串流類吞吐超過位元率就不再加分；瀏覽類在「良好」門檻以內差幾十毫秒不扣。
- 量測值的誤差範圍沿用 3.10 節的 `tolerance()`：分數差在誤差範圍內的節點算同一級，由延遲決定。

4. 不用下載吞吐評跨 CDN（要抓大檔，對網站是負擔）；跨 CDN 只用單一請求的分段時間（3.12 節）。

### 3.12 跨 CDN 的實測評分（3.5.0，B4）

`cross.rs` 的 `cross_explore()`。開關 `cdn.cross.requestScore`（預設開）。

- **原本的五個條件不變**：① 目標節點用這個網域做 HTTPS 探測成功（憑證相符）；② 回應確實是那一家；③ 不是錯誤頁；④ 跟原站是同一個網站；⑤ TCP 延遲比原站快 `cdn.nearestMinGainMs` 以上。
- **實測分數**＝`連線 + TLS 握手`（毫秒，`Timing::handshake_ms()`，跟 E7 第二版同一個函式；3.5.0 F13，Q6 定案）。① 的探測本來就做了，分段時間順便留下來；每一家取通過的節點裡最好的，原站用基準探測的。
  - 為什麼拿掉 TTFB（測試版是連線＋握手＋TTFB）：W11 唯一被拒絕的網站兩家都是 116 毫秒，實際用 curl 量 Cloudflare 台灣的握手 63 毫秒、原站 Fastly 108 毫秒，整頁 0.15 對 0.33 秒——TTFB 由原站決定、兩邊一樣，把握手的差距蓋掉了；同一次探索第一次與複測的分數差 17～62%，0.95／1.10 的門檻落在 TTFB 的雜訊裡。
  - 為什麼不是「握手＋前 N KB」：探測本來就讀最多 64 KB，但那只是 2～3 次來回，量到的跟握手是同一件事；動態頁邊產生邊送，又把原站的時間混回來。要量得出傳輸差別得抓幾百 KB 以上，等於對別人的網站做下載測試（原則 2）。
  - 不套用 E7 的台灣加權：那是「已經換到台灣，要不要退回」的偏向；這裡是「要不要換到另一家」，條件只能比 3.4.x 嚴。
  - 存檔的 `score`／`origScore` 意義換了：舊資料在下一次每日複驗時被新的值蓋掉；比較只發生在同一次探索內，新舊不互相比。
- **挑哪一家**：先留下 ⑤ 也通過的幾家，再挑分數最低的；跟最低的差在 10% 以內的幾家裡挑 TCP 延遲最低的。
- **再量一次**：第一名與原站各再探測一次，分數取比較小的（單次樣本雜訊大）。每次探索最多多 2 條連線；第二次失敗就用第一次的。
- **判斷**：`新的分數 ≤ 原站的分數 × 0.95` 才採用。現在正在用的那一家（複驗）放寬成 `× 1.10`（遲滯）。沒過記成失敗，原因「連線比較近，但握手沒有比較快」，`cdn.cross.failDays` 之後再試。
- **量不到分數**（探測沒有分段時間、其中一家沒有）：照 3.4.x 的規則（只看 TCP 延遲），不多探測。
- **只增不減**：新規則採用的一定也通過 3.4.x 的條件（⑤ 最低的那一家通過，才會有任何一家通過）。
- 0.95、1.10、10% 在 Q6 定案不變；等 W11 補做（至少 10 個網站、跑滿一天）確認每日複驗沒有來回。
- 跨 CDN 探索受 CDN 驗證的每分鐘名額管（3.5.0 F12）：每次算 1 個名額、排在重驗與問過 2 次以上的新網域之後；只問過 1 次的網域減量中不探索。
- 多來源網域不做跨 CDN（3.9 節）；通訊類網域不做跨 CDN（3.5.0 B6）；內建服務裡「不改寫」的四類（時間同步、連線偵測、憑證撤銷、地震速報）連驗證都不排（3.5.0 F11）。

**B11 重跑**（同一份資料、同樣的分類：IP 在範圍裡或 CNAME 認得＝已收錄）：「未收錄（有 CNAME）」從 159,550 個網域減到 134,818 個（−24,732，−15.5%）。依名單：台灣前 10 萬 200 → 170、台灣前 10 萬（第二次）53 → 44、台灣 50 萬級 2,856 → 2,505、50 萬級／Umbrella 55,209 → 45,465、Umbrella 99,288 → 84,723、新註冊網域 1,944 → 1,911。減少的裡面約 1 萬個是 Microsoft 365 的 `*-msedge.net`（Umbrella 為主）。

### 3.14 驗證失敗記在網站還是節點、業者專用 IP、原本就在台灣（3.5.1）

**K2：Fastly 節點反覆被暫停**。Windows 2 小時 44 分裡同樣幾個 Fastly 節點各被暫停 5～6 次；D3 壓測的系統記錄裡 Fastly「暫停使用」113 次，**109 次是在驗證 GitHub Pages 的網站**（`*.github.io` 與指到 `185.199.108.153`～`111.153` 的自訂網域），全部是 ECONNRESET；其他是 `linktr.ee`、`pinterest.ru` 這類少數網站。原因：

- Fastly 的範圍包含 GitHub 的 `185.199.108.0/22`（為了 GitHub 的下載、頭像這些走一般 Fastly 節點也可以用的服務），GitHub Pages 因此被認成 Fastly；但 GitHub Pages 只接受 GitHub 那幾個位址，拿節點池的節點去驗證一定被重設。
- 驗證時連不上一個節點就**馬上暫停那個節點**（保留最後一段的 Fastly 是暫停同網段的節點或整個 /24），30 分鐘後健檢（連業者自己的網站）通過就恢復，下一次驗證同一個網站又失敗——同一個節點一直被暫停又恢復，對其他網站是好的節點也被拉下來。

現在：

1. **業者專用 IP**（`providers.rs` 的 `dedicated_ip()`）：GitHub Pages 官方文件公布的四個 A（`185.199.108.153`～`185.199.111.153`）與四個 AAAA（`2606:50c0:8000::153`～`8003::153`）。答案全部是這些位址時照原本的答案，不驗證、不跨 CDN、不 ECS（`cdn.stats.dedicated`、`explain` 是 `dedicated-ip`；手動「一定換」照使用者的）。只有 Fastly 有這條規則，比的是幾個整數。
2. **網站的問題記在網站上**：一次驗證裡連不上（或憑證不符）的不同節點有 **3 個以上**、一個都沒通過，而且原本的 IP 連得上 → 記成這個網站的 `fail`（原因「試了 N 個台灣節點都連不上…這個網站可能只接受業者專用的 IP」），失敗次數照加、到期時間照一般失敗逐次拉長（6 → 12 → 24 小時…），不暫停任何節點。以前是「暫不判定、10 分鐘後再試」。
3. **節點的問題要看多個網站**：驗證時連不上不再馬上暫停節點，記下來；同一個節點 **1 小時內第 2 個不同的網站**也連不上才暫停（`pools.rs` 的 `note_conn_fail()`）。保留最後一段的 Fastly 以 /24 算（不同網站用的最後一段不同），到門檻時照舊暫停網段裡節點池的節點，沒有就暫停那個 /24。每家最多記 256 個節點，1 小時前的不算。原本的 IP 也連不上（多半是本機網路）時不記。
4. **同一個節點反覆被暫停時逐次加倍**：24 小時內第 n 次被驗證暫停，暫停 30 分鐘 × 2^(n−1)，最多 8 小時；暫停期間健檢通過也不恢復（健檢只證明節點對業者自己的網站可以用）；24 小時沒再發生就從 1 算；每家最多記 256 個。`/api/cdn/pools` 的節點多 `strikes`（次數）。
5. Fastly「每個網段都不服務這組憑證」的重找間隔從固定 1 小時改成 1、2、4…小時（不超過一般失敗的到期時間）。

**上限與恢復**：暫停最多 8 小時、紀錄每家最多 256 筆、1 小時與 24 小時的視窗都會自己過期；判斷錯的最壞情況是「某個網站暫時用原本的答案」或「某個節點晚一點才暫停」（健檢每 30 分鐘、Fastly 品質檢查每 5 分鐘照樣會把真的壞掉的節點拉下來）。

**原本的答案已經在台灣機房就不換**（Azure「台北換台北」）：7 個「比原本慢」的網域有 4 個是 Azure，原本的 POP 已經是 TPE，黑潮卻換成節點池裡另一個台北節點，握手反而慢（43.5 對 19.7、271 對 30.3 毫秒）。現在驗證時先探測原本的 IP（本來就有這一步），量到的 POP 已經是台灣機房、回應正常（狀態碼 500 以下、不像錯誤頁）就記成 `fail`＋`origTw`（POP），查詢路徑走既有的「驗證失敗 → 原始」；不加失敗次數、不算驗證失敗（`cdn.stats.origTw`）、不標壞節點、不再對候選節點一個一個連；`cdn.verifyFailHours`（預設 6 小時）後有人查再看一次（業者也可能把原本的答案改到國外）。範圍同 F9：IPv4、非最近節點型、不是手動「一定換」、`cdn.slowerFallback` 開著（關掉＝跟 3.5.0 一樣，驗證通過就換）。`explain` 是 `already-tw`（「驗證時原本的答案在 TPE」），`steps` 的 `v4` 多 `origTw`。

**explain 的「已是台灣」**：退回（F9「比原本慢」）到期之後，上游的答案已經是台灣節點時，以前一直說 `trial`「台灣節點還在驗證中（試用期先回原本的答案，TTL 10 秒）」，其實沒有在驗證、也沒有縮短 TTL——`explain` 只看存著的基準 POP（那是退回時量的國外 POP）。現在跟查詢路徑（`alias_family()`）一樣，用最近一次答案的 IP 在節點池裡的分類判斷（`Tw`／`Dead` 不換、`Global`／`Unknown` 才換）；這家的 IP 一個都沒有（舊資料）時才看存著的基準 POP。

### 3.15 長期資料檢查的修正（3.5.1）

一台 Windows、從 3.0.0 一路升級到 3.5.0 的機器，狀態資料檢查出的 CDN 問題（筆數上限的淘汰見規格 05 第 5.8 節）。

**M1：節點池每天整批換、驗證結果跟著失效**。05:30 的節點池工作把 Cloudflare、CloudFront v4 各 12 個、Azure 4 個節點全換掉；
網站的驗證結果只認節點池裡的 IP（`Pools::usable`），996 筆 v4 通過只有 1 筆的 IP 還在池裡，其他的查詢路徑先回原本的答案、
TTL 10 秒、排重新驗證——每天一次、對每個網站重驗一次。

- **前一輪還合格的節點優先留下**（`jobs::pool::sticky_pick`）：前一輪的節點這一輪也通過延遲、POP 檢查、不算慢，丟包不比新的前幾名差，
  延遲在新的前幾名最慢的那個的 115% 以內（`KEEP_MS_TOLERANCE`）→ 留著。還合格、但掉出容忍範圍的，每輪最多換掉前一輪節點數的 1/3
  （`REPLACE_DIVISOR`，排名最後的先換），幾輪之內換完、不會卡著；這一輪不合格的（連不上、不在台灣、不在候選裡）照換。
  日誌多一行「前一輪的 N 個節點留下 M 個」。只動 IP 置換型的 v4 節點池；v6 節點本來就永久保存，最近節點型（Fastly）照舊。
- **L8：決選的排在前面**。池子的 v4 節點 `speed` 全是 null（有 `speedRef`，但測過速的節點一個都沒進池子）：排序是「丟包 → 速度 → 延遲」，
  決選的 `poolSize × 2` 個用低並行重新量延遲與丟包，沒進決選的保留階段 A 的「0% 丟包」。重新量的時候只要有一次連線失敗
  （Windows 剛量完上千個候選、本機的連接埠還沒釋放時很常見），就排到所有沒重新量、也沒測過速的節點後面。
  現在決選（測過速、重新量過）的先排，沒進決選的只在不夠時補。
- **explain 跟查詢路徑一致**：`rewritten` 要驗證過的 IP 現在還能用（`Cdn::verified_ips`，`serve_pool` 也改用它：仍在節點池、沒被暫停；
  保留最後一段的 CDN 還要最後一段跟這次答案一樣）。都不能用時是新的代碼 `pool-changed`
  「驗證過的節點已不在節點池，下次查詢重新驗證（這段期間先回原本的答案，TTL 10 秒）」。

**M2：v4／v6 共用 `base`**。驗證時用原本的 IP 連一次記成基準（`base`：IP、POP、狀態碼），但 v6 驗證也寫同一格，把 `base.ip` 蓋成 IPv6；
`Domain::orig_ip(4)` 優先用 `base.ip`，每小時複驗、輪流抽驗、查詢路徑重驗都拿 IPv6 當 v4 的原本 IP，3.5.1 的「原本就在台灣不換」
因此拿 IPv6 量到的 TPE 判 v4 不換。現在：

- 基準只給 v4：v6 驗證不寫 `base`（`Db::set_base` 收到 IPv6 也不寫）。v6 的基準沒有任何地方用到（統計、explain 都只看 v4）。
- `orig_ip(4)` 只接受 IPv4 的基準 IP（`Domain::base_ip4`），否則用最近一次的 A；驗證時原本的 IP 家族不對就不探測基準。
- 舊資料裡 IPv6 的 `base.ip` 給 v4 當成沒有（相容）；載入時的清理見下面的 L1／L2。

**M3：每小時複驗只驗真的有在用的**（`Cdn::recheck`）。以前條件是「3 天內出現過＋通過＋1 小時內到期」，大量只問過一次的網域
每天被重驗一次。現在還要 `best` 是換節點（`Alias`，真的有在改寫）或問過 2 次以上；只問過一次的網域到期就讓它到期，
下次有人查時照一般流程（試用期、驗證）。輪流抽驗（第 3.8 節）本來就只抽 `best = Alias` 的，不變。

**L13：另一家的那一格也複驗**。多來源網域（第 3.9 節）另一家的驗證結果（`src.alt.v4`／`v6`）以前不會複驗，回答換回那一家時
常常已經過期、掉回試用期。現在同樣的條件（`best = Alias` 或問過 2 次以上、那一家最後回答在 3 天內、通過、1 小時內到期）也排複驗
（`Task::Verify` 帶那一家的名稱，驗證器照 `slot_of` 寫回那一格；原本的 IP 用那一格的 v4 基準或最近一次的 A／AAAA）。

**M4：單一節點的問題不記在網站上**。CloudFront 102 筆 `fail` 都是「HTTP 421 Misdirected（試了 2 個網段）」而且是同一個 IP；
Cloudflare 66 筆「錯誤 1xxx（試了 1 個網段）」。「不服務這個網站」（`zone_kind`：421、Cloudflare 錯誤 1xxx、CloudFront Distribution）
以前只寫相容性紀錄（`zone_note`），網站照記失敗（6、12、24 小時…）。現在比照 K2（第 3.14 節）：

- 回「不服務這個網站」的節點記下來（`Pools::note_conn_fail`，跟連不上共用同一份紀錄）：同一個節點 1 小時內對第 2 個不同的網站也這樣
  才暫停，反覆的逐次加倍（30 分鐘起、最多 8 小時）。保留最後一段的 CDN（Fastly）不算：那是網段的憑證組，照舊由 `zone_note` 處理。
- 候選不到 3 個（`SITE_FAIL_NODES`）、都回「不服務這個網站」：分不出是網站還是那一兩個節點的問題，**不記在網站上**——記 `unknown`
  （原因「…（只有 N 個候選節點，先不記在網站上）」），不加失敗次數。
- 候選 3 個以上都這樣：網站的問題，照舊記 `fail`，不記到節點上。
- `unknown` 的重試（這裡與其他「暫時無法判定」共用，`Cdn::unsure`）：10 分鐘後有人查再驗證，連續幾次就加倍（10、20、40、80、160 分鐘，
  `UNSURE_RETRY_MS`、`UNSURE_MAX_SHIFT`；次數記在驗證結果的 `extra.unsure`），驗證有結論（通過或失敗）時歸零。
  以前固定 10 分鐘：一直分不出來的網站每 10 分鐘重驗一次。

**M5：explain 跟查詢路徑一致**（`explain.rs` 的 `decide` 照 `alias_family()` 的順序判斷，共用 `Cdn::nearest_gain`、`Cdn::verified_ips`）：

- **最近節點型（Fastly）**：v4 通過、`best` 是換節點、查詢路徑有在換，explain 以前一律回 `no-tw-node`。現在照查詢路徑：最近的節點
  明顯比原本快（`cdn.nearestMinGainMs`，用測速快取與節點池的紀錄，不發請求）而且驗證過的節點還能用 → 新代碼 `nearest`
  「已經換成驗證過、比原本快的最近節點」；原本的答案已經夠近 → `no-tw-node`（「原本的答案已經是最近的節點」）。
- **節點池建過、但一個節點都沒有**（Gcore v4／v6 都是 0 個、`Pools::has()` 是 true）：查詢路徑直接回原本的答案、不縮短 TTL、不排驗證，
  explain 以前說「驗證中，TTL 10 秒」。現在是 `no-pool`（「這台的 X 台灣節點池目前沒有可用的節點，先用原本的答案」）；
  最近節點型而且是多來源時是 `multi-cdn`（它回台灣只能靠跨 CDN）。
- **多來源**：另一家的那一格（`src.alt`，7 天內回答過）也算一次決定，放在 `alt`（`provider`、`providerLabel`、`decision`、`text`、
  `lastSeen`、`steps`）；兩格的決定不同時，`text` 後面接「回答來自 B 時：…」。以前只看目前這一格，例如這一格是只辨識的業者
  就說「只辨識不改寫」，回答換成另一家時查詢路徑其實會換。

**L1／L2：舊資料清理**（`Cdn::clean_stale_learning`，載入時一次；有清才記一行 info，寫清掉幾筆）。這些假的學習資料會讓 `has_learning()`
誤判（筆數上限、記憶體控制都把它們當成有學習資料），也會讓複驗、explain 用錯資料：

| 清掉什麼 | 條件 |
|---|---|
| 那一格的 v4／v6／基準 | App 層（只辨識、不改寫）的業者；手動「一定換」、`cdn.appLayer: false` 的不動。3.5.0 B3 以前驗證過留下來的 |
| 基準（`base`） | IP 是 IPv6（M2），或不在這一格業者的官方範圍裡（那家有範圍檔時才比） |
| ECS、跨 CDN 結果 | 到期超過 7 天（`STALE_LEARNING_MS`）：早就不用了，查詢路徑本來就會重做 |
| `best` | 指向已經不成立的策略：`ecs`／`cross` 但那個結果沒有或不是 ok；`alias` 但 v4、v6 都沒有驗證結果 |

多來源網域的另一格照前兩列。清掉的網域標成重要變動（分片要重寫）；第二次啟動沒有東西可以清。附帶的種子網域資料也會被清
（3,958 筆裡有 521 筆的基準是 IPv6、1,290 筆 ECS 與 836 筆跨 CDN 結果早就過期）；種子檔本身不改。

**L3：相容性紀錄（`cdn/ip-zone.json`）的「特定產品專用」不會消退、同一個網站重複算**。`Pools::is_restricted` 是「不服務 2 次以上、
而且超過服務的 2 倍」，但同一個網站每驗證一次就多算一次，幾次重驗就把節點當成特定產品專用（排到最後），而且永遠不會消退
（那台機器 375 筆，347 筆是 Fastly）。現在：

- 「不服務」算**不同的網站**（`Pools::zone_note_site`：每筆記最多 8 個網站名稱的雜湊 `sites`，同一個網站重複失敗只算一次）。
  「服務」照舊每次加一。
- 記最後一次「不服務」的時間（`missAt`）；7 天沒有新的（`ZONE_MISS_KEEP_MS`）就把 `miss` 清掉，也沒有「服務」的整筆拿掉
  （`Pools::decay_zone`：載入時一次、之後每小時跟複驗一起，不在查詢路徑上）。舊資料沒有 `missAt` 時看 `at`。
- 檔案格式只多兩個選填欄位，舊版讀到會原封保留。

**L4：本機通訊端的錯誤不是網站或節點的結論**。Windows 壓測後的資料裡有「os error 10048」（位址已在使用中：連接埠用完）、
「os error 10055」（緩衝不足）被記成網站的驗證失敗、跨 CDN 的「原站無法用 HTTPS 連線」（6 小時）。現在：

- `kuroshio-net` 的錯誤分類多認得 `EADDRINUSE`、`ENOBUFS`、`EMFILE`、`ENFILE`（照各作業系統的錯誤號碼：Windows 10048／10049／10055／10024、
  Linux、MIPS 的 Linux 號碼不同、BSD／macOS），`probe::is_local_error()` 也認得舊版寫下來的原始文字（`os error 10048` 之類）。
- 驗證：原本的 IP 就是本機的錯誤 → 這一輪什麼都判斷不了；候選是本機的錯誤 → 不算「連不上的節點」（不記到節點上、不湊「3 個節點都連不上」）。
  一個都沒通過時記 `unknown`、10 分鐘起逐次拉長後重試（同 M4 的 `unsure`），不加失敗次數。
- 跨 CDN 探索：原站或候選是本機的錯誤、一家都沒通過 → 記 `unknown`、10 分鐘後有人查再探索（`Cdn::note_cross_local`），
  不寫 `none`（6 小時）或 `fail`（好幾天）。
