# 06 · 體驗優化：命中率、回台灣機率、速度

目標分三項，每項都要能量測，LuCI 狀態頁顯示數字，不靠感覺：

| 目標 | 指標 | 怎麼量 |
|---|---|---|
| 命中率 | 快取命中率、預取命中率 | `hit / query`；預取過的項目後來被用到的比例 |
| 回台灣機率 | 拉回台灣率 | CDN 連線裡「原本會出國、我們換回台灣」的比例（2.x 已有 `route` 統計） |
| 速度 | 回應時間 p50 / p95 | 分「快取命中」與「問上游」兩組，用固定區間的直方圖統計（不存每筆紀錄） |

## 1. 命中率

| # | 做法 | 狀態 | 說明 |
|---|---|---|---|
| 1.1 | **自適應預取** | ✅ | 2.x 只在剩 5 秒內、而且 10 分鐘內有人用過才預取。改成：剩餘時間 ≤ max(5 秒, 原始 TTL 的 10%)，而且（10 分鐘內有人用過，或累計被查過 3 次以上）就在背景更新。TTL 長的熱門網域會提早更新，不會等到最後 5 秒才搶 |
| 1.2 | **開機預熱** | ✅ | 定時把最常查的網域名稱（只存名稱與類型，不存答案）寫進快照 `hot-names.json`。重開機後慢慢重新查詢一遍（依 CPU 核心數：單核每秒 5 筆、四核以上 20 筆），用戶第一次打開常用網站就是快取命中。最多 2,000 個名稱；檔案只有幾 KB，跟著快照排程寫（Flash 上最少 6 小時一次） |
| 1.3 | **斷線時回舊資料（stale-if-error）** | ✅ | 2.x 過期超過 `serveStaleSec`（1 小時）就刪掉。改成保留到 `staleIfErrorSec`（預設 1 天，受快取上限約束）：平常照樣重新查詢，**只有所有上游都失敗時**才回舊資料（TTL 10 秒、附 EDE「Stale Answer」），不回 SERVFAIL。外網斷線、ISP DNS 故障時，常用網站還連得上 |
| 1.4 | 最低 TTL | 💡 | 有些網站給 TTL 0–30 秒，命中率很低。可以設最低 TTL，但會讓換 IP 的服務慢一點生效；CDN 置換過的、自己的網域不套用。預設不開 |
| 1.5 | 快取大小依記憶體 | ✅ | 規格 09：系統有餘裕時長大，接近保留量停止長大，低於保留量縮小 |

## 2. 速度

| # | 做法 | 狀態 | 說明 |
|---|---|---|---|
| 2.1 | **依實測延遲挑上游** | ✅ | 有 `parallel` 限制時（單核 / 雙核的自動值），先問「平均延遲最低」的那幾個，不是照設定順序；每 20 次查詢有 1 次先問一個沒在前段的（探索），讓統計保持新鮮 |
| 2.2 | 快速回應 + 背景合併 | ✅ | 第一個正常回應先回，背景再合併所有上游的 IP 並測速（同 2.x） |
| 2.3 | singleflight | ✅ | 同一個名稱同時只問一次上游 |
| 2.4 | **回應時間統計** | ✅ | 快取命中 / 問上游分開，p50 / p95 顯示在 `/api/status`，優化有沒有效看得到 |
| 2.5 | 上游 UDP 連線重用 | 💡 | 每筆查詢開新的 UDP socket 會多幾次系統呼叫，但**來源埠隨機**是防 DNS 快取汙染（偽造回應）的重要防線：固定 socket 後只剩 16 位元的 id。要做就必須搭配 socket 定期輪替（每個最多 100 筆或 10 秒）與 0x20 大小寫隨機化補回隨機性，並在 MIPS 實機量到明顯效益才做。加密上游（DoT / DoH）已經是持久連線，建議優先用加密上游 |
| 2.6 | DoT / DoH 持久連線、管線化 / HTTP/2 多工、TLS session resumption | ✅ | 0-RTT 之後評估 |
| 2.7 | 沒有 IPv6 時快速回應 AAAA | 💡 | 偵測到路由器根本沒有 IPv6 對外連線時，AAAA 直接回空答案，裝置不用等。選項，預設關閉 |
| 2.8 | 快取命中免重新編碼 | 💡 | 實機量測後如果編碼成本明顯（MIPS），快取改存編好的封包，命中時只改 id 與 TTL |

## 3. 回台灣機率（階段 2，CDN 改寫）

2.x 已經有的：節點池（實測延遲、POP、下載速度）、每個網站 HTTPS 實際驗證、ECS 突破、跨 CDN 備援、HTTPS 記錄提示改寫、永久 IPv6 節點。3.0 在這些之上：

| # | 做法 | 說明 |
|---|---|---|
| 3.1 | **ECS 優先用自己 ISP 的網段** | 偵測 WAN 的公網 IP 與 ASN，ECS 先帶自己 ISP 的 /24，再試其他台灣 ISP 的網段。CDN 依網段決定節點，帶自己 ISP 的網段拿到的通常是跟自己 ISP 互連最好的節點。每家 CDN 記錄哪個網段成功率最高，下次直接用 |
| 3.2 | **尖峰時段的品質** | 海纜壅塞在晚上 8–11 點最明顯。節點池在尖峰時段也量測品質，計分時尖峰時段的權重加倍，避免挑到凌晨很快、晚上很塞的節點 |
| 3.3 | 熱門網站優先驗證 | 開機預熱（1.2）的名單也拿來優先驗證 CDN 網站，重開機後最常用的網站最快恢復「拉回台灣」 |
| 3.4 | 擴充 CDN 辨識 | 除了現有的幾家，加上 Akamai、Google、Bunny、騰訊 EdgeOne、阿里雲等的 CNAME 後綴與 IP 範圍；LuCI 列出「看起來像 CDN 但不認識」的 CNAME 後綴，方便新增 |
| 3.5 | 每個網站記住最好的策略 | 直接換節點 / ECS / 跨 CDN 哪一種成功，就記下來，之後直接用那一種，不必每次重新嘗試 |
| 3.6 | 社群共享 | 好友的驗證結果與節點當候選（規格 03），新網站更快找到可用的台灣節點 |
| 3.7 | 失敗偵測 | 💡 換過 IP 之後，如果同一台裝置在很短時間內一直重查同一個網站，可能是連不上；累計多次就暫停這個網站的置換、重新驗證。訊號有雜訊，先只記錄觀察 |
| 3.8 | 輪流抽驗 | 「驗證通過」要 24 小時（`cdn.verifyOkHours`）才到期，期間節點健康、但某個網站開始不讓它服務（Cloudflare 1034）時會一路回壞節點。每小時除了即將到期的，再從「最近一天有換節點、上次驗證超過 1 小時」的網域抽「改寫中網域數 × `cdn.reverifyRatio`（0.02）」個（`cdn.reverifyMin` 5～`cdn.reverifyMax` 50）重新驗證，熱門 × 放越久的越先；失敗就跟判定過期一樣立刻改回原始結果。走原本的驗證併發上限 |

### 3.9 多來源 CDN 與第一層 CNAME（3.5.0，B3）

網站自己用 DNS 在多家 CDN 之間分流時，黑潮不把它硬綁在其中一家，也不替它選（`cdn.multiCdn`，預設開）。

**資料**（`db.rs`）

- 每個網域最多兩格：目前這一家（`provider`、`via`、`cname`、`c1`、`ips4`、`ips6`、`v4`、`v6`、`base`）與另一家（`src.alt`，同樣的欄位加 `last`）。跨 CDN（`cross4`）、ECS（`ecs`）、最佳策略（`best`）、手動策略不分業者，每個網域一份。
- `c1`：第一層 CNAME 的鍵＝查詢名稱的第一個 CNAME 目標取最後三段（`c1_key()`，最長 64 位元組）。直接放在網域紀錄上（共用字串）；`src`（防抖動狀態與另一格）只有看過第二家或第一層換過的網域才有，其他網域只佔一個指標。
- 目前這一格永遠是「最後回答的那一家」，所以改寫、驗證、健檢、複驗的程式都不用知道有兩格。背景的驗證寫結果時用 `Db::with_slot()` 寫回自己那一家的格子；那一家已經沒有格子就不寫、也不驗證。

**規則**（`Db::touch_at()`，每筆 CDN 回應一次，只有比較與指標對調，不配置）

| 情況 | 做什麼 | 上限 |
|---|---|---|
| 舊資料沒有 `c1` | 補上，不算變動、不算重要變動 | — |
| 回答的業者＝目前這一格 | 照常 | — |
| 回答的業者＝另一格 | 兩格對調（只算計數，不觸發寫入）。剛剛那一家 24 小時內才回答過 → 標成多來源（`multiAt`） | — |
| 回答的業者沒有格子 | 開一格（擠掉另一格裡的那一家），從試用期驗證；清掉 `cross4`、`ecs`、`best` | 每個網域 6 小時一次；超過的照原始答案回（`held`），不驗證 |
| 同一家、`c1` 是新的 | 連續 3 次、相隔 10 分鐘以上、中間沒有再看到舊的 → 確認，清掉 `cross4`、`ecs`、`best`，驗證結果留著 | 每個網域 6 小時清一次；24 小時內看過的鍵（最多記 3 個）不算新的 |
| 另一格 24 小時沒回答（不是多來源） | 定下來是「換家」，另一格丟掉 | — |
| 多來源 7 天沒有再輪流 | 取消多來源，另一格丟掉 | — |

- **不做跨 CDN**：多來源、或另一格還在（剛換家還沒定下來）的網域，不排探索、不用既有的跨 CDN 結果；探索開始時再看一次（排進佇列之後才變成多來源的也不連線）。
- **為什麼要看時間**：`apply()` 連快取命中都會走，同一份答案會重複出現，只算次數會被一份快取灌滿。
- **為什麼保留第二家的結果**（規格 11 的 Q5）：只留一家的話，兩家各半的網站有一半的回答是原始答案，而且每換一次就要重新驗證一次（重複做同一件事）。多來源網域占比很小，多一格（兩份驗證結果）的記憶體可以忽略。
- **風暴**：兩家輪流＝對調，零失效、零驗證；三家以上或一直換新的第一層＝每 6 小時最多一次。重新驗證走原本的佇列（同一個網域同時一個）與 `cdn.lite` 的每分鐘上限。

**App 層**（`providers.rs` 的 `app_layer`，`cdn.appLayer`）：由 App 或服務自己排程節點的業者（3.5.0：`google`、`apple`）只做辨識與統計，不改寫、不 ECS、不跨 CDN。手動策略優先：`never` 照舊，`always` 不受這個標記限制。只靠直接 A 記錄、不在任何 CDN 範圍裡的自有節點（例如影音服務自己的快取主機）本來就不會被辨識成 CDN，不在這個名單裡。
