# 06 · 體驗優化：命中率、回台灣機率、速度

目標分三項，每項都要能量測，LuCI 狀態頁顯示數字，不靠感覺：

| 目標 | 指標 | 怎麼量 |
|---|---|---|
| 命中率 | 快取命中率、預取命中率 | `hit / query`；預取過的項目後來被用到的比例 |
| 回台灣機率 | 拉回台灣率 | CDN 連線裡「原本會出國、我們換回台灣」的比例（2.x 已有 `route` 統計） |
| 速度 | 回應時間 p50 / p95 | 分「快取命中」與「問上游」兩組，用固定區間的直方圖統計（不存每筆紀錄） |

狀態：✅ 已實作 · 🔜 階段 1 內完成 · 2️⃣ 階段 2（CDN）· 💡 研究中

## 1. 命中率

| # | 做法 | 狀態 | 說明 |
|---|---|---|---|
| 1.1 | **自適應預取** | ✅ | 2.x 只在剩 5 秒內、而且 10 分鐘內有人用過才預取。改成：剩餘時間 ≤ max(5 秒, 原始 TTL 的 10%)，而且（10 分鐘內有人用過，或累計被查過 3 次以上）就在背景更新。TTL 長的熱門網域會提早更新，不會等到最後 5 秒才搶 |
| 1.2 | **開機預熱** | ✅ | 定時把最常查的網域名稱（只存名稱與類型，不存答案）寫進快照 `hot-names.json`。重開機後慢慢重新查詢一遍（依 CPU 核心數：單核每秒 5 筆、四核以上 20 筆），用戶第一次打開常用網站就是快取命中。最多 2,000 個名稱；檔案只有幾 KB，跟著快照排程寫（Flash 上最少 6 小時一次） |
| 1.3 | **斷線時回舊資料（stale-if-error）** | ✅ | 2.x 過期超過 `serveStaleSec`（1 小時）就刪掉。改成保留到 `staleIfErrorSec`（預設 1 天，受快取上限約束）：平常照樣重新查詢，**只有所有上游都失敗時**才回舊資料（TTL 10 秒、附 EDE「Stale Answer」），不回 SERVFAIL。外網斷線、ISP DNS 故障時，常用網站還連得上 |
| 1.4 | 最低 TTL | 💡 | 有些網站給 TTL 0–30 秒，命中率很低。可以設最低 TTL，但會讓換 IP 的服務慢一點生效；CDN 置換過的、自己的網域不套用。預設不開 |
| 1.5 | 快取大小依記憶體 | ✅ | 規格 09：系統有餘裕時長大，接近保留量停止長大，低於保留量縮小 |

## 2. 速度

| # | 做法 | 狀態 | 說明 |
|---|---|---|---|
| 2.1 | **依實測延遲挑上游** | ✅ | 有 `parallel` 限制時（單核 / 雙核的自動值），先問「平均延遲最低」的那幾個，不是照設定順序；每 20 次查詢有 1 次先問一個沒在前段的（探索），讓統計保持新鮮 |
| 2.2 | 快速回應 + 背景合併 | ✅ | 第一個正常回應先回，背景再合併所有上游的 IP 並測速（同 2.x） |
| 2.3 | singleflight | ✅ | 同一個名稱同時只問一次上游 |
| 2.4 | **回應時間統計** | ✅ | 快取命中 / 問上游分開，p50 / p95 顯示在 `/api/status`，優化有沒有效看得到 |
| 2.5 | 上游 UDP 連線重用 | 💡 | 每筆查詢開新的 UDP socket 會多幾次系統呼叫，但**來源埠隨機**是防 DNS 快取汙染（偽造回應）的重要防線：固定 socket 後只剩 16 位元的 id。要做就必須搭配 socket 定期輪替（每個最多 100 筆或 10 秒）與 0x20 大小寫隨機化補回隨機性，並在 MIPS 實機量到明顯效益才做。加密上游（DoT / DoH）已經是持久連線，建議優先用加密上游 |
| 2.6 | DoT / DoH 持久連線、管線化 / HTTP/2 多工、TLS session resumption | ✅ | 0-RTT 之後評估 |
| 2.7 | 沒有 IPv6 時快速回應 AAAA | 💡 | 偵測到路由器根本沒有 IPv6 對外連線時，AAAA 直接回空答案，裝置不用等。選項，預設關閉 |
| 2.8 | 快取命中免重新編碼 | 💡 | 實機量測後如果編碼成本明顯（MIPS），快取改存編好的封包，命中時只改 id 與 TTL |

## 3. 回台灣機率（階段 2，CDN 改寫）

2.x 已經有的：節點池（實測延遲、POP、下載速度）、每個網站 HTTPS 實際驗證、ECS 突破、跨 CDN 備援、HTTPS 記錄提示改寫、永久 IPv6 節點。3.0 在這些之上：

| # | 做法 | 說明 |
|---|---|---|
| 3.1 | **ECS 優先用自己 ISP 的網段** | 偵測 WAN 的公網 IP 與 ASN，ECS 先帶自己 ISP 的 /24，再試其他台灣 ISP 的網段。CDN 依網段決定節點，帶自己 ISP 的網段拿到的通常是跟自己 ISP 互連最好的節點。每家 CDN 記錄哪個網段成功率最高，下次直接用 |
| 3.2 | **尖峰時段的品質** | 海纜壅塞在晚上 8–11 點最明顯。節點池在尖峰時段也量測品質，計分時尖峰時段的權重加倍，避免挑到凌晨很快、晚上很塞的節點 |
| 3.3 | 熱門網站優先驗證 | 開機預熱（1.2）的名單也拿來優先驗證 CDN 網站，重開機後最常用的網站最快恢復「拉回台灣」 |
| 3.4 | 擴充 CDN 辨識 | 除了現有的幾家，加上 Akamai、Google、Bunny、騰訊 EdgeOne、阿里雲等的 CNAME 後綴與 IP 範圍；LuCI 列出「看起來像 CDN 但不認識」的 CNAME 後綴，方便新增 |
| 3.5 | 每個網站記住最好的策略 | 直接換節點 / ECS / 跨 CDN 哪一種成功，就記下來，之後直接用那一種，不必每次重新嘗試 |
| 3.6 | 社群共享 | 好友的驗證結果與節點當候選（規格 03），新網站更快找到可用的台灣節點 |
| 3.7 | 失敗偵測 | 💡 換過 IP 之後，如果同一台裝置在很短時間內一直重查同一個網站，可能是連不上；累計多次就暫停這個網站的置換、重新驗證。訊號有雜訊，先只記錄觀察 |
| 3.8 | 輪流抽驗 | 「驗證通過」要 24 小時（`cdn.verifyOkHours`）才到期，期間節點健康、但某個網站開始不讓它服務（Cloudflare 1034）時會一路回壞節點。每小時除了即將到期的，再從「最近一天有換節點、上次驗證超過 1 小時」的網域抽「改寫中網域數 × `cdn.reverifyRatio`（0.02）」個（`cdn.reverifyMin` 5～`cdn.reverifyMax` 50）重新驗證，熱門 × 放越久的越先；失敗就跟判定過期一樣立刻改回原始結果。走原本的驗證併發上限 |

### 3.9 多來源 CDN 與第一層 CNAME（3.5.0，B3）

網站自己用 DNS 在多家 CDN 之間分流時，黑潮不把它硬綁在其中一家，也不替它選（`cdn.multiCdn`，預設開）。

**資料**（`db.rs`）

- 每個網域最多兩格：目前這一家（`provider`、`via`、`cname`、`c1`、`ips4`、`ips6`、`v4`、`v6`、`base`）與另一家（`src.alt`，同樣的欄位加 `last`）。跨 CDN（`cross4`）、ECS（`ecs`）、最佳策略（`best`）、手動策略不分業者，每個網域一份。
- `c1`：第一層 CNAME 的鍵＝查詢名稱的第一個 CNAME 目標取最後三段（`c1_key()`，最長 64 位元組）。直接放在網域紀錄上（共用字串）；`src`（防抖動狀態與另一格）只有看過第二家或第一層換過的網域才有，其他網域只佔一個指標。
- 目前這一格永遠是「最後回答的那一家」，所以改寫、驗證、健檢、複驗的程式都不用知道有兩格。背景的驗證寫結果時用 `Db::with_slot()` 寫回自己那一家的格子；那一家已經沒有格子就不寫、也不驗證。

**規則**（`Db::touch_at()`，每筆 CDN 回應一次，只有比較與指標對調，不配置）

| 情況 | 做什麼 | 上限 |
|---|---|---|
| 舊資料沒有 `c1` | 補上，不算變動、不算重要變動 | — |
| 回答的業者＝目前這一格 | 照常 | — |
| 回答的業者＝另一格 | 兩格對調（只算計數，不觸發寫入）。剛剛那一家 24 小時內才回答過 → 標成多來源（`multiAt`） | — |
| 回答的業者沒有格子 | 開一格（擠掉另一格裡的那一家），從試用期驗證；清掉 `cross4`、`ecs`、`best` | 每個網域 6 小時一次；超過的照原始答案回（`held`），不驗證 |
| 同一家、`c1` 是新的 | 連續 3 次、相隔 10 分鐘以上、中間沒有再看到舊的 → 確認，清掉 `cross4`、`ecs`、`best`，驗證結果留著 | 每個網域 6 小時清一次；24 小時內看過的鍵（最多記 3 個）不算新的 |
| 另一格 24 小時沒回答（不是多來源） | 定下來是「換家」，另一格丟掉 | — |
| 多來源 7 天沒有再輪流 | 取消多來源，另一格丟掉 | — |

- **不做跨 CDN**：多來源、或另一格還在（剛換家還沒定下來）的網域，不排探索、不用既有的跨 CDN 結果；探索開始時再看一次（排進佇列之後才變成多來源的也不連線）。
- **為什麼要看時間**：`apply()` 連快取命中都會走，同一份答案會重複出現，只算次數會被一份快取灌滿。
- **為什麼保留第二家的結果**（規格 11 的 Q5）：只留一家的話，兩家各半的網站有一半的回答是原始答案，而且每換一次就要重新驗證一次（重複做同一件事）。多來源網域占比很小，多一格（兩份驗證結果）的記憶體可以忽略。
- **風暴**：兩家輪流＝對調，零失效、零驗證；三家以上或一直換新的第一層＝每 6 小時最多一次。重新驗證走原本的佇列（同一個網域同時一個）與 `cdn.lite` 的每分鐘上限。

**App 層**（`providers.rs` 的 `app_layer`，`cdn.appLayer`）：由 App 或服務自己排程節點的業者（3.5.0：`google`、`apple`）只做辨識與統計，不改寫、不 ECS、不跨 CDN。手動策略優先：`never` 照舊，`always` 不受這個標記限制。只靠直接 A 記錄、不在任何 CDN 範圍裡的自有節點（例如影音服務自己的快取主機）本來就不會被辨識成 CDN，不在這個名單裡。

### 3.10 節點池測速的相對評分（3.5.0，B1）

程式：`crates/kuroshio-cdn/src/speed.rs`（全部是純函式）、`jobs/pool.rs`（階段 C 與 `build_nearest()`）、`pools.rs`（`qscore_rel()`、`PoolNode::is_slow()`）。開關 `pool.relativeSpeed`（預設開；關掉＝3.4.x）。

| 項目 | 3.4.x | 3.5.0 |
|---|---|---|
| 「幾乎一樣」（量到瓶頸） | 前 4 個都 ≥ 1 MB/s、差 ≤ 5% | 前 4 個量到速度的（> 0，且 ≥ 0.1 MB/s），差 ≤ 這 4 個樣本裡最大的誤差範圍 |
| 誤差範圍 | 固定 5% | `tolerance(秒) = clamp(0.06 + 0.10 ÷ √秒, 0.08, 0.35)` |
| 快測（1 MiB）通過 | ≥ 1 MB/s | ≥ `min(參考 × 0.5, 1 MB/s) × (1 − 自己的誤差範圍)` |
| 「慢」 | 速度 < 1 MB/s | `速度 × (1 + 誤差範圍) < 參考 × 0.5`，或速度 < 0.1 MB/s；參考＝這一次量到速度的節點的中位數（至少 3 個） |
| 排序（一般 CDN） | 丟包 → 速度（數字大的在前）→ 延遲 | 丟包 → 速度的級別 → 延遲 |
| 品質分數（Fastly） | 慢的加 80 | 一樣加 80，慢不慢用上面的規則 |

- **速度的級別**：`floor(ln(最快 ÷ 速度) ÷ −ln(1 − 誤差範圍))`，誤差範圍取這一批量到的樣本裡最大的。第 0 級＝跟最快的分不出來。沒量到的 253、慢的 254。
- **為什麼快測有 1 MB/s 的上限**：1 MiB 大半在 TCP 慢啟動階段，量到的速度比完整測低很多（延遲越高越低），不能直接跟「參考的一半」比，否則快的線路上正常的節點會被標成慢。
- **儲存**：節點的 `slow`（布林）與 `sample`（`bytes`、`secs`、`connectMs`、`ttfbMs`、`quick`）是 `PoolNode` 上的欄位，`speedRef` 在業者的 `rest`。舊資料沒有 `slow`：沿用舊規則。參考速度每次節點池工作重算，不跨工作沿用。
- **流量**：每個節點最多一次 `download_sample()`（跟以前的 `download_speed()` 是同一條連線、同樣的上限）。
- **誤差範圍的係數是暫定的**（規格 11 的 Q6）：等老毛子 D3 與 Windows 的節點池日誌（每個節點的位元組數、傳輸時間、速度）回歸之後再定案。
- **離線重播**（`tests/speed.rs` 的 `replay_*`，資料是 `data/seed/cdn-pools.json` 裡實機量到的節點池）：結果見 [11-v3.5.0.md](11-v3.5.0.md) 的 B1。

### 3.11 工作負載分數（草案；3.5.0 **還沒有啟用**，規格 11 的 B2）

長期目標：用「各類使用情境的預估完成時間」評節點，取代單一的「延遲＋懲罰」分數。**3.5.0 只做這一節的規格草案與量測基礎，不用它決定任何節點的名次**；分數本身排在 3.6，先收一輪實測資料。

**為什麼不在 3.5.0 上線**

- 分數一上線就會改變所有節點的名次，是 B 組裡風險最高的一項。
- 權重（「慢了多有感」）與參考工作負載的數字目前沒有實測依據，也還沒有人逐一核對出處。
- 3.5.0 才剛把速度的量法改掉（3.10 節）。兩個同時上線，分不出是誰造成的變化。

**量測基礎（3.5.0 已經有的，全部有上限、不多連線、不多收資料）**

| 量測值 | 來源 | 上限 | 存在哪裡 |
|---|---|---|---|
| RTT（TCP 連線時間）、抖動、丟包 | 既有的 `Net::quality()`（節點池工作、健檢） | 每次 3～10 個 SYN | 節點的 `ms`、`jitter`、`loss`（尖峰時段另存 `peakMs` 等） |
| 吞吐 | `Net::download_sample()` 的 `SpeedSample`（3.10 節） | 每個節點一次；8 MiB 或 `pool.speedSeconds` + 3 秒；量到瓶頸後 1 MiB；只測前 `pool.speedTop` 個（小機器 4 個） | 節點的 `speed`、`sample.bytes`、`sample.secs` |
| 連線＋握手 | 同一次下載：開始連線到可以送請求（HTTPS 含 TLS 握手，HTTP 只有 TCP） | 同上 | `sample.connectMs` |
| TTFB | 同一次下載：送出請求到收完回應標頭 | 同上 | `sample.ttfbMs` |
| 單一請求的分段時間 | `ProbeResult.timing`（`connect_ms`、`tls_ms`、`ttfb_ms`）：驗證、健檢、跨 CDN 探索用的 `https_probe()`／`http_probe()` 順便記 | 既有的探測，不多連線 | 跨 CDN 的 `score`／`origScore`（3.12 節）；其他探測目前不存 |

- 只有成功的回應才帶分段時間；失敗、逾時的是 0（「沒量到」），不能拿半套的數字評分。
- 量到的值從 `GET /api/cdn/pools`（每個節點的 `sample`）與節點池日誌的測速行收集。
- 已知的限制（定案前要處理）：
  - 測速的 `connectMs` 是 TCP 與 TLS 合在一起的；要分開得改 `download_sample()` 的連線方式（`ProbeResult.timing` 已經分開）。
  - 快測（`sample.quick`）的吞吐大半在 TCP 慢啟動階段，不能當吞吐用；它的 `connectMs`、`ttfbMs` 可以用。
  - 只有測過速度的節點（前 `speedTop` 個）才有樣本；其他節點只有 RTT、抖動、丟包。
  - 測速用的是各家固定的測速網址（`providers.rs` 的 `speed_url`），TTFB 反映的是那個檔案的來源與快取狀態，不同業者之間不能直接比，只能同一家的節點互相比。

**六類工作負載與估算模型（草案）**

完成時間都是「估計值」，只用來比較同一家的節點，不是保證。下表的數字**全部待人工核對出處**，核對之前不能寫進程式。

| 類別 | 模型（草案） | 主要受什麼影響 | 參考數字（待人工核對出處） |
|---|---|---|---|
| 瀏覽 | 連線數 ×（連線＋握手）＋ 來回輪數 × TTFB ＋ 大小 ÷ 有效吞吐；有效吞吐在慢啟動階段受 RTT 限制 | RTT、握手、TTFB | 一頁約 2 MB、數十個請求、約 6 條連線〔待人工核對出處：HTTP Archive Web Almanac 的 Page Weight、HTTP 章節〕；「良好」的門檻 LCP 2.5 秒〔待人工核對出處：Web Vitals〕 |
| 購物 | 瀏覽 ＋ N 次小的 API 來回（每次約 RTT ＋ TTFB） | RTT、TTFB、抖動 | 互動回應 200 毫秒〔待人工核對出處：Web Vitals 的 INP〕；N 沒有出處，要從實測決定 |
| 社群 | 連續的小請求（RTT ＋ TTFB）＋ 圖片／短片分段（大小 ÷ 吞吐） | RTT、抖動、吞吐（中） | 分段大小、每分鐘請求數沒有出處，要從實測決定 |
| 串流 | 啟動時間（連線＋握手＋TTFB＋第一個分段 ÷ 吞吐）；之後看吞吐能不能撐住位元率，撐不住就降畫質 | 吞吐（有門檻，超過就沒差）、丟包 | 高畫質約 5 Mbps、4K 約 25 Mbps〔待人工核對出處：各串流服務公開的建議頻寬〕；品質模型〔待人工核對出處：ITU-T P.1203 系列〕 |
| 大檔 | 大小 ÷ 吞吐 | 吞吐、丟包 | 吞吐與 RTT／丟包的關係〔待人工核對出處：Mathis 等人的 TCP 吞吐公式、RFC 6349〕 |
| 通訊 | 訊息來回（RTT）、通話的延遲與抖動 | RTT、抖動、丟包（最敏感） | 通話單向延遲 150 毫秒以內〔待人工核對出處：ITU-T G.114〕；服務品質分類〔待人工核對出處：ITU-T G.1010〕 |

**分數怎麼合起來（草案）**

- `節點分數 = Σ 類別權重 × 類別的懲罰(預估完成時間)`，越低越好。
- `類別權重 = 本機查詢統計裡這一類的占比 × 這一類「慢了多有感」的係數`，每一類設上下限（草案 5%～40%〔沒有出處，要從實測決定〕），避免單一類別主導或被歸零。本機查詢統計只用既有的 `stats.rs` 彙總（依 CDN 業者與站台分類的計數），不新增每筆查詢的紀錄。
- 「慢了多有感」用門檻函式，不是線性：通話類延遲超過門檻才開始扣；串流類吞吐超過位元率就不再加分；瀏覽類在「良好」門檻以內差幾十毫秒不扣。
- 量測值的誤差範圍沿用 3.10 節的 `tolerance()`：分數差在誤差範圍內的節點算同一級，由延遲決定。

### 3.12 跨 CDN 的實測評分（3.5.0，B4）

`cross.rs` 的 `cross_explore()`。開關 `cdn.cross.requestScore`（預設開）。

- **原本的五個條件不變**：① 目標節點用這個網域做 HTTPS 探測成功（憑證相符）；② 回應確實是那一家；③ 不是錯誤頁；④ 跟原站是同一個網站；⑤ TCP 延遲比原站快 `cdn.nearestMinGainMs` 以上。
- **實測分數**＝一個請求的 `連線 + TLS 握手 + TTFB`（毫秒，`ProbeResult.timing`）。① 的探測本來就做了，分段時間順便留下來；每一家取通過的節點裡最好的，原站用基準探測的。
- **挑哪一家**：先留下 ⑤ 也通過的幾家，再挑分數最低的；跟最低的差在 10% 以內的幾家裡挑 TCP 延遲最低的。
- **再量一次**：第一名與原站各再探測一次，分數取比較小的（單次樣本雜訊大）。每次探索最多多 2 條連線；第二次失敗就用第一次的。
- **判斷**：`新的分數 ≤ 原站的分數 × 0.95` 才採用。現在正在用的那一家（複驗）放寬成 `× 1.10`（遲滯）。沒過記成失敗，原因「連線比較近，但整個請求沒有比較快」，`cdn.cross.failDays` 之後再試。
- **量不到分數**（探測沒有分段時間、其中一家沒有）：照 3.4.x 的規則（只看 TCP 延遲），不多探測。
- **只增不減**：新規則採用的一定也通過 3.4.x 的條件（⑤ 最低的那一家通過，才會有任何一家通過）。
- 0.95、1.10、10% 是暫定的（規格 11 的 Q6：等 Windows W11 的實測）。
- 多來源網域不做跨 CDN（3.9 節）；通訊類網域不做跨 CDN（3.5.0 B6）。
