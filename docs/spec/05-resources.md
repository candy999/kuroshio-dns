# 05 · 資源預算：記憶體、Flash 寫入、CPU

很多 ARM / MIPS 路由器只有 128–512 MB RAM、16–256 MB Flash，CPU 也慢。
這份規格定下三件事的平衡點：**重要資料不能丟、Flash 不能被寫壞、DNS 回應不能變慢**。沒有硬體等級：
記憶體與儲存空間都是「有空就大方用、別人要用時讓出來」（[09](09-memory.md)、第 5.6 節），跟 CPU 有關的值依核心數換算（第 7 節）。

## 1. 沒有硬體等級（動態調整）

以前依 `MemTotal` 分 tiny / small / standard / large 四級，每級一份固定的大小（`profiles.json`）。現在拿掉了：

- **記憶體**：依系統可用記憶體與**系統保留量**動態決定（[09](09-memory.md)）。設定裡的大小只是防濫用的安全上限，所有機器一樣。
- **CPU**：並行數之類在 `defaults.json` 寫 `"auto"`，載入時依 CPU 核心數換算（第 7 節）。
- **儲存空間**：依**儲存保留量**大方使用（第 5.6 節）。
- 設定合併順序：**內建預設值 → 使用者設定 → `"auto"` 換算**。使用者寫了的數字一律以使用者為準。
- 舊的 `system.profile` / `system.tier` / `system.memoryBudgetMB` 接受、不使用（啟動時記一筆說明）。
- `kuroshio sysinfo` 印出偵測結果、記憶體保留量、儲存保留量、依核心數換算的值。

## 2. 最低需求

| | 最低 | 建議 | 全部功能 |
|---|---|---|---|
| 記憶體 | 128 MB | 256 MB | 512 MB 以上 |
| Flash | 16 MB（安裝後剩 4 MB 以上） | 32 MB 以上或 NAND | 128 MB 以上，或外接儲存 |
| CPU | MIPS 24Kc 單核 ~575 MHz | 雙核（MT7621 880 MHz、Cortex-A53） | ARMv8 四核、x86 |
| OpenWrt | 24.10 | 24.10 / 25.12 | |

最低硬體上能用的功能：區網 DNS、快取、預設清單過濾、CDN 台灣節點置換（驗證與節點池，不掃描網段）、每日上游評測（縮小規模）。
DoH / DoT / DoQ / DoH3、社群共享、大型清單都可以開：記憶體夠時就用，接近保留量時依序讓出（連線數收緊、清單放不下的不載入，見第 6 節與 09）。
`system.allowHeavy` 已經沒有作用（接受、不使用）。

## 3. 記憶體

### 3.1 記憶體怎麼分配

沒有固定預算。記憶體結構在系統可用記憶體 ≥ 保留量 + 遲滯時才長大，低於保留量時依 09 的階梯讓出，最低到「純轉送」：

| 結構 | 安全上限（所有機器一樣） | 動態 |
|---|---|---|
| DNS 快取 | `resolver.cacheMax` 100,000 筆 | 接近保留量停止長大；吃緊縮到 1/4；只轉送時 64 筆 |
| 過濾清單 | `filter.maxDomains` 1,000 萬條 | 載入前依「保留量以上的空間」估計，放不下的不載入；不足時一次停用一份 |
| CDN 網域資料庫 | `cdn.maxEntries` 20 萬筆（磁碟上的總筆數） | 冷資料移到磁碟（查到時讀回）；只轉送時整個移到磁碟 |
| 排行、日誌、到站紀錄 | 2 萬 / 500 行 / 5 萬個 IP | 吃緊時縮小；接近保留量時到站紀錄 5 千個就換代 |
| 好友資料 | `community.maxBundleMB` 32 MB | 也不超過保留量以上空間的 1/4 |
| 加密連線 | 依核心數（第 7 節） | 接近保留量時新連線最多 32 條；不足時暫不接受新的加密連線 |

實測清單大小（2026-11）：預設啟用的 10 份合計約 37 萬條（去重後 37 萬個網域；3.1 以前的預設 7 份約 13 萬條）；其中 HaGeZi TIF 精簡版 19 萬條；HaGeZi TIF 完整版 105 萬條（原始檔 23 MB）；FutaGuard 新註冊網域 51 萬條。

### 3.2 做法

- **過濾清單用緊湊結構**：網域存成 64 位元雜湊的排序陣列（每筆 8 bytes）＋分類 / 清單編號（1 byte）。比對時對查詢名稱的每一層上層網域做二分搜尋。
  - 37 萬條約 3.3 MB；HaGeZi TIF 完整版 105 萬條約 9.5 MB。2.x 的 node 版要 800 MB 以上。
  - 64 位元雜湊在 1,000 萬筆時，每次比對誤判的機率約 1.8 兆分之一，可以忽略；「命中哪一條規則」的文字在使用者查詢時才回頭去清單裡找。
  - 正規表示式、萬用字元、修飾詞這類複雜規則另外存（`filter.maxComplex` 2 萬條；其中每次查詢都要跑的 `filter.maxUnindexed` 依核心數）。
  - 實作註記（`crates/kuroshio-filter`）：1 byte 只放分類（2 位元）＋清單編號（6 位元，最多 64 份清單）；精確 / 子網域、放行 / 封鎖、`$important` 三個旗標放在雜湊的低 3 位元（實際比對 61 位元，誤判機率仍可忽略）。清單層命中時的規則文字直接由命中的網域還原（同 2.x 的格式），不必回頭讀清單；自訂規則與複雜規則保留原始文字。預算以「規則數（未去重）」依序累計，跟 LuCI 用上次下載的規則數預估一致。建置時的暫存陣列每條 16 bytes，尖峰約為暫存＋最終結構（HaGeZi TIF 完整版 105 萬條：常駐 9 MB、建置尖峰約 19 MB；預設 10 份：常駐約 3.3 MB，3.1 以前的預設 7 份約 1.3 MB）。
- **串流下載與解析**：清單邊下載邊解析，不把整個檔案放進記憶體（23 MB 的 HaGeZi 不會先吃掉 23 MB）。
- **更新時的尖峰**：新結構建好才換掉舊的，尖峰是新舊兩份並存；每份清單逐一處理，不同時展開。
- **超過安全上限**：依使用者排列的順序載入；累計超過 `filter.maxDomains` 的清單不載入，記一條警告並在 LuCI 顯示。自訂規則永遠載入。
- **記憶體監看與控制**（[09](09-memory.md)，預設開啟）：依系統保留量分成寬裕 / 吃緊 / 不足（離保留量近時每 2–3 秒量一次，
  Linux 有 PSI 時當提早訊號），依序釋出診斷緩衝、DNS 快取、CDN 冷資料、（真的不足時）優先順序最低的過濾清單，
  最深到「純轉送」；寬裕後依相反順序恢復。接近保留量時背景工作延後、記憶體結構停止長大。
- **OOM 分數**：Linux 上 `oom_score_adj` = -500（`system.oomScoreAdj`），記憶體用完時核心不優先停掉 DNS（09 第 6 節）。
- **執行緒**：單核心用單執行緒 runtime（省下每條執行緒的堆疊與排程成本），多核心最多 4 條。

## 4. CPU

- **熱路徑不配置記憶體**：快取命中只做一次雜湊查找與複製；目標在 MT7621 上快取命中 p50 < 2 ms。
- **上游並行數依核心數**（`resolver.parallel`，`"auto"` 時）：

  | CPU | 同時問幾個上游 |
  |---|---|
  | 單核心 | 2 個（300 ms 沒回應再加問下一個） |
  | 雙核心 | 3 個 |
  | 四核心以上 | 全部（同 2.x） |

  每多問一個上游就多一倍封包與加密成本。
- **IP 測速、CDN 驗證、評測、掃描的同時數依核心數**（第 7 節的表）。
- **加密**：
  - MIPS 和沒有 AES 指令的 ARM，TLS 優先用 ChaCha20-Poly1305（比 AES-GCM 快好幾倍）。
  - 憑證預設 ECDSA P-256（acme `ec-256`），握手比 RSA 快。
  - TLS session resumption 與長時間保持連線，減少完整握手的次數。
- **背景工作不搶 DNS**：一次只跑一個工作，切成小段、每段之間讓出 CPU；清單解析也一樣。目標：任何背景工作期間，DNS 回應延遲增加 < 50 ms。
- **重的工作排在半夜**：網段掃描（`cdn-scan`）每週一次；記憶體接近保留量時延後（不再依等級停用）。

## 5. Flash 寫入

### 5.1 原則

Flash 的每個區塊能抹寫的次數有限：NOR 約 10 萬次，便宜的 SPI-NAND 可能只有幾千次。jffs2 / ubifs 每次寫入至少動到一整個抹除區塊（64–128 KB），所以**「頻繁的小寫入」比「偶爾的大寫入」傷得多**。

維護者的原則：「盡量保護 Flash 壽命，但該寫的還是要寫。資料最久多久沒存就一定要存，要有明確的上限。依照使用量走——不能因為怕傷裝置就不敢用功能。」

1. **常變動、可以重建的資料只放記憶體**（`/tmp`，也就是 RAM）。
2. **有價值、變動慢的資料定時寫回 Flash**，而且內容沒變就不寫。
3. **設定類資料只在使用者操作時寫**。
4. **少寫位元組才是真正的保護**：大檔壓縮、CDN 網域資料庫分片、只重寫有變動的分片、只有計數變動不單獨觸發寫入。
5. 每天的寫入量是「節奏目標」，超過就延後；但**有變動的資料最久 `system.persistMaxAgeHours`（預設 24 小時）一定寫出**，路由器常斷電也不會一連好幾天沒存。
6. 筆數上限由記憶體決定，不由 Flash 決定（09）。
7. 儲存空間有餘裕時，可重建、可省略的資料大方留著（第 5.6 節）；空間吃緊時依序刪掉。

### 5.2 資料分類

| 類別 | 資料 | 放哪裡 | 何時寫 Flash |
|---|---|---|---|
| 設定 | UCI、自訂規則、社群金鑰、憑證、評測名單 | `/etc/kuroshio/`、`/etc/config/kuroshio` | 只有使用者操作或憑證續期時 |
| 重要狀態 | 台灣節點池、永久 IPv6 節點、CDN 網站驗證紀錄、上游評測結果、社群好友 | 記憶體；快照在 `/etc/kuroshio/state/` | 定時快照（5.3）＋正常關機 |
| 可重建 | 統計、查詢紀錄、事件紀錄、DNS 快取、IP 測速結果 | 只在記憶體 | 不寫（統計跟著重要狀態的快照一起存當日累計） |
| 本機副本（可省略） | 過濾清單原文（zstd） | 儲存空間在保留量 + 遲滯以上、記憶體也還能長大時，存在 `filter-lists/` | 內容變了才寫，跟著快照節奏（5.3） |
| 暫存 | 鎖、背景工作中間檔 | `/tmp/kuroshio/` | 不寫 |

- 有本機副本時：開機先用副本建好過濾器（不必等下載），1 分鐘後問上游有沒有更新（大多 304，不重建）；記憶體控制停用 / 恢復清單時也用副本；
  下載失敗時拿副本頂著。沒有副本（空間不夠、第一次）就照舊下載。預設 10 份清單壓縮後約 3.7 MB（原文約 11 MB），內容通常一天變一次。

### 5.3 快照規則

- **寫入方式**：先寫暫存檔、`fsync`、改名，斷電不會留下半個檔案。
- **內容沒變不寫**：比對內容雜湊。
- **最短間隔**（同一個檔兩次寫入之間；`system.persistIntervalMin` = 0 時自動）：

  | 儲存類型 | 預設 | 跟著記憶體（只有 `flash` 且自動時） |
  |---|---|---|
  | `flash` | 6 小時 | 保留量以上還有 ≥ 256 MB → 最久未存上限（24 小時）；≥ 96 MB → 上限的一半（12 小時）；其他 → 預設 |
  | `disk` | 10 分鐘 | — |
  | `ram` | 10 分鐘（重開機會遺失，啟動時警告） | — |

  記憶體越多、變動留在記憶體越久：寫得越少，同一筆資料的多次變動合併成一次寫入，短命、沒用的資料在寫出之前就被淘汰。
  記憶體吃緊時反過來：偏低（保留量 + 遲滯以內）最多 1 小時、不足（低於保留量一半）下一輪（5 分鐘內）就寫，寫完把記憶體裡的待寫內容放掉；
  `Critical` 時也不受每日寫入目標限制。使用者自己設定的間隔不跟著記憶體拉長。一律不超過最久未存上限。
  實作：`persist::effective_interval(policy, mem)`，純函式、有單元測試。
- **最久未存**（`system.persistMaxAgeHours`，預設 24，`flash` 上 1–24）：每個檔記下「第一次出現還沒寫出的變動」的時間；
  超過上限就不管今天寫了多少、不管最短間隔，一定寫出，並記一筆 info（檔名、多久沒存、寫了多少 bytes）。`disk` / `ram` 照舊：最短間隔一到就寫。
- **每日寫入目標**：預設 4 MB（`system.flashWriteBudgetKB`），只算 `flash`，以磁碟上（壓縮後）的大小計。
  是節奏目標：沒超過就照最短間隔寫；超過就延後——但不超過最久未存上限。
- **只有計數的變動**：CDN 網域的查詢次數、最後出現時間不單獨觸發寫入。分片因為別的原因要寫時順便帶上；
  不然等到最久未存上限才寫（斷電最多少掉 24 小時的計數）。
- **關機時**：procd 停止服務、`sysupgrade` 前、備份匯出前都會把所有變動（包括只有計數的）寫出去。
- **壓縮**：CDN 的狀態檔（`cdn/` 底下：網域分片、節點池、IPv6 節點、候選 IP、網段分類）存成 zstd（等級 3、視窗 512 KB）的 `.zst`。
  讀的一方（啟動、備份匯出 / 匯入、`kuroshio compare`、種子資料）兩種格式都接受，兩份都有時用比較新的；
  寫出壓縮檔後刪掉舊的一般 JSON（只遷移一次）。小檔（統計、常用網域、排程、社群、存取控制）維持一般 JSON。
- **CDN 網域資料庫分片**：`cdn/domains/{N}-{i}.json.zst`，網域依名稱的 FNV-1a 雜湊分到 N 片（2 的次方，
  依 `cdn.maxEntries` 決定，上限筆數時每片壓縮後約 64–128 KB）；`cdn/domains/manifest.json` 記錄 N 與舊版不認識的欄位。
  - 驗證結果、IP、策略、ECS、跨 CDN、新增 / 刪除網域：那一片標成「要寫」；只有計數：標成「只有計數」。寫的時候只重寫有標記的分片（各自 tmp + fsync + 改名）。
  - 舊版的 `cdn-domains.json` 讀得進來，全部重寫成分片、分片清單寫好之後才刪掉舊檔；中途斷電下次會重來，不會遺失。
  - N 改變（例如改了 `cdn.maxEntries`，或從舊版的等級上限升級上來）：新的一組全部寫好、清單更新後才刪舊的一組（檔名帶 N，不會互相蓋掉）。
  - 載入時某片壞掉或不見：記警告、其他照常載入，只重寫那幾片；清單壞掉時用目錄裡檔案最多的一組救回。絕不因此不能啟動。
  - 備份檔格式不變：匯出時組回 2.x 的單一檔案；匯入合併時寫成單一檔案、分片作廢，下次啟動再搬進分片。
- **狀態頁顯示**（`/api/status` 的 `system.persist`）：`class`、`bytesToday`、`bytesYesterday`、`dailyBudgetKB`、`intervalMin`、
  `effectiveIntervalMin`、`maxAgeHours`、`oldestUnsavedSec`（最久未存）、`forcedByAge`、`estimatedDailyBytes`、`deferred`、`pending`、
  空間（`freeBytes`、`minFreeBytes`（＝保留量）、`lowSpace`、`freedBytes`、`skipped`、`space`（第 5.6 節）），以及每個檔的 `files.{名稱}.{lastWrite, pendingSince, countersOnly, size, compressed}`。
  設定頁與 LuCI 的狀態分頁顯示「最久未存」。

### 5.4 儲存類型判定

依 state 目錄所在檔案系統（`/proc/mounts`）：

| 判定 | 條件 |
|---|---|
| `ram` | tmpfs、ramfs |
| `flash` | jffs2、ubifs、squashfs、overlay（OpenWrt 的 overlay 底層幾乎都是 Flash）、或裝置是 `mtd*` / `ubi*` / `mmcblk*`（SD 卡、eMMC） |
| `disk` | 其他：x86 的硬碟、SSD、Windows |

USB 隨身碟也算 Flash，但通常容量大、可以更換，判定為 `disk`；如果要保守，可以用 `system.storageClass` 強制指定。

### 5.5 實測與估算（2026-11，`kuroshio-cdn` 的 `bench_persist`）

壓縮（zstd 等級 3）：

| 資料 | 原始 | 壓縮後 | 倍數 |
|---|---|---|---|
| 種子網域資料庫（3,961 筆，正式伺服器匯出） | 2,067 KB（534 B/筆） | 355 KB（約 92 B/筆） | 5.8 |
| 模擬的 5 萬–20 萬筆（種子打散名稱、時間、次數、IP） | 545 B/筆 | 115–120 B/筆 | 4.6–4.8 |
| 節點池 `cdn-pools.json` | 69 KB | 8 KB | 7.8 |
| 永久 IPv6 節點 `v6-nodes.json` | 107 KB | 14 KB | 7.6 |

等級 1 / 3 / 9 的壓縮率差不多（5.8 / 6.0 / 7.2 倍），9 要 4–5 倍的時間，所以用 3。注意：jffs2 / ubifs 本身也會壓縮（zlib / lzo），
所以在這兩種檔案系統上實際省下的 Flash 寫入比上表少；SD 卡、eMMC（ext4 / f2fs）上就是上表的比例。每日寫入量一律以壓縮後的檔案大小計。

分片（上限筆數時）：

| `cdn.maxEntries` | 分片數 | 每片（壓縮後，上限筆數時） | 一個驗證結果變動要寫 |
|---|---|---|---|
| 10,000 | 16 | 約 74 KB | 一片：約 74 KB |
| 25,000 | 32 | 約 93 KB | 約 93 KB |
| 150,000 | 256 | 約 70 KB | 約 70 KB |
| 200,000（現在所有機器的預設） | 256 | 約 93 KB（家用 5,000 筆時每片約 2.3 KB） | 一片 |

分片數依安全上限決定，所以家用的資料量下每片很小：一個變動只重寫幾 KB。

（舊的單一檔案：一個變動要整份重寫，20 萬筆是 110 MB。）

一般家庭每天的寫入量（假設）：資料庫約 5,000 筆（種子 4,000 ＋自己學到的）；每天幾百個網域重新驗證或新增，分散在各分片，
所以每次寫入時幾乎每片都有變動，一次約等於整個資料庫壓縮後 0.6 MB，加上節點池、IPv6 節點約 25 KB：

| 機器（典型可用記憶體，保留 16 MB） | 間隔 | 每天寫入 | 資料庫滿載時 |
|---|---|---|---|
| 128 MB 路由器（可用約 60 MB） | 6 小時 | 約 2.4 MB | 超過 4 MB 目標的部分延後，靠最久未存上限每天至少寫一次 |
| 256 MB（可用約 150 MB） | 12 小時 | 約 1.2 MB | 3 MB × 2 → 第二次超過目標延後；最多 6 MB |
| 512 MB 以上（保留量以上 ≥ 256 MB） | 24 小時 | 約 0.6 MB | 18 MB（超過目標，靠最久未存上限每天寫一次） |
| 硬碟 | 10 分鐘 | 不受限 | 不受限 |

（以前 tiny 等級固定 12 小時；拿掉等級後 128 MB 機器回到 Flash 的預設 6 小時，每天多寫約 1 MB，仍在 4 MB 目標內。）

16 MB NOR（可用 8 MB、10 萬次抹寫）理論上可以寫 800 GB；以每天 2 MB 計算超過一千年，遠超過硬體壽命。
便宜的 SPI-NAND（幾千次）也有數十年。

### 5.6 儲存空間：保留量以上大方用

跟記憶體同一個想法（09）：檔案系統留一段**儲存保留量**，在它之上可重建、可省略的資料大方留著（重開機更快、少重新下載、少重新學習），
空間不夠時依序刪掉。寫快照之前先看狀態目錄所在的檔案系統（Unix `statvfs`、Windows `GetDiskFreeSpaceExW`），每輪（5 分鐘）也檢查一次。

**保留量**（`persist::storage_reserve`）：`system.storageReserveMB` 與 / 或 `system.storageReservePercent`（檔案系統大小的百分比，最多 90），
舊的 `system.minFreeKB` 照樣接受（當成絕對值），有填的取最大；都 0 = 自動：

| 儲存類型 | 自動 | 理由 |
|---|---|---|
| Flash（OpenWrt overlay、SD、eMMC） | max(1 MB, 檔案系統 10%（最多 64 MB）, 最大一份待寫 × 2) | jffs2 的垃圾回收要有空的抹除區塊才能搬資料（核心預設保留約 5 塊給回收，NOR 每塊 64–256 KB），太滿時寫入越來越慢、甚至失敗；ubifs 回報的可用空間是估計值（壓縮率不定）。另外留給 `opkg install`（一般套件 100–500 KB）與改設定檔 |
| tmpfs | max(1 MB, 10%（最多 64 MB）, 最大待寫 × 2) | 用的是記憶體；記憶體另外由 09 管 |
| 硬碟、SSD、Windows | max(256 MB, 2%（最多 1 GB）, 最大待寫 × 2) | 系統更新、分頁檔、暫存檔都要空間，幾 MB 的狀態檔不該跟它們搶 |

一律不超過檔案系統的一半。**遲滯** = 保留量的一半，至少 1 MB；「保留 + 遲滯」是可重建資料的線。

| 類別 | 檔案 | 寫入 | 空間掉到線以下 |
|---|---|---|---|
| 日誌 | Windows 的 `kuroshio.log`、`.log.old`、殘留的暫存檔 | — | 最先刪 |
| 可省略 | 過濾清單的本機副本 `filter-lists/`（含索引） | 寫完還在線以上、記憶體也還能長大時才留 | 其次 |
| 可重建 | `cdn/harvest.json`、`cdn/ip-zone.json`、`stats.json`、`hot-names.json`、`import-last.json`、`benchmark/`、`cdn/ranges/`、`cdn/scan/` | 寫完還在線以上才寫 | 再其次（舊的先、一樣舊大的先），之後重新學習 / 下載 |
| 核心 | CDN 網域分片與清單、節點池、永久 IPv6 節點、社群身分 / 金鑰 / 好友、設定、自訂規則、黑名單、憑證、其他不認識的檔 | 只要放得下（暫存檔＋64 KB）就寫，可以用掉保留空間 | **絕不自動刪除** |

- 空間掉到線以下：依序刪到回到線上，每刪一個記一筆 info；還是不夠就只寫核心資料（其他留在記憶體，下次再試），`lowSpace` = true。
- 寫入節奏照舊：本機副本也經快照寫入器寫，受最短間隔、每日目標、最久未存上限管；**內容沒變不重寫**（比對原文雜湊，只有 ETag 變了只更新索引）。
  硬碟 / tmpfs 沒有每日目標。
- 狀態（`/api/status.system.persist.space`）：`totalBytes`、`freeBytes`、`reserveBytes`、`reserveAuto`、`reserveHow`、`marginBytes`、`headroomBytes`、
  `optionalFiles` / `optionalBytes`（目前留著的可省略 / 可重建資料）、`keepingOptional`（現在在線以上）、`deleted[]`（最近刪掉的檔）。

## 6. 防止低階硬體被拖垮

| 情況 | 處理 |
|---|---|
| 小記憶體機器打開大型清單（HaGeZi、新註冊網域） | 載入前依保留量以上的空間估計，放不下的不載入（`budget`）；LuCI 在勾選時就依上次下載的規則數預估並提醒 |
| 打開 DoQ / DoH3 | 連線上限依核心數；接近保留量時新連線最多 32 條，不足時暫不接受新的加密連線 |
| 社群共享 | 收到的資料解壓後不超過 `community.maxBundleMB`（安全上限 32 MB），也不超過保留量以上空間的 1/4 |
| 記憶體不足 | 09 的階梯依序讓出，最深到純轉送；背景工作延後、快照立刻寫出 |
| CPU 長時間滿載 | 背景工作自動延後；DNS 服務優先 |
| 本程式當掉 | OpenWrt procd 1 秒後重啟、不放棄；重新啟動期間 dnsmasq 備援轉送（09 第 6 節）；Windows 服務 1 秒後重啟 |

## 7. 依 CPU 核心數換算的預設值

`defaults.json` 寫 `"auto"` 的欄位在載入時換算（`kuroshio_config::derive_auto`）；使用者填了數字（UCI 給的字串也算）就用使用者的。
c = CPU 核心數（`available_parallelism`）：

| 設定 | 公式 | 單核 | 雙核 | 四核 | 八核以上 |
|---|---|---|---|---|---|
| `resolver.parallel`（同時問幾個上游） | 1 核 2、2 核 3、更多 0（全部） | 2 | 3 | 0 | 0 |
| `resolver.warmRate`（開機預熱每秒幾筆） | clamp(5c, 5, 20) | 5 | 10 | 20 | 20 |
| `iprank.concurrency` | clamp(8c, 8, 64) | 8 | 16 | 32 | 64 |
| `cdn.verifyConcurrency`（每個都是 TLS 握手） | clamp(2c, 2, 8) | 2 | 4 | 8 | 8 |
| `benchmark.concurrency` | clamp(8c, 8, 50) | 8 | 16 | 32 | 50 |
| `scan.concurrency` | clamp(50c, 32, 400) | 50 | 100 | 200 | 400 |
| `pool.latencyConcurrency` | clamp(32c, 32, 200) | 32 | 64 | 128 | 200 |
| `pool.probeConcurrency` | clamp(8c, 8, 32) | 8 | 16 | 32 | 32 |
| `system.maxTlsConnections`（每條約 30–60 KB，記憶體另由 09 收緊） | clamp(128c, 128, 2048) | 128 | 256 | 512 | 1,024（16 核 2,048） |
| `system.maxQuicConnections`（0 = 不開 QUIC） | clamp(32c, 32, 512) | 32 | 64 | 128 | 256 |
| `filter.maxUnindexed`（每次查詢都要跑的規則；每 2,000 條約 +0.5 ms/查詢，慢的 CPU 更多） | clamp(250c, 200, 2000) | 250 | 500 | 1,000 | 2,000 |

其他以前依等級調整的欄位現在所有機器一樣（安全上限，或網路工作的規模）：

| 設定 | 值 | 以前 tiny / small / standard | 現在怎麼控制 |
|---|---|---|---|
| `resolver.cacheMax` | 100,000 | 4,000 / 15,000 / 50,000 | 09：接近保留量停止長大、吃緊縮小 |
| `resolver.warmNames` | 2,000 | 200 / 500 / 1,000 | 名單只有幾 KB；預熱速度依核心數 |
| `cdn.maxEntries` | 200,000 | 1 萬 / 2.5 萬 / 15 萬 | 09：冷資料移到磁碟 |
| `cdn.zoneMax` / `v6NodesMax` | 8,000 / 2,000 | 2,000 / 4,000、300 / 800 | 安全上限（資料量由 CDN 官方範圍決定，幾百 KB） |
| `cdn.qualityIntervalMin` / `healthIntervalMin` | 5 / 30 | 15 / 10、60 | 背景工作接近保留量時延後 |
| `scan.samplesPerSubnet`、`pool.candidatesPerProvider` / `speedTop` / `speedSeconds` / `nearestProbeTop` | 6、1,500 / 16 / 5 / 1,500 | 依等級調低 | 工作規模；接近保留量時整個工作延後 |
| `jobs.cdn-scan.enabled` | true | tiny 停用 | 接近保留量時延後 |
| `filter.maxDomains` / `maxComplex` | 1,000 萬 / 2 萬 | 40 萬… / 2,000… | 09：載入前依空間估計 |
| `system.queryLogRing` | 20,000 | 200 / 1,000 / 5,000 | 安全上限 |
| `community.maxBundleMB` / `maxFriends` | 32 / 50 | 4 / 8、10 / 20 | 好友資料另受保留量以上空間的 1/4 限制；好友數是防濫用上限 |

網域資料庫的分片是要寫的時候才邊序列化邊寫進檔案（邊寫邊壓縮），整份 JSON 不會放在記憶體裡。
每筆常駐記憶體（`bench_persist`）：armv7 musl 約 600 B、i686 musl 約 520 B、x86_64 約 850 B。

## 8. 驗收

- CI：用 QEMU 跑 MIPS / ARM 執行檔。記憶體不再有固定目標：驗收的是「系統可用記憶體低於保留量時依序讓出、最深仍轉送」（09 第 8 節的測試）。
- 寫入計數器的單元測試：快照間隔、內容沒變不寫、每日目標、關機時寫出、超過目標時最久未存上限仍強制寫入、
  間隔跟著記憶體（保留量以上的空間）、只有計數的變動不單獨寫、壓縮與遷移、分片清單等分片寫好才寫、
  儲存保留量（自動 / MB / % / minFreeKB 取最大）、可省略資料在線以上保留 / 以下依序刪、核心資料不刪、清單副本內容變了才寫。
- CDN 分片的單元測試：一個驗證結果只重寫一片、只有計數不算重要變動、舊版單一檔案搬家、壞掉的分片不影響啟動、分片數改變。
- 實機（MT7621 128 MB / 256 MB）：連續 7 天，記錄每天寫入量、記憶體高點、快取命中延遲。
