# 09 · 記憶體控制：有空間就多留，吃緊就依序釋出

> 維護者的需求（摘要）：記憶體沒有餘裕時還是要寫進 Flash；記憶體越多，寫得越少、沒用的資料越有機會被淘汰。
> 要有記憶體控制機制，避免系統記憶體用光——例如從來沒被查過的過濾規則可以適度卸載，記憶體有餘裕時再載回。
> Flash 空間也一樣（已在 05 第 5.6 節做完）。彈性、聰明的狀態。

實作：`crates/kuroshio/src/memgov.rs`（控制器與四個步驟）、`filtering.rs`（清單停用 / 恢復、命中次數）、
`kuroshio-cdn` 的 `Db::evict_cold` / `Cdn::ensure_loaded`（CDN 冷資料）、`cache.rs` 的 `Cache::shed_to`。
寫入節奏（記憶體越多寫越少）在 05 第 5.3 節，這裡不重複。

## 1. 預算與量測

- **預算**：`system.memoryBudgetMB`；0（預設）= 依等級自動。

  | 等級 | 自動預算 |
  |---|---|
  | tiny | 24 MB |
  | small | 48 MB |
  | standard | 128 MB |
  | large | 實體記憶體的 1/8，介於 256–1024 MB（量不到實體記憶體時 512 MB） |

  自動預算一律不超過實體記憶體的一半。
- **量測**（每 30 秒）：自己的常駐記憶體 RSS（Linux：`/proc/self/statm`；Windows：`K32GetProcessMemoryInfo` 的 WorkingSetSize），
  系統實體 / 可用記憶體（Linux：`/proc/meminfo` 的 `MemTotal` / `MemAvailable`；Windows：`GlobalMemoryStatusEx`）。
- RSS 含執行檔本身被讀進來的部分（程式碼頁），所以預算是「整個行程」的預算，不只是資料結構。

## 2. 狀態與遲滯

三個狀態：**寬裕**（comfortable）、**吃緊**（tight）、**不足**（critical）。

| | 進入 | 離開（放鬆一級） |
|---|---|---|
| 吃緊 | 可用 < 15%、或可用 < 24 MB、或 RSS > 預算 | 可用 > 25%、可用 ≥ 32 MB、RSS < 預算 × 85% |
| 不足 | 可用 < 8%、或 RSS > 預算 × 120% | 可用 ≥ 12%、RSS ≤ 預算 × 110%（回到吃緊） |

- 變嚴重：立刻。放鬆：一次一級，條件要**連續**成立 180 秒（中間只要掉回去一次就重新計時），而且目前狀態已經停留 180 秒以上。
- 量不到的數字不參與判斷（例如沒有 `/proc` 的系統只看得到 RSS）；什麼都量不到就維持寬裕。
- 純函式 `memgov::step_state`，測試直接餵量測值（`Reading`），不依賴主機真正的記憶體。
- 原本的看門狗（`PRESSURE`，只看系統可用記憶體）照舊運作：延後背景工作、不足時拒絕新的加密連線、延後清單更新。
  開了記憶體控制後，看門狗原本的「縮快取一半、刪掉 CDN 網域三成（連磁碟一起刪）」改由下面的階梯處理（不再刪磁碟上的資料）。

## 3. 釋出階梯

吃緊 / 不足時，每 30 秒最多做**一步**，下一輪量到效果再決定要不要做下一步（重建成本由低到高）：

1. **診斷緩衝**：設定頁日誌 500 → 50 行；熱門網域 / 被擋網域 / 用戶端排行只留前 200 名（上限也維持 200）。
   公開頁的匿名網站排行不動。
2. **DNS 快取**：縮到 `resolver.cacheMax` 的 1/4（至少 256 筆），上限也維持在那裡。留下熱門的：
   分數 = 上次使用時間 + 每多一倍的查詢次數加 5 分鐘（常用的名稱就算幾分鐘沒人查也留著）。
3. **CDN 網域資料庫冷資料**：
   - 先在「登記鎖」底下把所有變動登記、立刻寫出（`flush_all`；記憶體不足時本來就要寫，見 05 第 5.3 節），
     然後只移出「已經在磁碟上、之後沒有任何變動、快照寫入器沒有待寫內容」的分片裡，一小時以上沒出現、自動策略的網域。
     手動設定策略的、最近出現的、剛改過的都不動。整個資料庫要重寫（搬家、分片數改變）時不動。
   - 記憶體裡只留移出網域名稱的 32 位元雜湊（每筆 4 bytes，原本每筆約 600–850 bytes）。
   - 查詢回應碰到移出的網域：從那個分片檔逐筆解析、只撈出那一筆放回記憶體（不展開整片；分片壓縮後約 70–90 KB）。
     判定（驗證結果、策略、ECS、跨 CDN）跟移出前完全一樣。管理 API（`/api/trace`、`/api/cdn/policy`、`/api/cdn/verify`）也一樣會讀回。
   - 這片之後有變動要重寫：從磁碟上的舊檔把移出的網域接回去（依名稱排在一起），寫出來跟全部都在記憶體時一模一樣，磁碟上不會少。
   - 舊版單一檔案匯出（`snapshots()`）、關機整份寫出前會先全部讀回。
   - `/api/cdn/domains` 這類列表只列記憶體裡的網域（移出的在磁碟上，查到就回來）。
4. **過濾清單**（只在「不足」、而且**系統**可用記憶體真的 < 8% 時；只是自己的 RSS 超過預算、系統還有空間時不做）：
   - 一次停用一份，順序：分類（廣告 → 遙測 → 惡意）、歷史命中次數少的先、佔記憶體多的先。
   - **絕不停用**：自訂規則、標成保護的清單（`filter.lists[].protect`；沒寫時惡意類——含 165 反詐騙——預設是保護）。
     「從來沒命中」不代表沒用：詐騙、惡意網域大多是第一次出現，所以命中次數只用來排順序，保護清單完全不參與。
   - 停用 = 重新下載其他清單、重建一份不含它的過濾器；建好才換（重建期間舊的照常使用）。下載失敗就保留舊的、不算停用。
   - 重建時新舊兩份同時存在：新的一份放不進系統可用記憶體的一半就不做（不能為了省記憶體反而把記憶體用光）。
   - 各清單命中次數（`filter-hits.json`）經快照寫入器保存（「只有計數」：不單獨觸發寫入）。
   - 狀態頁、LuCI 狀態頁明顯提示：「記憶體不足，暫時停用：XXX 清單（N 條規則）」。

### 3.1 為什麼不在 tmpfs 留清單的壓縮副本

停用 / 恢復清單都要重建（重複的網域只存一份、分類與清單編號合併在同一個位元組裡，不能從現有結構裡「減掉」一份清單），
重建需要清單原文。實測預設 7 份清單原文 3.6 MB，zstd -3 壓縮後 1.2 MB——跟整個清單層在記憶體裡的大小（約 1.3 MB）差不多。
放 `/tmp`（tmpfs）就是佔記憶體，等於沒省；放 Flash 每天又多寫 1 MB 以上。所以選擇**重新下載**：
只在停用 / 恢復時才發生（有停留時間、一次一份），下載失敗用指數退避重試（5 分鐘起，每次加倍，最多 6 小時），失敗期間維持現狀。

## 4. 恢復

- 寬裕持續 180 秒以上，才依**相反順序**一次恢復一項：過濾清單先（保護最重要；最後停用的先恢復），再來 CDN 冷資料（全部讀回），
  快取與診斷緩衝只恢復上限，之後自然長回來。
- 要恢復的項目估計需要的記憶體 × 1.3 ≤ 可用空間才恢復；可用空間 = min（預算 − RSS，系統可用 − 「寬裕」門檻），不夠就等（狀態裡寫明在等什麼）。
- 恢復後 10 分鐘內又吃緊：下次恢復的間隔加倍（避免來回）。

## 5. 不超過預算

- 過濾清單載入前：清單層的額度 = 預算 − （RSS − 目前清單層大小），也不超過系統可用記憶體的一半（重建時新舊兩份並存）。
  - 量過大小的清單：估計放不下就依停用順序先不載入（原因 `budget`，狀態裡看得到，記一條警告）。
  - 沒量過的（第一次載入）：換算成網域數，跟 `filter.maxDomains` 取小的；超過的清單整份不載入（`overBudget`）。
- 快取：釋出期間上限維持在 1/4，超過就清掃。CDN 網域資料庫照舊受 `cdn.maxEntries` 限制。
- 全部只用 32 位元原子操作（MIPS 沒有 64 位元原子操作）。

## 6. 實測（2026-11，x86_64 除錯組建，`cargo test -p kuroshio --test memgov_bench -- --ignored --nocapture`）

情境：small 等級、預設啟用的 7 份清單（本機伺服器提供 2026-11-11 下載的原檔）、種子 CDN 資料庫 3,961 筆（九成設成 6 小時沒出現）、
快取填滿 15,000 筆、排行 2,000 個網域。「heap 實測」是配置器實際少掉的位元組（最準）；「估計」是程式顯示在狀態頁的數字；
RSS 差受配置器影響（釋出後呼叫 `malloc_trim`），只供參考。

| 步驟 | heap 實測 | 估計 | RSS 差 | 內容 |
|---|---|---|---|---|
| 1. 診斷緩衝 | 123 KB | 113 KB | — | 日誌 50 行、排行前 200 名 |
| 2. DNS 快取 | 5,003 KB | 3,508 KB | 792 KB | 15,000 → 3,750 筆 |
| 3. CDN 冷資料 | 3,290 KB | 2,031 KB | 404 KB | 3,564 筆移出（磁碟保留） |
| 4. 停用 CHN: anti-AD | 861 KB | 916 KB | 696 KB | 101,072 條規則 |
| 4. 停用 EasyList China | 122 KB | 122 KB | 76 KB | 5,997 條 |
| 4. 其餘非保護清單（4 份） | 77 KB | 82 KB | 88 KB | 9,290 條 |
| 合計 | 9,475 KB | | | TW165（16,946 條，保護）不動 |

- 估計值偏保守（快取、CDN 的估計比實際少 30–40%），用在恢復時的空間判斷不會高估。
- 32 位元路由器上每筆 CDN 網域約 600 bytes（05 第 3.1 節），比 x86_64 小。
- 恢復：過濾清單重新下載後 heap 回到原本大小；CDN 讀回 3,564 筆、heap +3,314 KB。

## 7. 取捨（誠實說明）

- **停用清單期間保護變少**：只在系統真的快沒記憶體時才做、一次一份、從廣告類開始，惡意 / 反詐騙預設不動；
  停用中的清單在狀態頁、LuCI 狀態頁都有明顯提示。寧可少擋廣告，也不要整台路由器因為記憶體用光而重開（那時什麼都擋不了）。
- **CDN 冷資料第一次被查到時要讀一次磁碟**（一個分片，約 70–90 KB 壓縮檔解壓、逐筆解析），之後就在記憶體裡。
  32 位元雜湊理論上可能碰撞：碰撞時最多多讀一次磁碟、或讓一筆已刪除的冷資料在重寫分片時留下來，不會讓判定出錯。
- **配置器不一定把記憶體還給系統**：glibc 釋出後會呼叫 `malloc_trim`；musl（OpenWrt）釋放大塊時直接還，小塊可能留在行程裡。
  RSS 沒降下來時，狀態會停在吃緊、不會恢復——已釋出的項目維持釋出（不會更糟），但也不會自己長回來。
- **預算是整個行程的 RSS**：tiny 24 MB 含執行檔的程式碼頁。實際路由器上的 RSS 還沒有量過（見 8）；
  如果某台 tiny 路由器平常就超過 24 MB，會一直停在吃緊（快取 1/4、CDN 冷資料在磁碟），過濾清單不受影響（只看系統可用記憶體），
  可以把 `system.memoryBudgetMB` 調高。

## 8. 還沒驗證

- 真的 128 MB 路由器（MIPS / ARM、musl）上：平常的 RSS、各步驟實際讓 RSS 降多少、系統真的快用光記憶體時（OOM killer 出手前）
  30 秒一輪的反應夠不夠快。
- Windows 上的 WorkingSetSize 與 `GlobalMemoryStatusEx`（程式碼已經編過 Windows 目標的型別檢查，沒有在 Windows 上跑過）。

## 9. 設定與 API

| 設定 | UCI | 預設 | 說明 |
|---|---|---|---|
| `system.memoryGovernor` | `system.memory_governor` | true | 記憶體控制開關；關掉時回到 05 第 3.2 節的看門狗行為 |
| `system.memoryBudgetMB` | `system.memory_budget_mb` | 0 | 預算（MB）；0 = 依等級自動 |
| `filter.lists[].protect` | `filter_list.protect` | 惡意類 true，其他 false | 保護清單：記憶體不足也不停用 |

`/api/status.memory`（`/api/status.system.memory` 是同一份）：

| 欄位 | 說明 |
|---|---|
| `enabled` | 有沒有開記憶體控制（沒開時只有 `rssKB`） |
| `state` / `stateLabel` | `comfortable` / `tight` / `critical`（寬裕 / 吃緊 / 不足） |
| `since` | 進入目前狀態的時間（毫秒） |
| `rssKB`、`budgetKB`、`availKB`、`totalKB` | 上次量到的數字與預算 |
| `shed[]` | 釋出中的項目：`step`（`diagnostics` / `cache` / `cdn` / `filter`）、`label`、`detail`、`freedBytes`（估計）、`rssDeltaKB`（下一輪量到的 RSS 差）、`at` |
| `freedBytes` / `freedTotalBytes` | 目前釋出中合計 / 啟動以來合計 |
| `lastChange` | `{ at, from, to }` |
| `waiting` | 想恢復但空間不夠時，在等什麼 |
| `nextRestoreAt` | 下次可以恢復的時間（有釋出中的項目時） |
| `events[]` | 最近 20 筆狀態變化與動作（新的在前） |

`/api/status.filter` 新增：`unloaded[]`（`name`、`rules`、`bytes`、`reason`：`memory` / `budget`、`at`）、
`notice`（「記憶體不足，暫時停用：…」，沒有時是 null）、`sources[].protect`、`sources[].hits`、`sources[].status` 多了 `unloaded`。
