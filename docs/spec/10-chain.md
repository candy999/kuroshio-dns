# 10 串接模式、共用結果與 3.4.0 的其他項目

3.4.0 的規格。六個項目：

1. **串接模式**：兩層黑潮（例如 Newifi D3 接在跑黑潮的主路由器後面）時，下游認出上游、驗證身分、把上游當成第一順位上游。
2. **共用結果**：下游直接拿上游的每日評測結果、CDN 節點池，不自己重算（過濾清單 3.4.3 起不共用，見 3.1）。
3. **上游放行下游**：上游對驗證過金鑰的下游放寬存取控制與「繞過防護」清單（跟著 `allow_downstream`，不逐台核准）。
4. **低階機器的並行數**：沒有 AES 指令的 CPU 先問最快的 2 個上游，其他上游在背景補問。
5. **上游多樣性**：每日評測選「覆蓋」上游時優先台灣、日本、香港、新加坡（`coverage_region`）。
6. **重新載入時不斷線**（選做）：SIGHUP 後不再有 Connection refused。

**原則**（3.4.2 確立，之後的設計與測試都照這個判斷；完整說明、特別情境與檢查清單在 [核心理念與設計原則](../principles.md)）：

1. **目的**：讓每台黑潮都能自己拿到真實、乾淨、快的 DNS：繞過劫持與封鎖、拉回台灣 CDN。功能不為了省資源而砍掉；省資源是為了讓功能在小機器上也跑得動（小機器是「減量」，不是「關掉」）。
2. **不當攻擊者**：每日評測、劫持探測、雙層黑潮的共用結果，是為了不要對同一台伺服器重複大量查詢。否則測來測去都是同一台劫持伺服器；大量流量對上游像攻擊；被封殺後整個網路就異常。所以要分散、限速、共用、不重複做。
3. **每台黑潮都有自由**：上游的過濾是上游的政策；下游有自己的清單與加密上游，要不要擋由下游決定（第 1.6 節）。使用者選黑潮，就是想繞過阻擋。
4. **上下游是「直系血親」**：自動成立的好友關係（社群共享的變種），會互相傳承資料（評測結果、節點池；清單副本只到 3.4.2）。下游是有想法的獨立個體：保有自己收集資料的能力，拿到的資料自己查核，不深度依賴（節點金鑰是自己產生的，「驗證過」只證明對方會講這個協定，上游可能是偽裝的）。見第 3.8 節。
5. **安全路線**：雙層黑潮不常見，不做激進優化；任何機制都要有上限、會自己恢復、不能形成風暴或迴圈。
6. 不做讓效能變差的修改。

工作分解在 [10-chain-tasks.md](10-chain-tasks.md)。名詞：**上游**＝離網際網路近的那台黑潮（主路由器），**下游**＝接在它後面的黑潮。
文件裡的區網位址用 `192.168.1.1`（上游）、`192.168.1.2`（下游），跟 `docs/integration.md` 既有的範例一致；公網位址一律用文件用位址。

## 1. 串接模式

### 1.1 目標

- 下游認出「一般 DNS 被上游黑潮接走」之後，確認對方真的是那台黑潮（節點金鑰簽章），把它當成第一順位上游：下游只問它一台，省掉加密上游的並行查詢。
- 沒有攔截、攔截者不是黑潮、或上游版本低於 3.4.0：**不發任何串接查詢**，行為跟 3.3.7 完全一樣。
- 只有兩個開關：下游的 `chain`（要不要辨識上游黑潮並索取資料）與上游的 `allow_downstream`（要不要提供資料給下游），預設都開。**兩邊都開才通訊**；任一邊關就各走各的，下游的行為跟 3.3.7 一樣。沒有同意的步驟：認出來、驗證過就自動串接。
- 上游換掉、沒回應、換網路時自動解除，退回自己的上游。

### 1.2 通道：一般 DNS 的 CHAOS TXT

所有串接訊息都是 **CH 類別、TXT 型別**的查詢，名稱在 `chain.kuroshio` 底下，送到「路徑檢查命中的那個保留位址」的 53 埠。

**為什麼不用管理 API、社群 transport 或上游的 DoH／DoT**：

- 下游只確定兩件事：53 埠會被接走、預設閘道是哪個位址。攔截者不一定是閘道（中間可能還有一台不跑黑潮的路由器）。被接走的 53 埠是唯一「不需要知道上游位址、不需要上游多開任何埠」就到得了的路。
- 管理 API 預設只聽 `127.0.0.1`；社群 transport 走加密監聽、需要網域與憑證，而且預設沒開。
- 上游回答的條件沿用 `version.kuroshio`：`proto` 是 `udp`／`tcp`、來源是私有位址、通過 `listen.plain.allowFrom` 與 `access` 的 `plain`。公開的 DoH／DoT 一律不回答（不透露節點資訊）。

名稱一覽（`<…>` 是變數；全部小寫）：

| 名稱 | 用途 | 傳輸 | 誰簽章 |
|---|---|---|---|
| `<nonce>.a.chain.kuroshio` | 挑戰／回應（auth） | UDP，TC 時改 TCP | 上游 |
| `r.chain.kuroshio` ＋ EDNS 選項 65313 | 下游登記（reg，第 4 節才用到） | TCP 優先 | 下游簽請求、上游簽回應 |
| `m.s.chain.kuroshio` | 共用結果的清單（manifest，第 3 節） | 只有 TCP | 上游 |
| `<idx>.<oid>.s.chain.kuroshio` | 共用結果的分段（第 3 節） | 只有 TCP | 不簽（用清單裡的雜湊驗證） |

`<nonce>`：16 bytes 亂數的 32 個十六進位字。`<oid>`：物件 SHA-256 前 8 bytes 的 16 個十六進位字。`<idx>`：十進位。

回應：`rcode = 0`、一筆 TXT 記錄（class 3、TTL 0），把內容切成每段最多 255 bytes 的字串，接起來就是原始 bytes（**二進位，不是 base64**）。
不認得的名稱、來源不符、被速率限制：回 `REFUSED`（rcode 5），不轉給上游。

### 1.3 訊息格式

編碼用 CBOR（`kuroshio_community::envelope::{to_cbor, from_cbor}`），外層固定是：

```
Sealed = { "body": bytes, "sig": bytes(64) }
sig = Ed25519( 節點私鑰, "kuroshio-chain/1\0" || kind || 0x00 || body )
```

`kind` 是 ASCII：`auth`、`reg`、`regack`、`manifest`。簽章的前綴跟社群共享的 `kuroshio/2\0` 不同，兩邊的簽章不能互相冒用。
`body` 是下面各訊息的 CBOR（map，鍵是字串）。**不認得的欄位一律忽略；`v` 大於自己認得的版本就當成不支援。**

#### AuthBody（上游 → 下游）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `v` | u8 | 協定版本，3.4.0 是 `1` |
| `t` | text | `"auth"` |
| `nonce` | bytes(16) | 查詢名稱裡的 nonce 原樣帶回 |
| `ts` | u64 | 上游的時間（Unix 毫秒）。**只供顯示與除錯**，不拿來判斷有效期（下游的時鐘可能還沒對時） |
| `kid` | bytes(8) | 上游節點 ID（`kid_of(公鑰)`） |
| `pub` | bytes(32) | 上游 Ed25519 公鑰 |
| `app` | text | 上游版本（`CARGO_PKG_VERSION`） |
| `allow` | bool | 上游的 `allow_downstream` |
| `caps` | [text] | 能力：`"share"`（有共用結果可以拿）、`"reg"`（接受登記）。沒有的能力下游不會去問 |
| `peer` | text | 上游看到的用戶端位址（下游據此知道自己有沒有經過 NAT；登記時要帶回去） |
| `tok` | bytes(16) | 登記用的一次性憑據：`HMAC-SHA256(啟動時的亂數密鑰, "tok" || peer || 時間窗編號)[..16]`，時間窗 300 秒，上游接受目前與前一個時間窗 |
| `path` | [bytes(8)] | 節點 ID 鏈，從最上層到自己（自己在最後）。沒有串接別人的節點是 `[自己]` |

大小：約 270 bytes（`path` 4 層時約 300），UDP 不需要 EDNS。

`allow = false` 時照樣簽章回答（下游才能顯示「上游不允許串接」），但 `caps` 是空的、之後的登記與共用結果一律 `REFUSED`。

#### 防重放

- nonce 由下游每次查詢新產生（`random_bytes::<16>()`），回應必須帶回同一個 nonce、簽章驗得過才算數；一個 nonce 只用一次，查詢逾時（1.5 秒）就作廢。攔下舊的回應重放沒有用。
- **不依賴時間戳**：下游開機後時鐘可能還沒對時（`crate::clock`），用時間判斷有效期會誤判。
- `tok` 綁來源位址與 5 分鐘時間窗，登記訊息由下游簽章並涵蓋 `tok` 與 `peer`：攔下登記封包從別的位址重送無效。

### 1.4 狀態機（下游）

```
              路徑檢查：攔截者是黑潮 ≥ 3.4.0，而且 chain 開著
   ┌────────┐ ───────────────────────────────────────────▶ ┌──────────┐
   │ none   │                                              │ detected │ 發一次 auth 挑戰（探測）
   │ 未偵測 │ ◀─────── 路徑檢查：沒被接走／不是黑潮 ─────── └────┬─────┘
   └────────┘                                                   │ 探測通過：allow=true、沒有迴圈、不會太深
        ▲                                                        ▼
        │    探測失敗、allow=false、迴圈、太深              ┌───────────┐
        │   ┌──────────────────────────────────────────────│ verifying │ 重新挑戰＋直連閘道確認
        │   ▼                         驗證失敗              │ 驗證中    │
   ┌──────────┐ ◀──────────────────────────────────────────└─────┬─────┘
   │ released │                                                   │ 通過
   │ 解除     │   心跳失敗、節點換了、allow 變 false、迴圈、竄改   ▼
   │（帶原因）│ ◀───────────────────────────────────────── ┌──────────┐
   └────┬─────┘                                            │ chained  │ 每 5 分鐘心跳、登記、同步共用結果
        │ 重試計時到／下一次路徑檢查 ──▶ detected           │ 串接中   │
        │                                                  └────┬─────┘
   none ◀──────────────── wan-changed、chain 關掉 ──────────────┘
```

| 狀態（`state`） | 意思 | 解析行為 |
|---|---|---|
| `none` 未偵測 | 沒有攔截、攔截者不是黑潮、還沒檢查過、或 `chain` 關著 | 跟 3.3.7 一樣 |
| `detected` 偵測到 | 路徑檢查認出上游黑潮（≥ 3.4.0），正在探測 | 同上 |
| `verifying` 驗證中 | 探測通過，做綁定前的最後確認（幾秒） | 同上 |
| `chained` 串接中 | 上游黑潮是第一順位上游，共用結果由它提供 | 見 1.6 |
| `released` 解除 | 串接不成立或中斷，`reason` 寫原因 | 跟 3.3.7 一樣 |

沒有「等待同意」的狀態，也不存任何同意紀錄。

`released` 的 `reason`：

| 代碼 | 意思 | 之後 |
|---|---|---|
| `upstream-too-old` | 上游黑潮低於 3.4.0（只認得 `version.kuroshio`） | 不發挑戰；下一次路徑檢查再看版本 |
| `unsupported` | 版本夠新但挑戰沒有回應、格式不對、`v` 太新 | 10 分鐘後重試一次，之後跟著路徑檢查 |
| `not-allowed` | 上游的 `allow_downstream` 關著（上游不提供資料） | 每 10 分鐘（加 0～20% 亂數）探測一次，上游重新開放就自動接回（3.4.2；3.4.0／3.4.1 跟著路徑檢查重試，最久 6 小時）。下游自己做評測、CDN 掃描、下載清單，狀態頁寫明會重複使用網路 |
| `verify-failed` | 簽章不對、nonce 不符、公鑰與 `kid` 不符 | 60 秒起重試，每次加倍，最長 10 分鐘 |
| `pin-mismatch` | 上游的指紋跟設定的 `chainPin` 不符（3.4.4；3.4.3 算成 `verify-failed`） | 同上；不向它登記主機名稱 |
| `upstream-changed` | 心跳回來的公鑰跟綁定的不同 | 立刻回到 `detected` 重新走一次，**自動綁定到新的公鑰**，記警告並在 `warnings` 留 24 小時 |
| `no-response` | 心跳連續 3 次沒回應 | 改用自己的加密上游；60 秒起重試，最長 10 分鐘，上游回來自動接回 |
| `gone` | 路徑檢查：不再被接走，或攔截者不是黑潮了 | 回 `none` |
| `loop` | 上游的 `path` 裡有自己 | 10 分鐘後重試 |
| `too-deep` | 上游的 `path` 已經有 4 層（加上自己會超過上限） | 同上 |
| `tampered` | 路徑檢查發現攔截者竄改答案或改寫「不存在」 | 下一次路徑檢查沒問題才重試 |

**公鑰的連續性**：綁定時記住上游的公鑰（只在記憶體，跟著行程層級的串接狀態跨重新載入；重開機後重新認）。之後心跳的公鑰不同（上游重灌、換機器、金鑰輪替、或有人冒充）一律當成「上游換了」：自動重新綁定到新的，記一行警告（含新舊指紋），`/api/status` 的 `warnings` 留 24 小時。
3.4.0 **不驗證上游的金鑰輪替聲明**：輪替後的效果就是上面這個警告。

### 1.5 探測與驗證的步驟

接在路徑檢查之後（`pathcheck::run_once()` 套用結果之後呼叫），**不是另一個排程**：

1. 路徑檢查的結果不是「IPv4 的一般 DNS 被接走＋攔截者是 `Interceptor::Kuroshio(版本)`」→ `none`（原本是 `chained` 就先解除，原因 `gone`）。3.4.0 只走 IPv4 那條路。
2. 版本低於 3.4.0 → `released(upstream-too-old)`，結束。版本字串取開頭的數字部分比較（`3.4.0-rc1` 算 3.4.0）。
3. 路徑檢查有 `tampered` 或 `nx_rewrite` 而且 `via = "interceptor"` → `released(tampered)`，結束。
4. **探測**：對命中的保留位址發 auth 挑戰（UDP 被接走用 UDP，只有 TCP 被接走用 TCP；逾時 1.5 秒，失敗再試一次）。驗證：
   `Sealed` 解得開 → `body.t == "auth"`、`v == 1` → `nonce` 相同 → `kid == kid_of(pub)` → `verify(pub, 簽章輸入, sig)`。任何一步不過 → `verify-failed`（沒回應是 `unsupported`）。
5. `allow == false` → `not-allowed`。`path` 裡有自己的 `kid` → `loop`。`path.len() >= 4` → `too-deep`。
6. 探測通過 → 直接進 `verifying`（沒有同意的步驟）。探測結果（指紋、`allow`、版本）不管走到哪個狀態都放進 `/api/status`。
7. **驗證（`verifying`）**：
   - 再發一次新的挑戰（新的 nonce），公鑰必須跟探測時相同。
   - 預設閘道存在、是私有位址：對 `閘道:53` 直接發一次挑戰。回來的公鑰相同 → 綁定位址用閘道（`via = "gateway"`）；不同或沒回應 → 綁定位址用命中的保留位址（`via = "intercept"`）。
   - 通過 → `chained`，並在 5～15 秒後（隨機）提早做一次心跳，縮短兩台同時互相綁定時的迴圈時間。
   - 綁成經攔截之後，知道閘道了還會再試一次直連（3.5.0，見 1.6 的「經攔截綁定後改成直連閘道」）；直連剛失敗過的 1 小時內這一步不試閘道。

**心跳**：`chained` 之後每 300 秒（±30 秒）對綁定位址發一次挑戰。公鑰不同 → `upstream-changed`；`allow` 變 `false` → `not-allowed`；`path` 檢查同上；連續 3 次沒回應 → `no-response`。
另外，解析流程發現串接上游連續失敗 3 次時（見 1.6）立刻補一次心跳，不等 5 分鐘。

### 1.6 綁定：用什麼位址與協定

**建議：一般 DNS（UDP，只有 TCP 被接走時用 TCP），位址優先用驗證過的預設閘道，否則用命中的保留位址。**

| 做法 | 優點 | 缺點 |
|---|---|---|
| 一般 DNS 到閘道／保留位址（建議） | 任何上游設定都能用（不需要上游開加密監聽、不需要憑證）；下游完全不做 TLS，正是 MT7621 這類機器要的；閘道直連不依賴 DNAT 規則一直存在 | 每一筆查詢沒有驗證：同一個區網裡能做 ARP 欺騙的裝置可以竄改答案（見 8.1 的 T3） |
| 上游的 DoT／DoH | 每筆查詢有完整性與私密性 | 上游的加密監聽預設沒開；憑證綁的是上游的公開網域，下游只知道閘道 IP，要另外做「簽章公告的 SPKI 釘選」才驗得過；多一條 TLS 驗證路徑要維護 |

理由：上游區網裡的其他裝置本來就是用一般 DNS 問這台上游，串接沒有讓下游比它們更弱；被犧牲的是「下游原本走加密上游、不受區網內主動攻擊影響」這一點（見 8.1 的 T1、T3）；因此上游一有異狀（沒回應、竄改、公鑰換了）就退回或警告，而且兩邊各有一個開關可以關掉。
`AuthBody` 預留欄位 `dot`（`{ "port": u16, "spki": bytes(32) }`），3.4.0 的上游不送、下游忽略；之後要加「釘選公鑰的 DoT」不用改協定版本。

綁定的實作（`upstreams.rs`）：

- 新的 `Role::Chain`（`name()` = `"chain"`）。`Manager` 多一個 `chain: RwLock<Option<ChainSlot>>`，由串接模組用 `Manager::set_chain()` 設定／清除，不寫進設定檔。
- 上游規格字串：`udp://<位址>:53` 或 `tcp://<位址>:53`，用現有的 `Upstream::parse`。跟使用者的 `upstream.pinned` 裡某一筆 `id` 相同時不重複加入。
- `Up::via_interceptor()` 對 `Role::Chain` 回 `false`（它就是我們要的那台，`decide()` 不能把它的答案排到後面）。
- `Manager::active()`（串接中、串接上游沒暫停）＝ `[串接上游] + 使用者的固定上游`。**自動上游不問。**
- `Role::Chain` 連續失敗 3 次 → 暫停（`open_until`），並通知串接模組立刻做心跳。暫停期間 `active()` 跟沒串接時一樣（固定 + 自動），所以只有前 3 筆查詢會等到逾時。暫停時間 30 秒起、每次加倍、最多 10 分鐘（3.4.3）；中間穩定 10 分鐘才重新從 30 秒算。暫停 5 次（`CHAIN_RELEASE_TRIPS`）就解除串接（`no-response`），照退避重試：心跳正常、查詢卻一直失敗時，以前每 30～45 秒暫停、接回一次，沒有盡頭。
- `Manager::backup()`（串接中）＝ 沒暫停、`path_blocked()` 為否的自動上游 ＋ 備援 ＋ 最後手段，全部去掉 `via_interceptor()` 為真的（一般 DNS 會回到同一台掛掉的上游）。
- **上游掛掉時退回自己的加密上游是固定行為，不是開關**（原本構想的 `chain_backup` 不做）。
- **串接上游的回答怎麼用**（3.4.2）：
  - SERVFAIL：**下游自己再解析一次**（3.4.3）：用自己的上游（`backup()`）問；自己的上游也解析不到才照上游的 SERVFAIL。不算串接失敗。自己的上游問了兩台以上、只有一台回否定答案（NODATA／NXDOMAIN，其他沒回應或也解析不到）時不採用，照上游的 SERVFAIL（3.4.4：權威伺服器掛掉的網域偶爾有一台回空答案，裝置會以為「網域存在、沒有這種記錄」）；這一輪自己的上游沒回應也跟 SERVFAIL 一樣，同一輪有別台正常回答才算失敗（3.4.4：串接中自己的上游只收到這些壞網域，以前逾時一直累積、被暫停）。來源標成「…(上游解析不到，改用自己的上游)」，次數在 `stats.today.chainRetry`。3.4.2 把 SERVFAIL 當成最後答案：上游黑潮自己的上游壞了、心跳卻正常時，下游每一筆都 SERVFAIL、永遠不會退回自己的上游。
  - 上游擋掉非 A／AAAA 的查詢（空答案＋EDE 15／17）：當成「擋掉」，照下一條處理（3.4.3；以前當成 NODATA 直接回給裝置）。
  - 擋掉（0.0.0.0、`::`）：**下游自己決定**。下游的過濾沒擋（下游的過濾在問上游之前就先查），就用自己的上游（`backup()`）解析一次；自己的上游也沒有答案時，才照上游的擋。上游的過濾是上游的政策，下游有自己的 DoT／DoH，要不要擋由下游的清單決定。不算串接失敗，不暫停串接。
  - 一般 DNS 被上游接走時，`backup()` 本來就去掉 `via_interceptor()` 的明文上游，繞過只走下游自己的加密上游，不會回到上游形成迴圈。
  - 繞過的答案照常進快取（同一個名稱 TTL 內不再問任何上游）。串接中不做 CDN 改寫、不做 TCP 443 測速排序（下游保持輕量），不做背景補問。來源標成「…(上游擋，改用自己的上游)」。
  - 上游完全沒回應（逾時）：那一筆改問自己的上游，連續 3 次暫停 30 秒（同上）。
- 解析流程其他地方把 `Role::Chain` 當成固定上游以外的一般上游：可以當快速回應；不參與 `pinned_alias` 的剔除；`baseline`（「如果用一般 DNS 會怎樣」）不採計它的答案。
- 串接中 `pathcheck::warnings()` 不再列「一般 DNS 被…接走」那一條（這是預期中的狀況），改由串接狀態說明。

**經攔截綁定後改成直連閘道**（3.5.0）：

- 以前：只有綁定的那一刻會試閘道。開機時路由表還沒好、第一次路徑檢查沒拿到閘道，就綁成經攔截；之後的路徑檢查就算拿到閘道，
  串接中也什麼都不做，一直經攔截（依賴上游的 DNAT 規則一直存在、TCP 不一定可用、狀態頁只能寫「閘道或更上游」）。
- 現在：串接中、綁的是經攔截、知道閘道（私有位址、不等於綁定位址）時，在 (a) 路徑檢查的新結果進來、(b) 心跳成功 這兩個時機
  對 `閘道:53` 直連發一次挑戰（`Io::ProbeGateway`，跟綁定位址同一種協定）。
- **驗證通過才換，跟初次綁定同一個標準**：簽章驗證通過、公鑰跟目前綁定的**相同**（同一把金鑰＝同一台上游）、`allow = true`、
  鏈上沒有自己、不會太深、符合 `chainPin`。通過 → 只換位址：`via = "gateway"`、TCP 一定可用，`Manager::set_chain()` 換上游位址；
  串接沒有中斷（狀態一直是 `chained`，`since`、心跳的計時與失敗計數、金鑰換過的紀錄都不動），日誌一行「從經攔截改成直連閘道」。
  任何一項不符（閘道是別台、沒回應、不開放）→ 維持經攔截，什麼都不改；兩層 NAT、攔截者在更上游時這本來就是對的。
- 串接上游正在暫停（查詢連續失敗）時不探測、不換，一分鐘後再看。
- **不來回**：
  - 嘗試的間隔下限 10 分鐘；探測沒過時每次加倍（10、20、40 分鐘 … 最多 6 小時），閘道換了重新算。一次嘗試只有一筆 CH TXT 查詢（沒回應再一筆）。
  - 直連的綁定（升級來的或初次綁定的都算）不到 1 小時就因為沒回應（心跳連續 3 次、或查詢暫停 5 次）或驗證不過而解除：記一次「直連失敗」，
    **1 小時內不用直連**——重試時驗證不試閘道、綁回經攔截，路徑檢查與心跳也不升級。連續 3 次之後改成 **24 小時**一次
    （原規劃是「這次行程不再嘗試」；改成一天一次，直連的路修好之後會自己恢復，頻率仍然有上限）。
  - 直連維持 1 小時以上才算穩定，失敗次數歸零；穩定之後才中斷的（上游重開機）不算直連失敗。
  - WAN 變動、`chain` 關掉時清掉這些紀錄。都只在記憶體（行程層級，跨重新載入、不跨重開機）。
- 換位址時串接上游的暫停次數帶過去（`set_chain()`），不會因為換一次位址就把 `CHAIN_RELEASE_TRIPS` 的計數歸零。
- 共用結果的同步、登記都是對綁定位址發查詢：換了之後下一次用新位址（上游依來源位址記下游，目的位址換了不影響）。協定沒有改，3.4.x 的上游也適用。
- 最壞情況是維持經攔截，或直連失敗後照既有流程解除、退回自己的上游再接回經攔截。

**跨重新載入**：串接狀態放在行程層級的持有者（做法同 `CACHE_HANDOFF`），新的一輪建立 `Manager` 之後立刻把綁定接回去，不出現空窗；接回後在背景做一次心跳。

### 1.7 防迴圈

- 每個節點的 `path` ＝（自己串接中的上游的 `path`，沒串接就是空的）＋ `[自己的 kid]`。上游的 `path` 每次心跳更新，所以鏈的變動最慢 5 分鐘傳到下一層。
- 下游在探測、驗證、每次心跳都檢查：`path` 裡有自己（含金鑰輪替 7 天內的舊 `kid`）→ `loop`；`path.len() >= 4` → `too-deep`。**上限是 4 層**（家用環境兩層，三層已經少見；每多一層多一次轉送延遲）。
- A→B→A 的情形：B 串接 A 之後，B 回給別人的 `path` 是 `[A, B]`；A 若偵測到自己被 B 接走而去問 B，會在 `path` 裡看到自己而拒絕。
- 兩台同時互相綁定（都還沒有對方的 `path`）：綁定後 5～15 秒的提早心跳會讓其中一台看到自己而解除。這段時間內的查詢不會放大：`Resolver::fetch` 的 singleflight 讓同一個名稱同時只問一次，互相等待到 `timeoutMs` 後回 SERVFAIL。
- 不在每筆查詢上加跳數標記：多一個 EDNS 選項會讓每筆查詢變大、也讓上游的快取鍵與 3.3.x 的行為變複雜，鏈上的檢查已經足夠。

### 1.8 自動解除

| 事件 | 動作 |
|---|---|
| 心跳的公鑰跟綁定的不同（上游換掉） | `released(upstream-changed)` → 立刻回 `detected` 重新探測、自動綁定新的公鑰，警告留 24 小時 |
| 心跳連續 3 次沒回應 | `released(no-response)`，自動上游接手；60 秒起重試 |
| `kuroshio notify wan-changed`（`/api/notify/wan-changed`） | 立刻回 `none`（拿掉串接上游），接著原本就會觸發的路徑檢查重新偵測、自動接回 |
| 路徑檢查：不再被接走／攔截者不是黑潮／版本變舊 | `released(gone)` → `none` |
| 路徑檢查：攔截者竄改答案 | `released(tampered)` |
| 設定改成 `chain` 關（重新載入） | `none`，不再發任何串接查詢；共用結果不再同步，自己的工作照排程跑 |
| `path_check = 0` | 串接整個不啟用（沒有偵測來源）；狀態頁說明原因 |

解除時：`Manager::set_chain(None)`、清掉 DNS 快取裡來源是串接上游的項目不需要（答案仍然有效，照 TTL 過期）、共用結果依第 3.6 節處理。

### 1.9 上游端

- `resolver.rs::handle_inner` 在 `version.kuroshio` 那一段之後：`qclass == 3` 而且名稱是 `chain.kuroshio` 或它底下的 → 交給 `chain::Responder`，**不論結果都不往下走**（不過濾、不快取、不轉給上游）。
- 條件同 `version.kuroshio`：`proto ∈ {udp, tcp}`、`is_private_client`。不符合回 `REFUSED`。
- `allow_downstream = false`：只回答 auth（`allow: false`、`caps: []`），其他 `REFUSED`。
- 速率限制（簽章要花 CPU）：每個來源位址每秒 4 次、可累積 8 次；全部來源合計每秒 32 次；超過回 `REFUSED`。來源表最多 64 筆，滿了丟最久沒用的。
- 金鑰：第一次需要時 `Identity::load_or_create(community.dir)`（社群共享沒啟用也一樣；跟社群共享是同一把）。每次心跳／每 5 分鐘看 `key.pem` 的修改時間，變了就重讀（社群共享做了金鑰輪替）。
- 上游自己同時也可以是別人的下游（三層）：`path` 取自它自己的串接狀態。

### 1.10 `check-path` 與狀態頁

`kuroshio check-path`（不需要服務在跑）在攔截者是黑潮 ≥ 3.4.0、而且自己的 `chain` 開著時多做一次探測，文字輸出多一行，`--json` 多 `interceptor.chain`：

```
一般 DNS：被路由器 192.168.1.1 上的黑潮（3.4.0）接走
串接：上游提供資料給下游（節點指紋 3F2A-91C0-77B1-0C4E-5D21-9A60-E3F8-12AB）
```

其他情形的文字：`上游不提供資料（上游的 allow_downstream 關閉）：這台會自己做評測，重複使用網路`、`上游黑潮 3.3.7 不支援串接（需要 3.4.0 以上）`、`上游沒有回應串接查詢`、`這台的 chain 關閉：不辨識上游黑潮`（這時不發探測）。

`/api/status` 的 `network.path.interceptor` 多一個 `chain`（還沒探測過、或 `chain` 關著是 `null`）：

```json
"interceptor": {
  "kind": "kuroshio", "version": "3.4.0",
  "chain": { "supported": true, "allowDownstream": true, "nodeId": "a1b2c3d4e5f60718",
             "fingerprint": "3F2A-91C0-77B1-0C4E-5D21-9A60-E3F8-12AB", "caps": ["share", "reg"], "error": null }
}
```

`/api/status` 新增頂層 `chain`（下游與上游兩種角色都在這裡；沒有的部分是 `null`）：

```json

  "self": { "nodeId": "0f1e2d3c4b5a6978", "fingerprint": "…", "version": "3.5.0", "depth": 2 },
  "enabled": true,

  "text": "串接中：上游 192.168.1.1（黑潮 3.4.0），評測結果與 CDN 節點由上游提供",

    "address": "192.168.1.1", "proto": "udp", "via": "gateway",

    "keyChangedAt": null, "previousFingerprint": null,

  "retryAt": null,
```

- `self`（3.5.0 E13）：這台自己的節點 ID、指紋、版本、層數（串接中等於 `upstream.depth`，沒有串接是 1）。`chain` 關著、回應器沒有建立時也有；還沒有節點金鑰時 `nodeId`、`fingerprint` 是 `null`（不為了這個建立金鑰檔）。畫拓樸圖（自己＋往上每一層＋直接的下游）時跟 `upstream.path`、`serving.downstreams[].nodeId` 對起來；下游的下游、`path` 裡更上層的版本與位址不提供。
- `enabled`：下游的 `chain` 開關。
- `text` 是給狀態頁直接顯示的一行白話，**每一種情況都要看得出原因與影響**：

| 情況 | `state`／`reason` | `text` |
|---|---|---|
| 兩邊都開、串接成功 | `chained` | `串接中：上游 192.168.1.1（黑潮 3.4.0），評測結果與 CDN 節點由上游提供` |
| 上游的 `allow_downstream` 關 | `released`／`not-allowed` | `上游黑潮 3.4.0 不提供資料（allow_downstream 關閉）：自己做評測，會重複使用網路` |
| 自己的 `chain` 關、路徑檢查認出上游黑潮 | `none` | `已關閉串接（chain 關閉）：把上游黑潮當成一般的 DNS 攔截，自己做評測，會重複使用網路` |
| 自己的 `chain` 關、沒有上游黑潮 | `none` | `已關閉串接（chain 關閉）` |
| 上游版本太舊 | `released`／`upstream-too-old` | `上游黑潮 3.3.7 不支援串接（需要 3.4.0 以上）` |
| 上游沒回應 | `released`／`no-response` | `串接中斷：上游沒有回應，暫時用自己的加密上游` |
| 上游的公鑰換了（24 小時內） | `chained` | `串接中：上游 192.168.1.1（黑潮 3.4.0）；上游節點的金鑰換過（…時間），如果不是你換的請檢查上游` |
| 沒有攔截／不是黑潮 | `none` | `沒有偵測到上游黑潮` |

  `via = "intercept"` 時位址顯示閘道並加註「（經攔截）」；讀不到閘道（Windows）時顯示 `上游黑潮`。
- `upstream.direct`（3.5.0；沒試過是 `null`）：`{ lastTryAt, lastResult, upgradedAt, failures, blockedUntil }`。`lastResult`：`upgraded`（已從經攔截改成直連）、`other-key`（閘道是別台黑潮）、`no-response`、`verify-failed`、`not-allowed`、`loop`、`too-deep`、`pin-mismatch`、`suspended`（串接上游暫停中，沒有探測）、`direct-failed`（直連沒多久就中斷，`blockedUntil` 之前不用直連）；`failures` 是連續幾次直連沒多久就中斷。
- `upstreams[]` 裡串接上游的 `role` 是 `"chain"`。
- `chain` 關著而且沒有上游角色的資料時，`chain` 仍然是完整的物件（`enabled: false`、`state: "none"`、其他欄位是 `null`），方便前端。

| 路徑 | 說明 |
|---|---|
| `GET /api/chain` | 同 `/api/status` 的 `chain` |
| `POST /api/chain/recheck` | 立刻做一次路徑檢查與探測 |

### 1.11 設定

**只有兩個開關，都在 `config upstream 'upstream'`，預設都開。**

| UCI | JSON | 預設 | 角色 | 意思 |
|---|---|---|---|---|
| `chain` | `upstream.chain` | `1`／`true` | 下游 | 要不要辨識上游黑潮並索取需要的資料 |
| `allow_downstream` | `upstream.allowDownstream` | `1`／`true` | 上游 | 要不要提供黑潮資料給下游 |

**`chain`（下游）**

- 開：路徑檢查認出上游黑潮（≥ 3.4.0）就驗證、自動串接、登記、拿共用結果（第 3 節）。
- 關：一律當成「一般 DNS 被接走的網路」，行為跟 3.3.7 完全一樣（路徑檢查照常、評測不測一般 DNS），不發任何串接查詢。
- 說明文字（`defaults.json` 旁的文件、UCI 預設檔的註解、LuCI／Windows 設定頁）要寫出關掉的影響：**上游是黑潮時，這台會自己重做評測、CDN 掃描、下載清單，重複使用網路。**

**`allow_downstream`（上游）**

- 開：驗證過的下游黑潮可以串接、拿共用結果（評測結果、CDN 節點池），也包含第 4 節的放行（下游的位址通過存取控制、`bypass` 清單不擋下游解析它自己上游的主機名稱）。沒有其他獨立的開關。
- 關：照樣回答「我是黑潮」（簽章的 auth 回應，`allow = false`、`caps` 是空的），但不提供任何資料、不接受登記。
- 說明文字要寫出兩件事：
  - 關掉的影響：**下游黑潮會自己重做評測、CDN 掃描、下載清單，重複浪費網路資源（含這台上游的頻寬）。**
  - 開著的意思：區網裡任何會講這個協定的裝置都拿得到資料與放行（見 4.1、8.1 的 T8）；有啟用「繞過防護」清單、要管住區網裝置的環境請關掉。

**兩邊都開才通訊**：

| 下游 `chain` | 上游 `allow_downstream` | 結果 |
|---|---|---|
| 開 | 開 | 串接、登記、共用結果 |
| 開 | 關 | 下游探測一次（之後每 10 分鐘再探測一次，3.4.2），得到 `allow = false` → `released(not-allowed)`，自己算；除了探測沒有其他串接流量 |
| 關 | 開或關 | 下游不發任何串接查詢；上游看不出下游是黑潮 |

沒做成開關的：上游掛掉時退回自己的加密上游（固定行為）、串接就共用結果（固定行為）、沒有同意流程。

型別容忍（兩個都是布林，讀取端用同一個函式 `flex_bool`）：布林；字串 `"1"`／`"0"`／`"on"`／`"off"`／`"true"`／`"false"`／`"yes"`／`"no"`；數字（0 = 關，其他 = 開）。其他寫法（含早期草稿的 `"auto"`、`"ask"`）→ 預設值（開）並記一行警告。

UCI 的轉換：兩個選項都在 `upstream` 區段，`uci.rs::apply` 的 snake_case → camelCase 自動對到 JSON 名稱，`defaults.json` 的預設是布林，`option chain '0'` 會轉成 `false`；JSON 設定檔寫數字 `0` 或字串 `"0"` 也要能讀。

## 3. 共用結果（串接就共用）

### 3.1 目標

`chained` 而且上游的 `caps` 有 `"share"` 時，下游向上游拿：

| 種類（`k`） | 內容 | 下游省掉的工作 |
|---|---|---|
| `upstreams` | 上游的 `upstreams.json`（每日評測結果） | `dns-benchmark`（最長 150 分鐘） |
| `cdn-pools` | `cdn/pools.json`（台灣節點池） | `cdn-pool`、`cdn-scan` |
| `cdn-v6` | 永久 IPv6 節點（`v6store::FILE`） | 同上 |
| `cdn-ranges` | `cdn/ranges/*.txt`（官方範圍），包成一個 JSON：`{ "files": { "cloudflare-ipv4.txt": "…" } }` | `cdn-ranges` |
| `filter-copy` | **3.4.0～3.4.2**：一份過濾清單的本機副本（zstd 壓縮的原始清單；`name` 是清單網址）。3.4.3 起上游不提供、下游不接收 | 下載那一份清單 |

兩台在同一條對外線路上，上游量到的延遲、CDN 節點品質對下游同樣成立。

**3.4.3 起過濾清單不共用**：每台黑潮自己跟清單網址下載。原因：下游只驗得出「這是那台上游給的、路上沒被改」，驗不出上游給的就是清單作者發布的正本（串接的金鑰是各台自己產生的，「驗證過」只證明對方會講這個協定）；而過濾清單決定這台擋什麼，偽裝的上游可以讓下游多擋、少擋，而且一直持續到解除串接。下載一份清單只是一個 HTTPS 請求、大多回 304，不像評測會對大量伺服器查詢，不共用也不違反「不當攻擊者」。代價：存不下副本的小 Flash（D3）每次重新啟動要自己下載一次（約 9 MB）；串接中的查詢還是先經過上游黑潮，清單載入前沒有空窗。新版上游的清單不列 `filter-copy`；舊版上游的清單裡有，新版下游照「不認得的種類」略過。舊版下游接新版上游：上游沒有副本，照舊自己下載。下面關於 `filter-copy` 的規則是 3.4.0～3.4.2 的設計，留著對照。

**過濾清單共用的是「清單副本」，不是建好的過濾器**：過濾器是記憶體裡的雜湊結構，沒有序列化格式，另訂一個格式要長期維護；副本是現成的（`filter-lists/<網址雜湊>.txt.zst`），下游用現有的「從副本建」路徑就能吃。上游沒有留副本（儲存空間不夠）或兩邊訂閱的網址不同的清單，下游照舊自己下載。

### 3.2 通道與驗證

走第 1.2 節的 `s.chain.kuroshio`，**只接受 TCP**（UDP 回 `REFUSED`）。保留位址的 TCP 沒被接走、而且沒有驗證過的閘道直連時，共用結果不可用（`shared.error = "no-tcp"`），下游自己算。

1. 下游問 `m.s.chain.kuroshio` → `Sealed`（`kind = "manifest"`），用**綁定的上游公鑰**驗簽。
2. 清單列出每個物件的雜湊；下游只抓雜湊跟上次不同的物件：依序問 `0.<oid>…`、`1.<oid>…`，每段 32,768 bytes（最後一段較短），接起來算 SHA-256，必須等於清單裡的 `sha`。
3. 分段本身不簽章：內容位址（`oid` 是雜湊的前 8 bytes）加上簽過的清單已經保證完整性，路上的人改不了。

ManifestBody：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `v` | u8 | `1` |
| `t` | text | `"manifest"` |
| `kid` | bytes(8) | 上游節點 ID |
| `at` | u64 | 產生時間（Unix 毫秒，顯示用） |
| `app` | text | 上游版本 |
| `objects` | [Object] | 最多 64 個 |

Object：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `k` | text | 種類（見 3.1）。不認得的種類略過 |
| `fmt` | u8 | 這個種類的格式版本，3.4.0 都是 `1`。比自己認得的大 → 略過這個物件 |
| `id` | bytes(8) | `sha` 的前 8 bytes（就是名稱裡的 `<oid>`） |
| `sha` | bytes(32) | 傳輸內容（壓縮後）的 SHA-256 |
| `size` | u64 | 傳輸內容的大小 |
| `raw` | u64 | 解壓縮後的大小 |
| `enc` | text | `"zstd"` 或 `"none"` |
| `name` | text | `filter-copy`：清單網址；其他種類是空字串 |
| `at` | u64 | 資料的時間（`upstreams`：評測的 `generatedAt`；其他：檔案時間） |
| `rules` | u64 | 只有 `filter-copy`：規則數（下游估記憶體用） |
| `hash` | text | 只有 `filter-copy`：原始內容的雜湊（`CopyMeta.hash` 的 16 個十六進位字），下游存副本時原樣記下 |
| `etag`、`lastModified` | text | 只有 `filter-copy`：上游下載時拿到的驗證資訊（可以是空字串），下游之後自己下載時拿來問 304 |

### 3.3 上游端

- 第一次有人問清單時才產生，放在記憶體裡的 `ShareCache`；10 分鐘內重複問直接回同一份，超過 10 分鐘重新產生；30 分鐘沒人問就整個釋放。下游登記成功時也先在背景產生（3.5.0）：下游綁定後約 30 秒才第一次同步，那時通常已經建好，不必先回 `REFUSED`。
- `upstreams`、`cdn-pools`、`cdn-v6`、`cdn-ranges`：產生清單時讀進記憶體、用 zstd 壓縮後留著（實測種子資料：7 KB、72 KB、110 KB、76 KB，壓縮後合計約 80 KB）。**上限合計 1 MiB**，超過的種類不列進清單。
- `filter-copy`：不進記憶體。清單只記檔名、大小與雜湊（第一次用串流算，結果跟 `CopyMeta.hash` 一起記著，副本沒變不重算）；分段請求時從檔案的對應位置讀 32 KiB。單一副本（壓縮後）超過 8 MiB 不分享。
- 分段請求的物件不在目前的 `ShareCache` 裡 → `NXDOMAIN`（rcode 3），下游重新拿清單。
- 沒有資料的種類不列（例如還沒評測過、CDN 沒啟用）。`upstreams.json` 是從種子來的（沒有 `generatedAt` 或 `selected` 是空的）也不列。
- 同時最多 2 條在傳分段的 TCP 連線；每個來源每秒最多 64 段。記憶體壓力不是 `Normal` 時清單回 `REFUSED`（下游晚點再來）。

### 3.4 下游端

- 時機：進入 `chained` 後 30 秒做第一次；第一次遇到 `REFUSED`（上游還在建清單）時隔 5、15、30 秒再試（各加 0～20% 亂數，連續最多 3 次，3.5.0；以前每次 30 秒），之後回到正常間隔；之後每 6 小時（±10 分鐘）拿一次清單。上游的評測在 04:10、節點池在 05:30，最慢 6 小時後拿到新資料。記憶體壓力不是 `Normal`、時鐘沒對時不影響（不靠 TLS）；壓力大時延後 10 分鐘。
- 一次處理一個物件，處理完才抓下一個。順序：`upstreams` → `cdn-ranges` → `cdn-pools` → `cdn-v6` → `filter-copy`。
- 匯入前的檢查（任何一項不過就丟掉這個物件、記在 `shared.objects[].error`，**不影響其他物件**）：

| 種類 | 檢查 | 匯入方式 |
|---|---|---|
| `upstreams` | 解壓後 ≤ 256 KiB；是 JSON 物件、`selected` 是陣列、1～64 筆、每筆的 `id` 能用 `Upstream::parse` 解析而且 `supported()` | 拿掉 `type` 是 `udp`／`tcp` 的（對下游來說都會回到上游自己）；加上 `"source": { "chain": "<上游 kid>", "at": <時間> }`；寫到下游自己的 `upstream.autoStateFile`，`Manager::reload_auto()` 照檔案時間重讀。`autoTypes`、`autoMax` 照下游自己的設定再篩一次（現有行為） |
| `cdn-ranges` | 解壓後 ≤ 2 MiB；檔名只能是 `[a-z0-9-]+-ipv[46]\.txt`；每行是合法的 CIDR | 寫到 `state/cdn/ranges/`，呼叫 `Cdn::reload_ranges()` |
| `cdn-pools` | 解壓後 ≤ 1 MiB；能解析成 `PoolsFile`、不是空的；每家最多 `pool.poolSize × 4` 個節點；節點位址必須在那一家的官方範圍裡（`Pools::in_ranges`） | `Cdn::import_shared()`（新函式）換掉記憶體裡的節點池並標成 dirty，照平常的快照流程寫出；15 秒後重新量一次健康與品質（同 `cdn-pool` 工作結束後的做法） |
| `cdn-v6` | 解壓後 ≤ 1 MiB；`V6Store::from_json` 解析得過 | 同上 |
| `filter-copy` | `name` 是下游自己有啟用的清單網址；`size` ≤ 8 MiB、`raw` ≤ 64 MiB；記憶體控制允許（`rules × BUILD_BYTES_PER_RULE` 放得下） | 見下 |

- **過濾清單副本**：
  - 下游留得下副本（`ListCopies::wanted(size)` 為真）：分段抓下來（壓縮後的內容暫時放在記憶體，最多 8 MiB，跟現在下載清單時 `CopySink` 的做法一樣），雜湊驗過之後原樣交給 `ListCopies::offer()` 存成本機副本（不解壓、不重新壓縮），全部抓完後用「副本優先」重建一次過濾器（現有的 `Source::PreferCopy` 路徑）。
  - 留不下副本（小 Flash，3.4.2 起）：照樣分段抓，雜湊驗過之後**留在記憶體**（`FilterService` 的 `held`，壓縮後的原樣），重建過濾器時讀它、不從網路下載；不存檔，重新啟動後再跟上游拿一次（區網）。
    - 條件：記憶體還能長大（`memgov::growth_allowed()`），而且留著的合計（壓縮後）加上這一份不超過 8 MiB；不符合時才是 `no-room`，下游照舊自己下載。
    - 之後空間夠、存成本機副本時，記憶體裡那份就釋放。
    - 狀態：`/api/status` 的 `filter.heldCopies`（`count`、`bytes`）。
    - 原因：3.4.0 的「不抓、自己下載」讓 7.5 MB 狀態分割區的 D3 每次重新啟動都從網路整份下載約 9 MB（10 份清單只有 5 份存得下）。用幾 MB 記憶體換，串接中的下游重新啟動後對外流量接近 0。
  - 「跟上游一樣、不用傳」要本機副本的**檔案還在**：只比索引裡的雜湊不夠（空間不夠時副本檔會被刪掉、索引還留著，3.4.2 以前會因此跳過傳送、重建時又從網路下載）。記憶體裡留著同一個雜湊的也算一樣。
  - 雜湊沒變不重抓的規則，清單副本**只看這台真的有沒有一樣的內容**（上一條：本機副本檔或記憶體裡的），不看 `chain-share.json` 記的雜湊：只留在記憶體的副本重新啟動後就不見了，紀錄還在（3.4.2 以前會因此不再跟上游要、改從網路下載，padavan-tw 實測 10.2 MB）。其他種類照舊看紀錄的雜湊。
  - 下游自己的清單更新排程照常跑；副本是 6 小時內從上游拿到的清單，這一輪跳過下載（當成 304）。
  - 開機後的第一次清單更新先等：還不知道會不會串接（第一次路徑檢查還沒做完，`chain::deciding()`）、正在驗證上游黑潮、或已經串接但還沒同步過（`chain::share_pending()`），合計最多 10 分鐘（`chain::filter_wait()`，3.4.2；以前只看 `share_pending`，路徑檢查還沒做完時判斷成不用等）。只在開機時已經用本機副本建好過濾器時才這樣等；一份副本都沒有（第一次安裝）時照舊只等 `share_pending`，不讓過濾在這段時間完全沒有清單。
- **不採用 hosts 檔的 IP**：共用的節點池是上游實測的 CDN 節點，匯入時再用官方範圍檢查一次；清單副本只當過濾規則用，裡面的位址不會變成答案或節點。串接上游的位址只來自路由表的預設閘道與路徑檢查，不讀系統的 hosts 檔。

### 3.5 跳過自己的工作、退回自己算

`chain-share.json`（快照目錄，幾百 bytes）記每個種類最後一次成功匯入的時間與雜湊。

- 「新鮮」＝ 36 小時內成功匯入過，而且現在是 `chained`。
- `dns-benchmark`：`upstreams` 新鮮 → 這次不跑，工作狀態記「由上游黑潮提供，略過」。
- `cdn-pool`、`cdn-scan`：`cdn-pools` 新鮮 → 不跑。`cdn-ranges`：`cdn-ranges` 新鮮 → 不跑。
- 不新鮮（上游沒資料、驗證失敗、36 小時沒同步成功、串接解除、`chain` 關著）→ 工作照原本的排程跑，跟 3.3.7 一樣。
- **新鮮也不會永遠略過**（3.4.2，第 3.8 節）：這台自己上一次真的跑這個工作超過 7 天，就照排程自己跑一次。
- 串接解除時，手上的資料已經超過 48 小時 → 向排程器 `request("dns-benchmark", "串接解除")`（照排程器現有的最小間隔與延後規則，不會馬上搶 CPU）。
- 匯入的資料不刪：解除後繼續用，直到自己的工作算出新的。

格式相容：`fmt` 只在資料格式有不相容的改變時加 1；下游遇到比自己新的 `fmt` 就略過那個物件、自己算。狀態檔格式在 3.x 之間沒有變過，所以 3.4.x 之間不看 `app` 版本，只看 `fmt` 與上面的內容檢查。

### 3.6 記憶體與儲存上限

| 項目 | 上限 | 備註 |
|---|---|---|
| 上游 `ShareCache`（記憶體） | 1 MiB，30 分鐘沒人用就釋放 | 過濾清單副本不進記憶體 |
| 上游分段緩衝 | 32 KiB × 2 條連線 | |
| 下游清單 | 16 KiB、64 個物件 | 超過整份丟掉 |
| 下游非過濾類物件 | 壓縮 ≤ 1 MiB、解壓 ≤ 2 MiB；一次一個 | 尖峰約 3 MiB，處理完就釋放 |
| 下游過濾清單副本 | 一次一份；壓縮後 ≤ 8 MiB 暫存在記憶體，存成副本後釋放 | 記憶體壓力不是 `Normal` 時不抓 |
| 下游留在記憶體的清單副本（3.4.2） | 存不下副本時，壓縮後合計 ≤ 8 MiB，一直留著（重建時讀），存得下副本或重新啟動時釋放 | 記憶體不能長大、或合計超過 8 MiB 時不抓（`no-room`） |
| 單獨運作：下載到但存不了副本的清單（3.4.2） | 同一個地方、同一個上限（合計 ≤ 8 MiB）；存得下副本或重新啟動時釋放 | 記憶體「不足」時、或合計超過 8 MiB 時不留（照舊每次重建都下載）；記憶體還不能長大時照樣留（內容已經下載進來了，丟掉的話記憶體恢復時每次重建又要下載） |
| 下游 Flash 寫入 | `upstreams.json` 每天約 7 KB、範圍每週約 76 KB、節點池照平常的快照 | 內容沒變不寫 |

128 MB 的機器：非過濾類的尖峰 3 MiB 可以接受；過濾清單副本多半存不下（小 Flash），記憶體還能長大時留在記憶體（預設清單壓縮後約 4 MB），記憶體控制不允許長大時不抓、照舊自己下載。512 MB 的 D3：存不下的清單留在記憶體，重新啟動後跟上游拿，不從網路下載。

### 3.8 直系血親：繼承但查核（3.4.2）

上游給的資料預設照用（省下游的 CPU 與網路），但下游保有自己的能力，用很小的量持續核對。全部有上限，查到問題時只是回到單獨運作（本來就會走的路）。

**自己的工作定期照跑**
- `chain-share.json` 多記 `own`：每個工作（`dns-benchmark`、`cdn-pool`、`cdn-scan`、`cdn-ranges`）這台**自己真的跑完**的時間（被略過的不算）。
- 上游的資料新鮮、而且自己 7 天內跑過 → 略過（同 3.5）。自己超過 7 天沒跑 → 照排程自己跑一次（排程時段、補跑時段照舊，不會一開機就跑）。
- 第一次串接、還沒有 `own` 紀錄：記下 `ownSince`（第一次串接的時間），當成那之前 6 天跑過，也就是 24 小時後的排程時段才第一次自己跑（不在剛串接時把所有工作一起跑）。這只影響排程，不算「自己有資料」。
- 狀態：`chain.shared.ownRuns.<工作>` 的 `at`（自己真的跑完的時間）、`dueAt`（最晚什麼時候會自己跑）。
- 下游自己的評測結果比上游給的新（自己跑完的時間晚於上游資料的時間）：同步時不拿上游的評測結果蓋掉自己的（`objects[].error` 是 `own-newer`，只是說明、不是失敗），上游有更新的資料時才照常匯入。上游宣稱的時間比現在晚超過 10 分鐘時不採信、當成最舊的（3.4.3）。
- 節點池是合併的（3.4.3 起照這樣做）：上游的節點在前、這台原本的接在後面，每家上限照舊；這台記的壞節點（`bad`、`bad24`）不清掉、也不放進來。節點用這台「匯入前」的官方範圍檢查：處理順序改成 `upstreams` → `cdn-pools` → `cdn-v6` → `cdn-ranges`。
- 官方範圍：每個網段前綴至少 /8（IPv6 /16）；跟這台現有的範圍至少一半重疊才換上（這台還沒有這家的範圍時照收），不符的那一份不換、記 warn，全部不符時 `objects[].error` 是 `import-failed`（3.4.3）。
- 評測結果照這台自己的設定（`autoTypes`、`autoMax`、固定上游、支援的類型）篩完，至少要 min(`benchmark.minAuto`, 2) 台能用才匯入；不夠就不算新鮮，自己的評測照排程跑（3.4.3）。這台沒開自動上游（`autoTypes` 是空的或 `autoMax` 是 0）時不檢查。
- 「新鮮」只算目前綁定的那一台上游給的：`chain-share.json` 的每一筆多記 `kid`（上游的金鑰 ID），換了上游或金鑰，舊的紀錄不讓這台略過自己的工作（3.4.3）。上游的金鑰換了之後 24 小時內，照樣當解析的上游，但不收它的共用資料（`error` 是 `key-changed`）。
- 可選的 `upstream.chainPin`（UCI `chain_pin`）：只跟這個指紋的上游黑潮串接（寫法可以帶空格、冒號；空的＝不限定），不符時不串接（3.4.3；3.4.4 起原因是 `pin-mismatch`，也不向它登記主機名稱）。
- 下游自己關掉 CDN 置換（`cdn.enabled` 關）時，問上游黑潮的查詢帶私有 EDNS 選項 65431（`KUROSHIO_NO_CDN`），上游照原樣回答、不換台灣節點（3.4.3；上游的置換是在送回應時做的，快取存的是原本的答案）。3.4.2 以前的上游看不懂這個選項，照樣會換。各家 CDN 個別的開關、`v6Policy` 不同時不處理。

**抽查上游給的答案**
- 對象：串接上游回答的 A／AAAA，在存進快取時抽樣（1/16）。3.4.3 起不限 CDN 的答案、也不看這台有沒有開 CDN 置換（以前只查 CDN 答案，下游關掉 CDN 時對上游完全沒有查核）。
- 上限：同時最多 1 個、每 30 秒最多 1 個；記憶體壓力不是 `Normal`、系統時間沒對時、沒有串接時不做。
- 做法：
  1. 連到上游給的第一個 IP，用網域名稱當 SNI 做 TLS 握手、完整檢查憑證（`probe::verify_site`，不送 HTTP 請求）。憑證有效 → 通過；連不上、逾時 → 不判斷。
  2. 憑證不符 → 用這台自己的加密上游（`backup()`，不經攔截者）解析一次，對自己拿到的 IP 做同樣的檢查：自己的通過 → 記一次「可疑」（上游給的答案不對、自己的對）；自己的也不符 → 網站本身的問題，不算。
- 1 小時內累積 3 次可疑 → 解除串接，原因 `audit-failed`（「上游給的答案查核不通過」），6 小時後重試；同一把金鑰再不通過就 12、24 小時（最多 24 小時，3.4.3；3.4.2 是固定 10～15 分鐘，說謊的上游會讓下游一直「串接、解除」）。解除時清掉累積的次數。
- 因為「不可信」解除（`audit-failed`、`tampered`、`upstream-changed`、`verify-failed`、`pin-mismatch`）：請排程器補跑 `dns-benchmark`、`cdn-ranges`、`cdn-pool`（最小間隔照舊；3.4.3）。
- 狀態：`/api/status` 的 `chain.audit`：`sampled`（抽查）、`valid`、`unverified`、`siteInvalid`、`suspicious`、`last`（最近一次可疑：名稱、IP、時間）。

**機房以本機量到的為準**（3.5.0 E4，`cdn.popAudit`，預設開；關掉＝照收上游的機房、串接中不量）
- 匯入的節點（`import_shared()`）：上游帶來的 `upPop` 一律拿掉；這台原本就有、本機量過的節點，機房一樣就不記，不一樣就用這台的；其他記 `upPop`＝上游給的 `pop`（種子不記），上游的永久 IPv6 節點併進節點池時也記。`upPop` 跟著 `pools.json` 存，舊版讀到原樣保留。往下再分享（`export_shared()`）不帶 `upPop`。
- 比對時機（都是既有的量測）：定時健檢套用結果時、節點池工作換新節點池前（只比重新量過的節點）、**串接中的機房抽查**：上面的答案抽查握手通過之後，用同一個抽查名額（不多佔同時數、不縮短 30 秒的間隔），如果那個 IP 是 `upPop` 還在的節點（`Cdn::pop_audit_pick()`，3.5.0 F7；E4 原本的 `pop_audit_wanted()` 保留、只看答案的 IP。F7 起：不是的話改從節點池挑一個待確認的節點——每一家 CDN、每個位址族排在前 `serveCount` 名的先、各家輪流，前幾名都確認了就不再挑），對它做一次那家 CDN 的機房探測（同健檢：`Net::http_probe()` 打 `Provider.probe`），量到的交給 `Cdn::note_local_pop()`（主程式的 `resolver::pop_audit_probe()` 量的是 `pop_audit_pick()` 回傳的那個 IP）。抽查另外的上限在 CDN 那一層：10 分鐘最多 1 個、24 小時 24 個、每個節點一次（`cdn.lite`：30 分鐘 1 個、8 個）；回 `Some` 就算用掉一個名額（探測失敗也不還；前幾名都確認了、沒有對象時不用掉名額，`noTarget` 加 1）；記憶體壓力不是 `Normal`、沒對時、CDN 關、`cdn.popAudit` 關時不做。匯入一次之後抽查量自己歸零。
- 比對：一樣 → 確認、拿掉 `upPop`；不一樣但在台灣 → 改用本機的、拿掉 `upPop`、計一次不一致；不在台灣 → 照既有流程標成壞節點（`POP=xxx`）。
- 不一致**不解除串接、不記可疑**（憑證是對的、節點在官方範圍裡，機房不同是線路拓樸，例如上游有多條對外線路），列入 `findings` 的 `pop-mismatch`；24 小時內比對過的一半以上不一樣（至少 4 個）→ `chainPopUnreliable`，只暫停機房切換（規格 11 E5），24 小時沒有新的不一致自己解除。
- 狀態：`/api/status` 的 `cdn.popAudit`（`pending`、`confirmed`、`mismatch`、`probes24h`、`lastMismatchAt`、`chainPopUnreliable`；3.5.0 F7 多 `pendingServed`（前幾名裡還沒確認的）、`lastProbeAt`、`noTarget`（拿到名額但已經沒有要量的））。
  為什麼要 F7：W17 串接 80 分鐘，答案抽查做了 22 次，機房抽查卻是 `pending 129`、`probes24h 0`——答案抽查是 16 筆抽 1、不限 CDN，抽到的大多不是 CDN 答案，是 CDN 的也多半是同一兩個排最前面的節點；串接中定時健檢又不跑。名額完全不變（10 分鐘 1 個、一天 24 個），3 家 CDN × 2 個位址族 × 前 4 名 = 24 個，一天內確認完。

**不會造成的事**
- 每 30 秒最多 1 次 TLS 握手，D3 上大約是 3.4.0 下游 CPU 負擔的幾百分之一；交叉確認一次最多再多 1 筆查詢。
- 抽查不改答案、不排 CDN 驗證、不寫 CDN 網域資料庫；判斷錯誤的最壞情況是暫時改用自己的上游。

## 4. 上游放行下游（跟著 `allow_downstream`）

### 4.1 目標與原則

上游的 `allow_downstream` 開著時（預設），**驗證過金鑰的下游**（完成 4.2 登記的節點）除了可以串接與拿共用結果，還得到兩項放行。沒有獨立的開關、沒有逐台核准；`access.deny` 永遠優先。

| 放行 | 內容 |
|---|---|
| 加密 DNS | 登記中的下游目前的來源位址，在存取控制裡當成「社群好友」那一級允許 |
| 繞過防護清單 | 登記中的下游查它登記的上游主機名稱時，不套用標成 `bypass` 的清單 |

過濾清單多一個標記：

| UCI（`config filter_list`） | JSON（`filter.lists[]`） | 預設 | 說明 |
|---|---|---|---|
| `option bypass '1'` | `"bypass": true` | `false` | 這份是「繞過防護」類的清單（擋加密 DNS／VPN／代理的主機名稱）。`defaults.json` 與預設 UCI 裡 HaGeZi `doh-vpn-proxy-bypass` 那一筆加上這個標記（那一筆清單本身預設停用） |

**`allow_downstream` 開著代表什麼（設定頁的說明與狀態頁的上游角色區塊要寫出這個意思）**：節點金鑰是每台自己產生的，「驗證過金鑰」只證明對方會講下游協定、持有它自己那把金鑰，不證明它是誰。所以開著就等於信任區網裡**任何能跑下游協定的裝置**：任何人都能自己產生金鑰、架一個下游來登記，藉此拿到共用結果、讓 `bypass` 清單不擋它登記的名稱（每個下游最多 32 個）、讓它的位址通過存取控制。家用網路（區網裡都是自己的裝置）這是可以接受的預設；**有啟用 `bypass` 清單、要管住區網裝置不能自己換 DNS 的環境，請把 `allow_downstream` 關掉。**狀態頁列出目前連上來的下游（指紋、位址、第一次與最後出現時間），讓管理者看得到是誰。

這段說明**不放進 `/api/status` 的 `warnings`**（預設就是開，固定的警告只是噪音），只出現在設定頁的說明與狀態頁的上游角色區塊（`chain.serving.text`、`chain.serving.note`）。

### 4.2 登記（reg）

下游在 `detected` 之後、探測得到 `allow = true` 而且 `caps` 有 `"reg"`、自己的 `chain` 開著時登記（**不必等串接成立**：驗證中、或串接因故中斷而上游還在時，下游用的是自己的加密上游，bootstrap 一樣會被上游的清單擋）；之後每 5 分鐘跟著心跳更新。上游的 `allow_downstream` 關著時 `caps` 是空的，下游不登記。

查詢：`r.chain.kuroshio`、CH TXT，帶 EDNS 選項 **65313**，內容是 `Sealed`（`kind = "reg"`，**下游的金鑰簽章**）。

RegBody：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `v` | u8 | `1` |
| `t` | text | `"reg"` |
| `up` | bytes(8) | 上游的 `kid`（簽給別台的登記不能拿來這台用） |
| `tok` | bytes(16) | 最近一次 auth 回應裡的 `tok` |
| `peer` | text | 最近一次 auth 回應裡的 `peer` |
| `kid`、`pub` | bytes | 下游的節點 ID 與公鑰 |
| `app` | text | 下游版本 |
| `names` | [text] | 下游的上游主機名稱（固定、自動、備援、最後手段裡不是 IP 的主機，去重複），最多 32 個、每個要通過 `valid_domain` |
| `local` | bool | `peer` 是不是下游自己某張網卡的位址（否 = 中間有 NAT） |

上游的檢查（**四項都不可省略**，任何一項不過回 `REFUSED`）：

1. `Sealed` 驗簽（用 `body.pub`）而且 `kid == kid_of(pub)`；
2. `up` 是自己；
3. `peer` 等於這個查詢的來源位址；
4. `tok` 對這個來源位址有效（目前或前一個時間窗）。

另外 `names` 要合法。

回應：`Sealed`（`kind = "regack"`，上游簽）：`{ v, t: "regack", kid: 下游的 kid, ttl: 900 }`。只有一個開關，所以沒有「放行了哪幾項」的欄位：登記成功就是兩項都放行。下游把結果顯示在 `chain.upstream.registered`。

登記表（上游，記憶體）：最多 **16** 筆，每筆 `{ kid, pub, 來源位址, app, names, local, 第一次與最後出現時間, 到期時間 = 現在 + 900 秒 }`；同一個 `kid` 重新登記就更新（位址換了，舊位址的放行立刻失效）；滿了拒絕新的。重新載入後登記表清空，下游最慢 5 分鐘內重新登記。

### 4.3 放行的對象（不逐台核准）

登記通過 4.2 的四項檢查就算「驗證過金鑰的下游」，在登記有效期間（900 秒，下游每 5 分鐘更新）直接得到 4.1 的兩項放行。沒有核准名單、沒有核准用的管理 API，上游也不為這件事存任何檔案。

管理者看得到是誰連上來：上游的狀態頁（`chain.serving.downstreams`，見 4.5）列出每個登記中的下游的指紋、位址、版本、第一次與最後出現的時間、有沒有經過 NAT、登記了幾個名稱。不想放行時：關掉 `allow_downstream`（全部），或把某一台的位址加進 `access.deny`（加密 DNS 那一項會被 `deny` 擋下）。

保持的安全性質：

- **防重放**：`tok` 綁來源位址與 5 分鐘時間窗；登記由下游簽章並涵蓋 `tok`、`peer`、`up`。錄下別人的登記封包、從別的位址重送，`peer` 與實際來源不符；隔兩個時間窗重送，`tok` 失效。
- **綁來源位址**：放行的是登記當下的單一來源位址；同一個 `kid` 從新位址登記，舊位址立刻失效。
- **有上限、會過期**：登記表 16 筆、每筆 32 個名稱、900 秒到期；重新載入後清空。

### 4.4 放行的範圍

**加密 DNS**

- `ipfilter::Rules` 多一組 `chain`（`Dual`），判斷順序放在「社群好友」之後、`allow` 之前；`Reason::Downstream`，說明文字「已登記的下游黑潮」。`deny` 照樣優先。
- 內容＝登記沒過期的下游的來源位址，**只放單一位址**（IPv4 /32、IPv6 /128），由 `Access::set_chain(&[IpAddr])` 更新（做法同 `set_friends`）；登記表每次變動與每分鐘各更新一次。
- 套用到哪些服務照 `access.applyTo`，沒有新的規則。
- 現況提醒（寫進設定頁的說明）：下游用私有位址時本來就允許，這一項只對「來源是公網位址的下游」有差別。
- `local = false`（下游在另一台 NAT 後面）：放行的是那台 NAT 的位址，它後面的裝置都一起放行。狀態頁的清單要標「經 NAT」。
- 核心層的 nftables 規則不用改：只在 WAN 輸入鏈，下游從區網來。

**繞過防護清單**

三個條件都成立才不擋：

1. 查詢的來源位址是登記沒過期的下游；
2. 命中的是標成 `bypass` 的清單（自訂規則、其他清單命中照擋）；
3. 查詢名稱（或 CNAME 目標）在這個下游登記的 `names` 裡（完全相同，不含子網域）。

實作：

- `resolver::Verdict` 加 `bypass: bool`（`FilterService::check` 用 `v.list` 對到 `sources[i].bypass`）。
- `handle_inner` 的過濾步驟：`v.block && v.bypass && responder.exempt(ctx.client, &qname)` → 當成沒命中，繼續往下。
- CNAME 目標命中：`cache::Entry` 加 `blocked_bypass: Option<String>`（命中 `bypass` 清單的那個 CNAME 目標）；`serve()` 多一個參數，來源是登記中的下游而且那個目標在它的 `names` 裡時不回封鎖。其他用戶端拿同一個快取項目照樣被擋。
- 不改快取鍵：過濾在快取之前判斷，快取項目本身存的是上游的原始答案。

### 4.5 狀態

`/api/status` 的 `chain.serving`（上游角色；一定有這個物件，讓狀態頁看得出目前是哪一種情況）：

## 5. 低階機器的並行數

### 5.1 `resolver.parallel` 的 `auto`

`kuroshio_config::Host` 加 `aes: bool`（`has_aes()` 從 `sysinfo.rs` 搬到 `kuroshio-config`，`sysinfo` 改呼叫它）。`derive_auto`：

| 條件 | `resolver.parallel` |
|---|---|
| 沒有 AES 指令 | 2（不管幾核心） |
| 有 AES，1 核心 | 2（不變） |
| 有 AES，2 核心 | 3（不變） |
| 有 AES，3 核心以上 | 0 ＝ 全部（不變） |

- 使用者填了數字一律優先（含 `0`；UCI 的 `option parallel '0'` 轉成數字 0 ＝ 全部）。
- `has_aes()` 在 MIPS、ARMv7、RISC-V 一律是 `false`（沒有偵測的方法）。有硬體 AES 的 ARMv7 機器很少，被當成「沒有」只是保守一點，可以手動設 `0`。
- `kuroshio sysinfo` 與啟動記錄說明原因：「沒有 AES 指令：先問最快的 2 個上游，其他在背景補問」。

### 5.2 背景補問（backfill）

`parallel` 有限制（`0 < parallel < 這次的上游數`）時，沒被問到的上游原本只在失敗或 300 ms 沒有正常回應時才補上，所以「覆蓋」上游幾乎不會被問到：CDN 網域少了別家給的節點、汙染也少了比對的對象。新行為：

- 先照現在的流程回答用戶端（**不增加任何等待**）。
- 回答之後，符合下面任一條件就在背景問「這次沒問到的上游」，把結果跟前面的合在一起重新走一次 `decide()`、`merge_rank()`、`store()`（快取項目換成合併後的）：
  1. **CDN 相關**：查詢是 A／AAAA，而且剛才的答案裡有任何一個位址被 `Cdn::classify()` 認得（屬於某家 CDN 的範圍）。CDN 沒啟用時這一條不成立。
  2. **抽樣**：其他 A／AAAA 查詢每 `backfillSample` 次抽一次（預設 16）。比對：前面是正常回應，補問的上游多數（至少 2 台而且過半）是 NXDOMAIN／NODATA，或反過來 → 記一筆 `stats` 的 `backfillMismatch`，快取換成合併後 `decide()` 的結果。
- 不補問：`verbatim`（DO、類別不是 IN）、串接中（只有一台上游）、所有上游都已經問過、記憶體壓力不是 `Normal`、同時已經有 `backfillMax` 個補問在跑（1～2 核心：2；其他：4。超過就跳過，不排隊）。
- 補問的失敗照樣記在各上游的統計（`Up::record`），自動上游的暫停機制照常運作。

| UCI（`config resolver 'resolver'`） | JSON | 預設 | 說明 |
|---|---|---|---|
| `backfill` | `resolver.backfill` | `cdn` | `cdn`：上面的行為；`off`（或 `0`／`false`）：不補問（3.3.7 的行為） |
| `backfill_sample` | `resolver.backfillSample` | `16` | 非 CDN 查詢每幾次抽一次；`0` ＝ 不抽樣 |

`/api/status` 的 `stats` 多 `backfill`（補問次數）、`backfillMismatch`。

## 6. 上游多樣性（`coverage_region`）

### 6.1 怎麼判斷上游在哪裡

**程式裡現在沒有全球的 geo 資料**：`data/geo/tw-ip.json` 只有台灣網段（`kuroshio_jobs::geo::TwIp`），評測的 ip-api 查詢只拿業者與 AS。三個訊號合起來用：

| 訊號 | 來源 | 可靠度 |
|---|---|---|
| 台灣網段 | `tw-ip.json`（已經隨程式附帶、每月在本機更新），離線可用 | 高，但任播位址（anycast）登記在國外的不算 |
| 國別 | ip-api 批次查詢的 `fields` 多要 `countryCode`，跟業者資料一起存進 `cidr_cache.json`（每筆多一個選用的 `"cc"`；舊的快取沒有就是空的，只對決選的上游補查，不整批重查） | 中：任播位址給的是登記地（`1.1.1.1` 是 AU），/16 的粒度也粗（3.5.1 起快取改用 /24、30 天到期，見規格 11 的 A10.1） |
| 量到的最低延遲 | `Scored.min`（評測本來就有） | 高：任播位址實際落在哪個節點，延遲最老實。從台灣量，台灣 < 15 ms、香港 15～30、日本 30～50、新加坡 40～60、美西 > 110 |

判斷（`Scored` 多 `region: String` 與 `near: bool`）：

```
region = "TW"              如果上游位址在 tw-ip.json 裡
       = 國別碼            如果 ip-api 有給
       = ""                都沒有
near   = region ∈ {TW, JP, HK, SG} 而且 min ≤ nearMaxMs × 2
      或 min ≤ nearMaxMs（預設 60 ms；不管國別，涵蓋任播與查不到國別的）
```

理由：我們要的其實是「這台上游從哪裡去問權威伺服器」，因為那決定 CDN 回的是不是亞洲節點；對任播上游來說這只能從延遲看出來。國別是補充（延遲在 60～120 ms 之間、但確實在鄰近四地的非任播上游），也是報表上給人看的標籤。
ip-api 查不到（離線、被限速）時只靠 `tw-ip.json` 與延遲，功能不受影響。

**國別是註冊地**（3.5.0）：ip-api 的國別是 IP 的註冊地，不是實際位置（任播的公共 DNS 在東京的節點也會標成 GB、AU）。`selected[]` 多 `regionSource`：`"tw-net"`（位址在台灣網段，可信）或 `"registered"`（註冊地；舊的 `upstreams.json` 沒有這個欄位也當成這個）。`region` 的值不改（串接的下游、`auto_shared()` 都在讀）。狀態頁用 ui-core.js 的 `regionLabel` 顯示：`tw-net` 是「台灣」，註冊地是「註冊地 GB」，鄰近的是「鄰近（註冊地 GB）」，沒有國別但鄰近是「鄰近」。不用延遲推國別：延遲只能說近不近，`near` 已經在用它。

### 6.2 選擇

`select::select()` 的「覆蓋」階段分兩輪（「最快」與「備援」不變）：

1. 只在 `near` 的候選裡做貪婪覆蓋，直到台數上限或覆蓋率達標；
2. 還有名額而且覆蓋率還沒達標，才在剩下的候選裡繼續。

`coverage_region = any` 時跟 3.3.7 一樣（一輪、不分遠近）。

台灣率（3.5.0）：兩輪的每一步，新增覆蓋差在 10% 以內的候選裡先挑台灣率高的（答案本來就是台灣節點的網域比例，評測時用台灣網段算）；差距更大時照舊，台數上限、覆蓋率目標、`near` 的分輪都不變。台灣網段讀不到、或有台灣節點的網域不到 10 個時不看，跟 3.4.4 一樣。

| UCI（`config benchmark 'benchmark'`） | JSON | 預設 | 說明 |
|---|---|---|---|
| `coverage_region` | `benchmark.coverageRegion` | `near` | `near`／`any` |
| `near_max_ms` | `benchmark.nearMaxMs` | `60` | 最低延遲在這以內就算鄰近 |

輸出：`upstreams.json` 的 `selected[]` 每筆多 `"region"`（`"TW"`、`"JP"`…或 `""`）與 `"near"`；`final_dns_smart.csv` 多 `Region`、`Near` 兩欄（加在最後，舊的欄位順序不變）；`/api/status` 的 `upstreams[]` 多 `region`。`reason` 的文字（最快、覆蓋、備援）不變。評測記錄多一行「覆蓋：鄰近 N 台、其他 M 台」。

## 7. 重新載入時不斷線（選做）

### 7.1 評估

| 做法 | 評估 |
|---|---|
| `SO_REUSEPORT`：新的一輪先綁好再關舊的 | **不建議。**前提是兩輪同時活著，但現在的設計是舊的 runtime 完全結束才建新的；兩輪並存會讓快照寫入器、排程器的鎖、行程層級的狀態（路徑檢查、快取交接）同時有兩份。另外 Linux 關掉其中一個監聽時，已經排進它佇列的 TCP 連線會被重設；Windows 沒有對等的行為 |
| 把 socket 傳給新的行程 | 不適用：重新載入是同一個行程 |
| **監聽 socket 留在行程層級，每一輪拿複製品（建議）** | 可行、改動小、Linux 與 Windows 都能用 |

### 7.2 設計：`ListenBank`

- 行程層級的表（`static`，做法同 `CACHE_HANDOFF`）：鍵 `(用途, 協定, 位址)` → `std::net::UdpSocket`／`std::net::TcpListener`。
- 每一輪要監聽時向它要：表裡有就 `try_clone()`（`dup`）一份交給 tokio；沒有才綁定、放進表裡再複製。
- 舊的一輪結束時只關掉它自己的複製品，**核心裡的 socket 一直開著**：空窗期間 UDP 封包留在接收緩衝區、TCP 連線留在 accept 佇列，新的一輪接手後照常回答。用戶端看到的是 0.2～0.4 秒的延遲，不是 Connection refused。
- 新的一輪啟動完成後，表裡這一輪沒人要的項目（設定改了位址或埠、關掉了某個協定）才關掉。
- 埠是 0 的（測試）不進表。
- 範圍：一般 DNS（UDP／TCP 53）、DoT 與 DoH 的 TCP 監聽、管理介面。QUIC（DoQ／DoH3）：socket 一樣可以留著，新的 quinn `Endpoint` 建在複製的 socket 上；進行中的 QUIC 連線照舊會斷（跟現在一樣），這一點不是這次的目標。HTTP.sys 模式不適用。
- 啟動失敗改回上一份設定時 socket 還在表裡，不受影響。

### 7.3 交接的順序（3.5.1）

舊的一輪結束時（`Started::shutdown_reload`，`main.rs` 的 `generation` 收到重新載入時呼叫）照這個順序：

1. 背景工作、上游狀態、過濾清單層交給下一輪，寫出快照（最多 10 秒）。這段時間**照常回答**（快取還在）。
2. 停止收新的查詢：一般 DNS 的 UDP 接收、TCP accept，DoT、DoH 的 accept 迴圈都停下來（`Serving::quiesce`，停在等封包、等連線的地方，
   已經讀進來的不會丟）。核心裡的 socket 還開在 `ListenBank`，之後到的封包留在接收緩衝區、連線留在 accept 佇列，給新的一輪。
3. 等處理中的一般 DNS 查詢（讀進來到送出回應）做完，最多 1 秒（`QUIESCE_MAX`）：它們照常回答，問上游拿到的新答案也進了快取、跟著交出去。
   **剛接受、第一筆查詢還沒回完的 TCP、DoT、DoH 連線也等**（見下面「剛接受的連線」）。
4. 交出 DNS 快取，記下「這一輪已經交出」（`Serving::retire`）。

以前快取在寫完快照的那一刻就交出去，舊的一輪卻還在讀同一個（共用的）監聽 socket，直到執行環境關閉：

- 這段時間讀到的查詢一律沒命中、改問上游（重複問一次上游）；
- 剛好碰上執行環境開始關閉時，問上游的工作開不起來（tokio 不再接新的工作），整輪看起來像「上游全部失敗」，回了 **SERVFAIL**；
- 或是查詢讀進來了，回答之前就跟著執行環境一起被丟掉，用戶端要等逾時（通常 1～2 秒）重送。

在路由器上每次在設定頁按「儲存」都是一次重新載入，所以這是真的會碰到的（測試 `reload_never_refuses` 在機器很忙時偶爾拿到 SERVFAIL）。

交出快取之後還是可能有查詢進來（已經建立的 TCP／DoT／DoH 連線，跟以前一樣隨執行環境結束才斷）：快取命中照常回答；
要問上游而失敗的**不回 SERVFAIL**（一般 DNS、DoT 不回應，TCP 關掉連線；DoH 回 503 `Retry-After: 1`），讓用戶端重送給新的一輪。
這個判斷只在失敗的路徑上（一次原子讀取），快取命中的路徑不變；每筆一般 DNS 查詢多兩個 32 位元原子操作（處理中的計數），不加鎖。

**剛接受的連線（3.5.1）**：以前一般 DNS 的 TCP 連線要等查詢讀完才算進處理中。「已經接受、查詢還沒讀進來」的連線（剛好在寫快照～停止收查詢那幾毫秒連上的）
交接時看起來是 0 筆，快取馬上交出去、舊的執行環境結束時連線被關掉，核心回 RST，用戶端要重送（Windows 測試機重新載入 40 次裡 3 次各有 1 筆 TCP 查詢收到 10054）。
DoT、DoH 在 accept 之後、TLS 握手與第一筆查詢之前也一樣（而且它們的查詢本來就不算進處理中）。現在：

- accept 迴圈接到連線、交給連線的工作之前就算進處理中（`Serving::accept`，同時最多 64 條，`FRESH_MAX`；超過的照以前，不等）；
- 第一筆查詢的回應寫出去（DoH：第一個請求回完；沒有回應的也算）才放掉，之後跟一般的連線一樣；
- 每一個階段太久沒有動靜就提早放掉，不讓預先連上、閒著的連線拖住交接（`hold_while`；等的東西不取消，讀到一半的資料不會丟）：
  - 連上之後 200 ms（`FRESH_GRACE`）內要送來第一個位元組（一般 DNS 是查詢的長度，DoT、DoH 是 TLS 的 ClientHello，純 HTTP 的 DoH 是請求）；
  - TLS 握手 500 ms（`FRESH_HANDSHAKE`）內要完成；
  - 握手之後 200 ms 內要送第一筆查詢（DoH：第一個請求要進來；進來了就等它回完）；
- 交接等的總時間上限照舊是 1 秒（`QUIESCE_MAX`）。社群的連線（DoT 埠的 `kuroshio/2`）不算。

成本：每條 TCP／TLS 連線多幾個 32 位元原子操作與一個計時器，查詢的路徑不變（DoH 之後的請求只多一次原子讀取），不加鎖。
最壞情況：閒著的連線讓交接多等最多 200 ms（只有交接前 200 ms 內連上的）；握手或查詢卡住的最多等到 1 秒，跟處理中的查詢卡住一樣。
已經回過第一筆、之後閒著的連線照舊隨執行環境結束（用戶端在連線之間本來就要能重連，RFC 7766）；QUIC（DoQ／DoH3）、HTTP.sys 模式不在範圍。

上限與最壞情況：停止收查詢之後最多等 1 秒（處理中的查詢一般幾十毫秒內做完，只有上游卡住才會等滿）；時間到還沒做完的跟以前一樣被丟掉、
用戶端重送，日誌記一行警告。QUIC（DoQ／DoH3）的端點不在這次的範圍：進行中的 QUIC 連線照舊會斷。

測試：`tests/reload.rs` 的 `reload_stops_reading_before_handing_over_cache`（交接期間每 10 ms 一筆查詢，每一筆都剛好得到一次正確的答案；
交接時正在問上游的那一筆照常回完、答案跟著快取交出去；快取交出去之後舊的一輪不再讀監聽 socket，那一筆由新的一輪回答；上游只被問過一次），
`tests/resolver.rs` 的 `retired_round_does_not_answer_servfail`，`tests/encrypted.rs` 的 `quiesce_waits_for_fresh_connections`（交接之前連上、交接開始之後才送查詢的
一般 DNS TCP、DoT、DoH 連線都拿到答案；一直不送的連線不讓交接等滿 1 秒），`server.rs` 的 `fresh_is_capped_and_released_once`、`hold_while_releases_idle_connections_only`。

列為選做：跟其他五項沒有相依；驗收是「重新載入期間連續查詢，沒有任何一筆被拒絕」。來不及就延到 3.4.1，不影響其他項目。

## 8. 安全分析

### 8.1 威脅與對策

**前提（已決定）**：兩個開關預設都開，沒有同意、沒有核准。這代表：

- 同一個區網裡**任何會講這個協定、而且站在下游一般 DNS 路徑上的黑潮（或冒充者）都會被下游自動串接**；
- 上游會把共用結果與第 4 節的放行**給區網裡任何能產生金鑰的裝置**。

簽章在這個設計裡的作用是：證明回答的是「持有某把金鑰的同一台」（連續性）、防重放、保護共用結果不被路上的人竄改。它**不能**證明那台是使用者想要的上游。下表逐項寫清楚。

| # | 威脅 | 對策 | 殘餘風險 |
|---|---|---|---|
| T1 | 區網裡的裝置冒充上游黑潮（自己產生金鑰、回答挑戰），讓下游自動串接到它 | 冒充者必須先站在下游的一般 DNS 路徑上（能接走 53 埠：路徑檢查偵測到的就是這件事），單純在區網裡喊「我是黑潮」沒有用。已經串接之後換人：公鑰不同 → 自動重綁但記警告、`warnings` 留 24 小時、狀態頁顯示新舊指紋。路徑檢查對攔截者做已知答案與 `.invalid` 檢查，發現竄改就解除。下游可以關 `chain` | **存在（已決定接受）**：能接走下游 53 埠的攻擊者（惡意閘道、ARP 欺騙、假 DHCP）第一次就能讓下游把它當上游，之後下游的解析都經過它，也會匯入它給的評測結果與節點池（有格式與官方範圍檢查，見 T5）。相較 3.3.7（被接走時下游改用加密上游、不受影響），這是預設值換來的風險；不信任所在的區網就關 `chain` |
| T2 | 重放舊的簽章回應 | 每次挑戰用新的 16 bytes nonce，回應必須帶回而且在 1.5 秒內；不靠時鐘 | 無 |
| T3 | 區網內的主動攻擊者把挑戰原樣轉給真的上游，之後竄改一般 DNS 的答案 | 一般 DNS 的通道本身防不了。緩解：路徑檢查每 6 小時（與 WAN 變動時）對攔截者做竄改檢查，發現就解除；上游沒回應時退回加密上游；共用結果有簽章，改不了 | **存在**，程度等同上游區網裡其他用一般 DNS 的裝置。要完全排除需要「釘選公鑰的 DoT」（協定已預留 `dot` 欄位，3.4.x） |
| T4 | 攻擊者擋掉串接查詢（降級） | 降級的結果是下游用自己的加密上游，比串接更安全 | 無 |
| T5 | 竄改或偽造共用結果（讓下游用壞的上游或節點） | 清單由綁定的公鑰簽章，物件用 SHA-256 驗證，路上的人改不了。匯入前的檢查限制了惡意上游能做的事：上游清單要能解析、最多 64 筆、明文的拿掉；節點池的位址必須在各家 CDN 的官方範圍裡；清單副本只當過濾規則用 | 被自動串接的惡意上游（T1）可以給「合法但不好」的資料，等同它本來就能回答下游的任何 DNS |
| T6 | 迴圈（A→B→A） | 節點 ID 鏈、上限 4 層、綁定後的提早心跳、singleflight | 兩台同時互綁時最多 15 秒的查詢逾時 |
| T7 | 用挑戰查詢耗盡上游的 CPU（簽章）或當放大器 | 只回答私有來源的一般 DNS；每來源每秒 4 次、全域每秒 32 次；回應約 300 bytes | 區網內的小幅放大（約 4 倍），受速率限制 |
| T8 | 區網裝置自己產生金鑰、架一個假下游，拿共用結果與放行（存取控制、繞過防護清單） | **協定擋不住**（已決定不核准）。範圍限制：只回答私有來源的一般 DNS；登記要簽章、綁來源位址與 5 分鐘的憑據、15 分鐘到期；放行單一位址；繞過只限登記的主機名稱（每個下游 32 個、登記表 16 筆）而且只對 `bypass` 清單；`access.deny` 仍然優先；狀態頁列出每個連上來的下游。上游可以關 `allow_downstream` | **存在（已決定接受）**：`allow_downstream` 開著時，`bypass` 清單管不住會架假下游的裝置（它登記的名稱不擋），它的位址也通過存取控制。`bypass` 清單預設是停用的；啟用它的環境應該關掉 `allow_downstream`（設定說明與狀態頁都有寫）。下游在 NAT 後面時整個 NAT 一起放行（清單有標示） |
| T9 | 攔下登記封包從別的位址重送 | `tok` 與 `peer` 綁來源位址，上游比對查詢的實際來源 | UDP 偽造來源位址只能讓「被偽造的那個位址」被放行，攻擊者自己拿不到 |
| T10 | 透過管理 API 動手腳 | 串接沒有需要按的決定；`recheck` 是需要登入的 POST；開關只能改設定 | 同現有管理 API |
| T11 | 公開的加密監聽洩漏節點資訊 | `chain.kuroshio` 只在 `udp`／`tcp` 而且私有來源時回答，其他一律 `REFUSED` | 無 |
| T12 | 上游的節點私鑰外洩 | 金鑰檔 0600；跟社群共享同一把，輪替方式相同。輪替後下游自動重綁並警告 | 拿到私鑰的人可以無警告地冒充上游（仍然要先站在路徑上） |

**緩解的總結**：簽章防「半路換人不被發現」與重放；路徑檢查決定誰有資格被當成上游（只有真的接走 53 埠的那一台）並持續檢查竄改；上游一有異狀就退回加密上游；共用結果有簽章與匯入檢查；**任一邊都可以用一個開關完全關掉**（下游 `chain`、上游 `allow_downstream`），關掉之後行為跟 3.3.7 一樣。

### 8.2 隱私

- auth 回應給區網裡任何問的裝置：節點 ID、公鑰、版本、`allow`。這些跟 `version.kuroshio` 已經透露的同一個等級。
- 共用結果給區網裡任何問的裝置（不要求登記）：上游用哪些公開 DNS、CDN 節點、訂閱了哪些公開清單。沒有查詢紀錄、沒有自訂規則、沒有任何金鑰。不想分享就關 `allow_downstream`。
- 登記時下游把自己的上游主機名稱告訴上游：上游本來就看得到這些查詢。

## 11. 已決定的事項

| # | 題目 | 結論 |
|---|---|---|
| 1 | 開關 | **只有兩個，預設都開**：下游 `chain`（要不要辨識上游黑潮並索取資料）、上游 `allow_downstream`（要不要提供資料給下游）。兩邊都開才通訊，任一邊關就各走各的。不做 `ask`／同意流程、`chain_backup`、`chain_share`、`downstream_encrypted`、`downstream_bypass` |
| 2 | 串接通道的完整性（T3） | 3.4.0 用一般 DNS，接受「區網內主動攻擊者」的殘餘風險。釘選公鑰的 DoT 留到 3.4.x；`AuthBody` 的 `dot` 欄位維持預留（3.4.0 的上游不送、下游忽略） |
| 3 | 自動串接的信任（T1） | 接受：預設會自動串接到路徑上任何會講這個協定的黑潮。緩解是路徑檢查、竄改偵測、公鑰換了的警告、可以關 `chain` |
| 4 | 上游放行下游 | 跟著 `allow_downstream`，不逐台核准（T8 的殘餘風險已接受）。狀態頁列出連上來的下游（指紋、位址、第一次與最後出現時間）；說明只放在設定頁與狀態頁的上游角色區塊，**不放進 `warnings`** |
| 5 | 上游掛掉時 | 固定退回自己的加密上游 |
| 6 | 共用結果 | 串接就共用；`allow_downstream` 關或 `chain` 關時下游自己算，狀態頁寫明會重複使用網路 |
| 7 | 上游公鑰換了 | 自動重新綁定，記警告，`/api/status` 的 `warnings` 留 24 小時（唯一的行為）。不驗證金鑰輪替聲明 |
| 8 | 過濾清單共用的範圍 | **3.4.3 起不共用**，每台自己跟清單網址下載（理由見 3.1）。3.4.0～3.4.2：共用「上游有留副本、網址相同」的清單，3.4.2 起下游存不下副本時留在記憶體 |
| 9 | 鏈的上限 | 4 層（`MAX_DEPTH = 4`） |
| 10 | 下游的資料自主（3.4.2） | 下游自己的工作每 7 天至少照排程跑一次、上游給的 CDN 答案每 30 秒最多抽查 1 個（第 3.8 節）。抽查只看 TLS 憑證，查不出「憑證正確但不是最近的節點」這類不好但合法的答案 |
| 11 | 其他新增的設定鍵 | 照第 10 節：清單的 `bypass`（關；HaGeZi `doh-vpn-proxy-bypass` 預設帶這個標記）、`resolver.backfill`（`cdn`）、`backfill_sample`（16）、`benchmark.coverage_region`（`near`）、`near_max_ms`（60） |
