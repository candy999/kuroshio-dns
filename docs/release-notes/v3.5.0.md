黑潮 DNS 3.5.0（開發中）

## 系統、記憶體與 Windows

- **開機後沒有本機副本的過濾清單 10～15 秒就下載，而且只下載缺的**：以前開機先用本機副本建好過濾器之後，不管有沒有缺副本的清單都固定等 60 秒，缺的清單開機後約 63 秒規則都不在；到時候還把每份清單都問一遍（多半 304，但還是請求）。7.5 MB Flash 的 D3 存不下副本的那幾份每次開機都缺。現在有缺時等 10 秒加 0～5 秒亂數（讓開機的路徑檢查、bootstrap、對時先跑，很多台同時重開也不會同一秒去問），對時了、記憶體不是不足才下載，**只下載缺的那幾份**，有副本的照讀副本、不發請求，之後等到更新間隔再檢查。全部都有副本時照舊 60 秒。缺的下載失敗時照既有的退避（60 秒起）重試。日誌寫明「N 份沒有副本的 X 秒後下載」。
- **記憶體不足時一次停用多份過濾清單、只重建一次；恢復時也一樣**：以前缺口大時一份一份停用，每停用一份就重建整個過濾器一次（新舊兩份同時在記憶體裡），停用 5 份就重建 5 次，CPU 與記憶體的尖峰都發生在最缺的時候；恢復也是一份一份（3.4.2 Windows 實測恢復 7 份重建 7 次）。現在記憶體控制把「還缺多少」告訴這一步，依原本的停用順序取到估計合計 ≥ 還缺的 × 1.3（扣掉同一輪快取、CDN 已經讓出的）一次停用、只重建一次；恢復時從最後停用的開始，取到合計 × 1.3 放得進可用空間的一次恢復、只重建一次。重建的尖峰只會比以前低（新的一份比較小），保護清單照舊不在這一步，恢復後很快又吃緊時的退避照舊。日誌是「暫時停用 N 份清單：…（重建 1 次）」。
- **記憶體「不足」路徑的測試開關（給測試者）**：以前要在記憶體很多的機器（512 MB 的 D3、Windows）上測停用清單、只轉送、恢復，只能真的把記憶體吃掉。現在設定 `system.testHooks: true` 後可以用 `kuroshio notify simulate-memory --avail-mb 20 --minutes 5`（或 `POST /api/memory/simulate`）模擬系統可用記憶體只剩 20 MB，最長 30 分鐘、到期自動恢復，`--off` 立刻取消。只會讓讀數變小、不影響系統層；生效期間每分鐘一行 WARN、`/api/status` 的 `memory.simulated`、狀態頁黃色橫幅。`testHooks` 預設關、不放進 LuCI 與設定頁，沒開時 API 回 403。用法見 `docs/spec/09-memory.md` 第 11 節。
- **Windows 主控台關閉視窗、登出、關機時正常停止**：以前用 cmd 執行時只有 Ctrl+C 會正常收尾；按視窗的關閉鈕、登出、關機、Ctrl+Break 時行程直接被系統結束，學習資料（快照）沒寫、日誌也沒有最後一行。現在這五種都走同一個正常停止，日誌寫「收到主控台關閉，正常停止」之類的一行。關閉視窗、登出、關機時 Windows 大約 5 秒後就強制結束行程，所以這三種寫快照最多 3 秒（小檔先寫，寫不完的下次啟動用上一次存的），Ctrl+C 與服務停止照舊 10 秒。服務模式的流程沒有變。

## 小修正

- **CDN 關掉時，`/api/status` 的 `cdn` 是 `{"enabled": false}`**：以前是 `null`，看不出是關掉還是讀不到（D3 3.4.3 回報）。
- **記憶體控制讓出不到 1 KB 的步驟不寫 WARN**：例如快取本來就是空的時，「縮小 DNS 快取（約 0 KB）」。只收 WARN 日誌的小機器上這些是雜訊；改成除錯等級（D3 3.4.3 回報）。
- **追蹤網域時標出「被閘道接走」的一般 DNS**：一般 DNS 在路上被路由器攔下時，`/api/trace` 每個上游多 `viaInterceptor`、`note`，表示回答的其實是攔截者，不是那個位址（D3 3.4.2 回報：1.0.0.2、8.8.4.4 其實都是主路由器在回答）。

- **OpenWrt 的 LuCI 讀得到串接狀態、可以重新檢查**：rpcd 的白名單以前沒有 `/api/chain` 與 `/api/chain/recheck`（直接查會回「不允許的路徑」）。現在開放，狀態頁的串接區塊多一個「重新檢查上游黑潮」按鈕（只重新偵測，不改任何設定）。也開放唯讀的 `/api/cdn/domain`、`/api/cdn/cross`。padavan 韌體的 `kuroshio.sh api` 白名單在韌體那邊，路徑表寫在整合說明。

## CDN 台灣節點

- **每週的 CDN 網段掃描（cdn-scan）每秒新連線有上限、開始時間錯開**：
  - 以前：同時 50～400 個探測、沒有節流。到 CDN 只有幾毫秒時，Windows 實測每秒 1,832～1,904 條新 TCP 連線（多半是 80 埠），會塞滿路由器的連線追蹤表。每台都在週日 03:20 準時開始。
  - 現在：每秒最多開始 `scan.maxPerSec` 個探測（預設依 CPU 核心數，每核心 50、50～200；小記憶體減量 `cdn.lite` 時再減半）。前面的探測卡住逾時之後也不會一次補回來。開始時間每台往後錯開 0～30 分鐘（`jobs.cdn-scan.jitterMin`）。
  - 掃描的網段數沒有減少，只是攤開。開始時的日誌寫「每秒最多 N 個探測，預計 X～Y 分鐘」。最壞情況（約 2.4 萬個 /24、每段 6 個探測、每秒 25 個）約 96 分鐘，在 240 分鐘的逾時內。
- **「為什麼沒換到台灣」**：管理 API `GET /api/cdn/explain?name=` 與 LuCI、Windows 設定頁的「為什麼沒換到台灣」按鈕：哪家 CDN、換或不換、原因（驗證中、驗證沒通過、小機器減量等第二次、沒有台灣節點、手動設定、串接中由上游處理、記憶體最低限度…）與驗證結果。只讀，不會因為查了就排驗證或連網路。以前要自己對照 `/api/cdn/domain` 的原始紀錄。

## 串接

- **重新啟動後第一次跟上游同步不再固定等 30 秒**（老毛子 3.4.2 回報：每次都是先 `refused`、30 秒後才成功）：
  - 以前：上游的共用清單 30 分鐘沒人用就釋放；下游重新啟動後第一次同步時，上游才開始建，先回 REFUSED，下游隔 30 秒再試。
  - 現在上游：下游登記成功時就先在背景建好清單（下游約 30 秒後才第一次同步，那時通常已經建好）。舊版的下游接新版的上游也受益。
  - 現在下游：遇到 REFUSED 時隔 5、15、30 秒再試（各加 0～20% 亂數），仍然最多連續 3 次。新版的下游接舊版的上游也受益。
  - 不會形成風暴：一台下游最多多 2 筆重試，上游同時只建一份清單，記憶體吃緊時照舊不建。

## 查詢紀錄（除錯用）

- **管理介面可以看最近的查詢**：網域、類型、來源、結果（快取、上游、擋掉、過期資料）、延遲、答案來源。`GET /api/querylog`；`POST /api/querylog/enable?minutes=10` 暫時開啟。
  - 以前：設定裡有 `log.queryLog`、`system.queryLogRing`，但 3.x 的程式沒有用到。
  - **只在記憶體、預設關閉**：不寫磁碟、不進備份、不給公開頁、不傳給上游／下游／好友。暫時開啟最長 60 分鐘，到時間自動關閉並釋放。
  - 有上限：筆數（`system.queryLogRing`，預設 2 萬筆；實體記憶體 160 MB 以下最多 1,000 筆、512 MB 以下最多 5,000 筆），每筆固定約 160 bytes。
  - 不拖慢查詢：關閉時每筆查詢只多讀一次旗標；開著時查詢不等紀錄的鎖，拿不到就丟掉那一筆。

## 效能量測

- **`/api/status` 多了效能計數器 `perf`**：3.4.2 測試時，D3（MT7621，沒有 AES 指令）單獨運作、每秒 20 筆查詢時延遲高，CPU 閒置只剩 12～18%，原因還沒證實（懷疑是自己做 TLS 的負擔）。這一版先量、不改：
  - 加密上游（DoT、DoH）的握手是完整還是續用 session、協商到 AES 還是 ChaCha20，連線失敗幾次；QUIC 連線數。
  - 每次詢問實際送出幾個上游查詢、背景補問送出幾個。
  - 只在握手完成、詢問結束時加一次計數（32 位元原子操作，沒有鎖），查詢路徑沒有變慢。
  - 下一批依老毛子在 D3 上量到的結果決定要不要改（例如沒有 AES 的機器偏好 ChaCha20）。
