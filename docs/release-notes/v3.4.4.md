黑潮 DNS 3.4.4：串接的小修正（3.4.3 的 Windows 複驗與 D3 實測找到的）。

重點：
- **鎖定了上游指紋（`chainPin`）時，不向別台登記主機名稱**：以前指紋不符、不串接之後，還是把這台的主機名稱登記給那一台。
- **鎖錯指紋時寫清楚原因**：狀態頁寫「跟設定的 chainPin 不符」，原因代碼是新的 `pin-mismatch`。以前寫「簽章不對」，看起來像上游有問題。
- **上游黑潮解析不到、改問自己的上游時，只有一台回空答案不採用**：照上游的 SERVFAIL。
- **串接中，自己的上游不再被壞網域的逾時暫停**。

## 鎖定上游指紋（`chainPin`）

兩邊都回報了同一件事（Windows 複驗 G5、D3 S3）：指紋不符、解除串接後 20 毫秒，日誌還是寫「已向上游黑潮登記（4 個主機名稱）」。登記跟驗證是分開跑的，登記只看探測本身的簽章對不對，沒看 `chainPin`。鎖定指紋就是不信任別台，主機名稱不該交出去。現在指紋不符就不登記。

原因代碼也分開了：
- 以前指紋不符算成 `verify-failed`。狀態頁寫「上游黑潮的身分驗證失敗（簽章不對）」，日誌寫「簽章、nonce 或節點 ID 不對」。使用者自己鎖錯指紋時，會以為上游有問題。
- 現在 `/api/chain` 的 `reason` 是 `pin-mismatch`，狀態頁寫「不串接：上游黑潮的指紋跟設定的 chainPin 不符（設定鎖定的是別台），用自己的上游」。
- 重試的方式不變：60 秒起，每次加倍，最長 10 分鐘。

## 上游黑潮解析不到時，自己再解析的兩個修正

3.4.3 起，上游黑潮回 SERVFAIL 時，下游用自己的加密上游再解析一次。實測找到兩個問題：

**只有一台的空答案不採用**（Windows 複驗 G7）
- 情況：權威伺服器掛掉的網域，自己的上游大多沒回應，偶爾有一台回「沒有這種記錄」（NOERROR 空答案）。以前照用，裝置拿到的是「網域存在、只是沒有 A 記錄」，不是 SERVFAIL。
- Windows 實測：3.4.2 是 SERVFAIL 的 28 個網域，3.4.3 有 9 個變成這種空答案。抽查 5 個，其他公共 DNS 都是 SERVFAIL。
- 現在：自己的上游問了兩台以上、只有一台回否定答案（空答案或不存在）時不採用，照上游的 SERVFAIL；兩台回同樣的否定答案才採用。自己的上游只有一台時，照用它的答案。

**自己的上游不再被壞網域的逾時暫停**（Windows 複驗 G6）
- 情況：串接中，自己的上游只收到「上游黑潮解析不到」的網域，大多是壞掉的網域，常常逾時。3.4.2 起 SERVFAIL 只在「同一輪有別台正常回答」時才算失敗，但沒回應還是立刻算。沒有成功的查詢把連續失敗歸零，所以一直被暫停。
- Windows 實測：10 分鐘的負載裡，nextdns、controld、funil 被暫停 5 次（1→2 分鐘，會繼續加倍）。上游黑潮真的掛掉時，可以退回的自己的上游就少了。
- 現在：只在這種重問時，沒回應的上游也跟 SERVFAIL 一樣，同一輪有別台正常回答才算失敗。平常的查詢不變。

## 沒有在這一版處理的

- **狀態分割區小的時候，清單副本比學習資料優先**（D3 建議）：
  - D3 的情況：解除串接的 10 分鐘裡，自己做 CDN 驗證，CDN 網域資料（核心資料，256 個分片）變大。之後狀態分割區少留一份清單副本，每次重新啟動多下載一份（約 2 MB）。
  - 這要調整儲存空間的分級（現在 CDN 網域資料是核心資料，不會自動刪；清單副本是可省略的）。CDN 網域資料丟掉就要重新驗證，也是重複的工作，兩邊怎麼取捨要另外設計，放進 3.5.0。
- D3 建議放進 3.5.0 的照舊：
  - 「稍後下載」的約 63 秒延後。
  - `cdn.enabled` 關時 `/api/status` 的 `cdn.enabled` 是 null。
  - 讓出 0 KB 的記憶體控制步驟也寫 WARN。
  - 一直沒成功的自動上游。
  - padavan 韌體 `kuroshio.sh api` 的白名單要加 `/api/chain`（這是韌體那邊的腳本）。
